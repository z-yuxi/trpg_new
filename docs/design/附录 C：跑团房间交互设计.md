#### 4.1.2.1 私密场参与者存储与消息可见性
**参与者存储**：
- 每次角色加入私密场（GM 添加或申请通过）插入一条记录，`joined_at = 当前时间`，`left_at = NULL`。
- 角色退出整个团时，将所有 `left_at = NULL` 的记录更新为退出时间（不删除历史）。
**消息可见性规则**：

| 场类型 | 新成员加入时可见历史 | 默认可见条数 | GM 是否可配置 |
| --- | --- | --- | --- |
| 剧情场 | ❌ 不可见 | 0 | 否（固定规则：`history_visibility = 'none'`） |
| 私密场 | ✅ 当前仍在参与者列表时可见全部历史；退出后完全不可见 | 全部 | 否（固定规则） |
| 公共场 | 默认不可见；可改为可见最近 N 条 | 50 | 是（仅支持 `none` / `recent` 两档；`recent` 下可在 10-200 条间调整） |

**公共场历史消息可见性（统一口径）**：

| 设置项 | 默认值 | 可选范围 | 说明 |
| --- | --- | --- | --- |
| `history_visibility` | `none` | `none` / `recent` | GM 在场景设置中修改 |
| `visible_history_count` | 50 条 | 10-200 条 | 仅 `recent` 模式生效 |

- `none` 模式（默认）：新成员加入该公共场后，看不到加入前的任何历史消息。
- `recent` 模式：新成员加入后，可看到最近 `visible_history_count` 条消息；超过该数量的更早消息不可见。
- 已有成员：始终可查看自己加入后到现在的全部消息。
- GM：始终可查看全部历史，不裁剪。

**技术实现（写扩散）**：
- 为每条消息预计算可见用户列表，存储在 `chat_messages.visible_to` JSON 字段中。
- 剧情场：消息对发送时处于该场的角色对应用户可见；历史查询时继续按角色在场区间过滤，防止玩家回场后补看离场期间的内容。
- 私密场：消息仅对 `scene_participations` 中 `left_at IS NULL` 的角色对应用户可见；角色退出后立即失去该私密场全部历史的查看权限。
- 公共场：消息对团内所有活跃成员可见；历史查询时，新加入成员再叠加 `history_visibility` / `visible_history_count` 规则裁剪加入前可见片段。
- GM 查询消息时不使用 `visible_to` 过滤，确保全量可见。
- OB（旁观者）默认仅可查看剧情场；公共场按公共场权限规则查看；私密场默认不可见。
- 当主持人在私密场中手动授予指定 OB「旁听权限」后，该 OB 可查看该私密场中授权时刻之后的新消息；未授权部分与授权前历史仍不可见。
- `visible_to` 是技术层的权限兜底机制，不是产品层的"悄悄话"功能。产品层的私密沟通通过创建私密场（Virtual Scene）实现。

**剧情场历史消息过滤规则**：

当玩家查看剧情场历史消息时，系统基于该角色在该剧情场的在场状态进行过滤：

1. 查询该角色在该剧情场的所有在场区间，数据来源以 `position_history` 为准。
2. 仅返回落在任一在场区间内的消息；角色离场后产生的对话、掷骰、线索揭示等内容，对该玩家不可见。
3. 若角色多次进出同一剧情场（如 14:00-15:00 和 17:00-18:00 两次在场），返回两个时间段内的消息并集；离场期间的内容即使后来回场也不可补看。
4. **系统级豁免**：`message_type` 为 `system` 的进出场、时间推进等系统事件可在时间点快照中显示，用于解释角色移动；不因此放开普通对话内容。
5. **`visible_to` 叠加**：在场状态过滤和 `visible_to` 取交集。消息必须同时满足"该玩家在消息产生时处于场内"且"你在 `visible_to` 列表中（或 `visible_to` 为 null）"才可见；当 `visible_to = []` 时，视为对所有角色不可见（仅系统内部占位）。
6. **时间基准**：实现查询优先使用 `messages.story_time` 与 `position_history.story_time_entered/story_time_left` 判断在场状态；若该条消息或移动记录缺少剧情时间，再回退到真实时间顺序。

**私密场历史规则（QQ 群模式）**：

1. 当前仍在 `scene_participations` 参与者列表中的角色，可查看该私密场从创建到现在的全部历史。
2. 已退出私密场的角色，对该私密场立即变为完全不可见；既不能看新消息，也不能回看历史。
3. 从未加入过该私密场的角色，始终不可见。
4. GM 默认拥有全部私密场访问权；玩家侧不提供"退出后保留历史"的例外。

**各角色视角的时序裁剪行为**：

| 角色  | 时序裁剪                      | 说明                 |
| --- | ------------------------- | ------------------ |
| GM  | 不裁剪                       | GM 在所有模式下看到场景的全部消息 |
| OB  | 剧情场不裁剪；私密场默认不可见 | 可看剧情场全部消息；私密场仅在主持人手动授权后可见授权后的新消息（仍不可导出日志） |
| 玩家（剧情场）  | 按在场状态裁剪                  | 仅看自己在场期间产生的消息 |
| 玩家（私密场）  | 按当前参与者身份过滤               | 当前在群内可看全部历史，退出即完全不可见 |

**与"我的剧本"导出的关系**：
- 玩家导出日志时，系统根据上述时序裁剪规则，仅导出该角色有权限看到的消息片段。
- 玩家不会看到自己离开剧情场期间的消息；私密场则仅在当前仍为参与者时允许导出全部历史，退出后不可导出任何内容。



**实现逻辑**：
- 剧情场：角色只能看到其在场区间内的消息；离场期间内容即使后来回场也不可补看。
- 私密场：当前仍在 `scene_participations` 参与者列表中的角色可见该私密场全部历史；退出后立即完全不可见。
- 公共场：新加入成员按 `history_visibility` 决定加入前可见历史；`none` 返回 0 条加入前消息，`recent` 返回最近 `visible_history_count` 条加入前消息，加入后的消息始终完整可见。
- 服务器全量保留所有消息，导出时按上述规则过滤。

**与“我的剧本”导出的关系**：
- 玩家导出日志时，系统根据上述可见性规则，仅导出该角色有权限看到的消息片段。
- 玩家不会看到自己离开期间的消息，也不会看到新加入前的剧情场/私密场消息。
#### 私密场权限细则

**玩家创建的私密场**：
- 任何玩家可在任何时间创建私密场
- 创建者自动成为该私密场的“主持人”（非 GM）
- 主持人可邀请其他玩家加入（邀请时自动包含 GM）
- 主持人可解散自己创建的私密场
- 主持人不可踢人（如需移除玩家，只能解散后重建）

**GM 创建的私密场**：
- GM 可创建私密场并直接指定参与者
- GM 可随时进入任何私密场，默认以“旁听”进入，并可在场内一键切换为“参与”。
- GM 可解散任意私密场（无论创建者是谁）

**私密场 OB 授权（默认关闭）**：
- 默认状态下，OB 不可查看任何私密场内容。
- 私密场主持人（该私密场创建者）或 GM 可手动为指定 OB 开启该私密场的「旁听权限」。
- 旁听权限按“私密场 + 指定 OB”粒度生效，不会自动继承到其他私密场。
- 授权后，OB 仅可查看授权时刻之后的新消息；不回补授权前历史。
- 关闭旁听权限后立即生效，OB 失去该私密场查看权限。
- 即使开启旁听权限，OB 仍不具备主持人/GM能力：不可发言、不可掷骰、不可管理成员、不可导出日志、不可访问 GM 私有数据（如 GM 笔记/暗骰）。

**系统自动创建**：
- 开团时若勾选“为每位玩家自动创建私密场”
- 系统为每个玩家创建一个包含「该玩家 + GM」的私密场

### 5.2 时间系统与移动机制

#### 4.2.1 时间架构

- **本地时间**：真实时间戳，用于消息排序（雪花ID）和技术日志；每条消息不向用户显示时间戳，用户可通过**长按（移动端）/右键（PC端）**查看精确到秒的发送时间。
    
- **剧情时间标签**：GM手动宣布，系统在当前场景的聊天流末尾插入一条 `message_type = 'time_tag'` 的特殊消息，内容格式为 `HH:MM`（仅时、分，不含日期）。标签只出现在聊天流中，不固定显示于顶部栏或任何 UI 组件。
    
- **时间记录**：后端在 `campaigns.global_story_time` 存储最新已宣布时间（供查询用）；`position_history.story_time_entered/left` 存储 GM 审批移动时**可选填**的剧情到达时间（精确到分钟，不填则为 `null`）。
    
- **无自动推进**：系统永不自动推进时间，也不自动插入任何时间标签。时间的唯一来源是 GM 手动操作。公共场不使用时间标签，消息 `story_time` 字段始终为 `null`。

- **时间单调递增**：GM 宣布的剧情时间必须 ≥ 当前 `global_story_time`，系统拒绝时间回退操作。若 GM 需要修正时间错误，应通过强制移动等操作修正结果，而非回退时间本身。

- **大幅推进确认**：开团招人 设定的新时间与当前时间差 > 2 小时时，前端弹出二次确认弹窗："确定将时间从 {当前时间} 推进到 {新时间} 吗？这将触发期间所有预约移动，且不可撤销。"小幅调整（≤ 2 小时）不弹窗。

- **预约移动自动触发**：GM 宣布时间推进后，系统自动检查所有 `status = 'approved'` 且 `execute_at_story ≤ 新时间` 的预约移动，按预约时间从早到晚逐个执行（见 4.2.5 自动调度规则）。


#### 4.2.2 移动审批机制（核心玩法）

```plain
流程：
玩家申请移动（选择目标剧情场） 
  → GM审批弹窗（批准/拒绝 + 可选填写"剧情到达时间 HH:MM"） 
  → GM点击批准 → 系统立即执行移动（原子操作） 
  → 更新角色位置 
  → 若填写了剧情到达时间，写入 position_history.story_time_entered
  → 聊天流插入过渡消息："张三 离开酒馆，前往教堂"（不显示耗时）
  → 轨迹矩阵更新（会员可见）
```

**约束与规则**：

- **数量限制**：每个角色同时最多存在 **1条** 待审批的移动申请

- **位置唯一性**：每个角色同时只能处于一个剧情场（参与私密场不改变位置）

- **两种执行模式**：
  - **即时执行**：GM 审批时不填写预约时间 → 批准后立即执行移动
  - **预约执行**：GM 审批时填写剧情到达时间（HH:MM）→ 批准后等待剧情时间到达自动执行（见 4.2.5）

- **预约语义**：预约的含义是"在某时间到达目标场景"，不绑定出发地。若角色在等待期间被 GM 强制移动到其他场景，预约仍然有效。

- **玩家可取消**：玩家可自行取消自己处于 `pending` 状态的预约移动（"改主意了"），无需 GM 操作。

    
**移动执行的事务原子性**：
- GM 点击批准时，服务端开启数据库事务，执行以下操作（按顺序）：
  1. 校验目标场存在且为剧情场；若无效则返回错误。
  2. 更新 `campaign_character_instances` 中的 `current_spatial_scene_id`。
  3. 若GM填写了剧情到达时间：
     - 更新 `position_history` 中该角色的旧记录（将 `story_time_left` 设为到达时间）；
     - 插入新记录（`story_time_entered = 到达时间`, `story_time_left = NULL`）；
     - 更新 `campaign_character_instances.personal_story_time`；
     - 更新 `campaigns.global_story_time`（供后续查询参考）。
  4. 若GM未填写时间：仅更新位置，不写入时间字段（`story_time_entered = NULL`）。
  5. 将移动申请状态改为 `executed`。
  6. 提交事务。
- 若事务中任何步骤失败，整体回滚，并向 GM 返回错误。

**系统过渡消息**：
- 移动执行后，系统在聊天流插入：`{角色名} 离开 {源场景}，前往 {目标场景}`（不显示耗时、时间信息）。

**场景连通与路径规划**（高阶功能，需启用）：
- GM 可预先配置剧情场之间的连通关系及不同交通方式（步行、骑行、驾车）的参考耗时，数据存储于 `scene_connections` 表。
- 玩家申请移动时，系统根据所选交通方式自动计算最短路径和参考耗时，供GM参考填写剧情到达时间。
- GM 审批时可查看系统建议，并允许手动覆盖（如修改时间）。
- 支持碰撞检测查询（仅会员）：GM 可在轨迹矩阵中查询指定角色的时空交集。

> 注：该功能对推理本尤其重要，能够精确记录每个角色的时空轨迹，提供不在场证明分析。

**可见性总结**：
- **完整版轨迹矩阵为 GM 专属会员功能**，玩家不可见。
- **玩家仅通过左侧导航的"路线图"纯文本列表及聊天区系统消息感知移动事件**，且不知道其他角色的具体目标场景。
- 系统过渡消息格式统一为：`{角色名} 离开 {源场景}，前往 {目标场景}`（不含耗时、时间信息）。

#### 4.2.3 强制移动（GM特权）

GM可右键角色选择"强制移动"：

- 立即执行，取消该角色所有未执行预约
    
- 计入位置历史表（`move_type = 'force_move'`）
    
- 在剧情Log中标记 `[GM强制]`
    
- 助理台显示系统提示："🔨强制移动：玩家A 从 图书馆 移动至 密室"
    
**强制移动特性**：
- 立即执行：角色瞬间传送到目标场景，不经过玩家申请环节。
- GM可在弹窗中选填剧情到达时间（可选），写入 `position_history`。

##### 4.2.3.1 交互状态细则：强制移动

> 强制移动本身不属于“拒绝申请”动作；但若 GM 的强制移动覆盖了该角色已有的待执行移动申请，系统必须自动取消原申请，并将取消原因记录为“GM 强制移动覆盖原申请”，同步通知玩家。

| GM 操作 | 前端反馈 | 后端动作 | 异常处理 |
|:---|:---|:---|:---|
| 在角色列表或单元格右键 -> “强制移动” | 弹出模态框，标题“强制移动 {角色名}” | - | - |
| 选择目标场景，选择“立即执行”，点击【确认强制移动】 | 弹窗关闭，角色瞬间移动。聊天区插入系统消息：“`[GM强制] {角色名} 被移动至 {目标场景}`”。该角色所有未执行的预约自动取消 | 更新角色位置，写入位置历史（`move_type = 'force_move'`）；取消相关预约 | 事务失败回滚 |
| 选择目标场景，选择“设定剧情时间”，填写时间后确认 | 同上，但聊天消息中附加到达时间 | 按定时执行创建已批准预约（跳过玩家申请），`execute_at_story` 为指定时间 | 时间必须晚于当前全局时间，否则拒绝 |
| 在轨迹矩阵中多选单元格，右键批量强制移动 | 弹窗汇总所有角色名，确认后批量执行 | 逐条处理，每条独立事务 | 某条失败不影响其他，并在结果中提示失败项 |

#### 4.2.4 场景生命周期管理

**场景状态**：

| 状态 | 含义 | 可进入 | 消息保留 | 玩家可见 |
|------|------|:------:|:------:|:------:|
| `active` | 活跃场景 | 是 | 是 | 是 |
| `archived` | 已归档（历史保留，不可进入） | 否 | 是 | 否（GM 视角可展开查看） |
| `hidden` | GM 预准备中 | 仅 GM | 是 | 否 |

**状态转换**：
- `active` → `archived`：GM 归档场景，已有数据保留，角色不可再进入
- `archived` → `active`：GM 恢复归档场景
- `active` → `hidden`：GM 隐藏场景（用于预准备下一幕场景）
- `hidden` → `active`：GM 公开隐藏场景

**物理删除保护**：

场景仅在同时满足以下四个条件时才允许物理删除：

| 条件 | 校验 |
|------|------|
| 消息数 = 0 | `chat_messages` 中该 `scene_id` 计数为 0 |
| 轨迹数 = 0 | `position_history` 中该 `scene_id` 计数为 0 |
| 从未被进入 | `scene_participations` 中该 `scene_id` 计数为 0 |
| 创建时间 < 24 小时 | `created_at > NOW() - INTERVAL 24 HOUR` |

**不满足任一条件 → 仅提供"归档"操作，不提供删除按钮。**

**场景分组**：GM 可创建分组（幕 / Act），将场景拖入分组中组织管理。分组为纯视图层，不影响场景本身的数据和行为。

##### 4.2.4.1 交互状态细则：场景管理操作

> 与审批拒绝的联动：当场景状态为 `hidden` 时，GM 拒绝玩家前往该场景的移动申请时，可直接选择预设理由“目标场景尚未开放”，无需手动填写。

| 操作 | 二次确认 | 前端反馈 | 后端动作 | 异常处理 |
|:---|:---|:---|:---|:---|
| GM 点击“归档场景” | ✅ 弹窗：“归档后场景将不可进入，剧情历史保留。确定归档？” | 场景在列表中变为“已归档”灰色标记，不可进入 | `scenes.status` 变为 `archived` | - |
| GM 点击“隐藏场景” | ✅ 弹窗：“隐藏后玩家将看不到此场景，仅 GM 保留访问。确定隐藏？” | 场景在玩家端消失，在 GM 端显示“（隐藏）” | `scenes.status` 变为 `hidden` | - |
| GM 点击“恢复场景” | 否（直接操作） | 场景状态恢复为 `active`，列表中正常显示 | `scenes.status` 变为 `active` | - |
| GM 点击“删除场景” | ✅ 弹窗：“此操作不可逆。若场景内有历史消息则仅可归档。确定删除？” | 若满足删除条件则删除，否则提示“场景有关联数据，只能归档” | 校验四个条件，通过则物理删除 | - |

#### 4.2.5 预约移动自动调度

开团招人 宣布时间推进（`announceTime`）后，系统自动检查并执行所有到期的预约移动。

**触发规则**：
- **精度**：分钟级。只要 `新宣布时间 ≥ 预约时间（execute_at_story）` 即触发。
- **顺序**：多个预约按 `execute_at_story` 从早到晚逐个执行，保证因果链正确（角色 A 12:00 去图书馆，16:00 从图书馆去警局，两个预约必须按序执行）。
- **不合并**：每次移动独立生成 `scene_event` 消息，保持事件颗粒度。

**冲突处理**：

| 冲突场景 | 处理方式 |
|---------|---------|
| 目标场景 `status ≠ active`（已归档或隐藏） | 预约状态改为 `cancelled`，向玩家发送系统消息："{角色名} 前往 {场景名} 的预约已取消（目标场景已关闭）" |
| 角色已不在战役中（被移除或退出） | 静默取消预约（状态改为 `cancelled`），不发通知 |
| 角色状态为 `dead` | 静默取消预约，不发通知 |
| 等待期间角色被 GM 强制移动到其他场景 | **预约仍然有效**。预约语义是"到达目标"而非"从某地出发" |

**预约移动状态机**：
```plain
                  ┌──────────┐
                  │ pending  │
                  └────┬─────┘
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
   (GM 审批通过    (玩家取消)    (自动取消)
    + 时间到达)        │            │
          │            ↓            ↓
          ↓        [cancelled]  [cancelled]
     [executed]                     │
                        ┌───────────┴───────────┐
                        │                       │
                  目标场景非 active          角色非 active
                  → 通知玩家               → 静默取消
```

**前端交互**：
- **玩家侧**：角色面板显示当前 pending 预约列表（目标场景 + 预约时间 + [取消] 按钮）
- **GM 侧**：导演台"此刻"仪表盘显示即将自动执行的预约移动时间线

### 5.3 轨迹矩阵（GM控制台可视化）
> **可选模块**：轨迹矩阵是一个高级功能，默认不启用。GM 在创建团时可在「高级设置」中勾选“启用轨迹矩阵”。启用后，系统开始记录角色位置历史，并在 GM 控制台显示矩阵视图。该功能属于 **会员专享**。

> **⚠️ 只读约束**：本矩阵为系统自动记录的权威数据源，**所有 GM 只能查看，禁止手动编辑单元格**。角色位置和剧情时间的修正必须通过系统功能（强制移动、移动审批、时间标签插入等）完成，不可直接修改表格。多 GM 打开控制台时，看到的是同一份只读数据，保证状态一致。
**视觉设计**：

- **横轴**：剧情场列表（按创建顺序）
    
- **纵轴**：时间轴（固定按 `position_history.story_time_entered` 排序，支持加载更多）
    
- **灰白分区**：
    
    - **灰色单元格**：已发生的时间点，显示角色历史位置（头像缩略图）
        
    - **红色竖线**：当前最近已宣布时间点
        
    - **白色单元格**：未来时间点，显示虚线框"将移动至X"（预约移动预览）
        

**交互功能**：

- 点击单元格查看该时刻该场的角色卡状态快照
    
- 支持批量选择时间范围导出剧情回顾
    
- 拖拽调整预约移动的时间（需重新审批）
    
**只读约束**（重申）：
- 轨迹矩阵为系统自动生成的只读数据，GM 不可直接编辑单元格。
- 如需修正角色位置，请使用强制移动功能；如需修正角色名称，请编辑角色卡。

**辅助操作**：
- 右键单元格 → “移动此角色到此场” → 自动创建强制移动（立即执行）。
- 支持多选单元格（Ctrl+单击）进行批量强制移动。
- 单元格内容可选中并复制（但不可修改）。

**移动可视化**（当启用场景连通功能时）：
- 对于处于“在途”状态的角色，轨迹矩阵中对应时间切片不显示头像，而是在时间轴左侧或单元格背景显示移动图标；图标映射固定为：步行=🚶、骑行=🚲、载具=🚗，未知方式统一回退为 🚶。
- 鼠标悬停图标显示详细提示：“角色A 正在从酒馆步行前往图书馆，剩余12分钟，路径：酒馆→走廊→图书馆”。
- 单击图标可查看该移动的完整路径及历史记录。

#### 4.4.5 成团流程

**触发条件**：
- 人数已满时自动触发成团。
- GM 可在未满员时手动点击【成团】触发。

**流程**：
1. 系统检查该招募帖是否已关联 `campaign`（即是否来自路径 B 先建团后发帖）。
   - **若已关联**：直接将该房间的成员列表更新为所有通过申请的玩家，并推送通知。
   - **若未关联**（路径 C：先发帖后成团）：
    - **a. 模组确认**：
      - 若发帖时模组状态为"已选定"，成团时直接使用该已选定模组。
      - 若发帖时模组状态为"无模组"，成团时直接创建空白团（无预设模组内容）。
       - 若发帖时模组状态为"待定"，弹出模态框：
         - 成团 - 选择模组  
          ○ 从已获取资产（「团途」→个人馆藏）中选择已有模组 [下拉▼]  
           ○ 创建一个空白模组（即兴团）  
           [取消] [确认成团]
     - **b. 创建房间**：系统根据招募帖的规则包和选定的模组状态自动创建房间（私密）。
     - **c. 导入内容**：若绑定了模组，自动导入场景、NPC、线索等。
2. 系统通过站内通知和私信向所有通过申请的成员发送房间码。
3. 房间自动出现在所有成员「房间」标签中。
4. 招募帖状态变为"已关闭"。

**边界情况**：
- 若成团时 GM 取消模组选择，则流程中止，招募帖保持原状态。
- 若成团时模组选择"创建一个空白模组"，则创建的房间无预设内容，GM 需在房间内手动添加。

> **与附录 B 对齐**：成团弹窗中的已通过玩家默认勾选、模组选择三种选项（使用已选定/从已获取资产中选其他/创建空白团）需与附录 B 6.2 完全一致，不得擅自修改。

```typescript
// 统一消息结构（剧情场、私密场、公共场共用）
interface ChatMessage {
  id: string;                      // 雪花 ID，全局单调递增
  scene_id: string;
  campaign_id: string;
  sender_user_id: string;
  sender_character_id?: string;    // 若为 GM 广播或系统消息可为空
  content: string;
  message_type: MessageType;
  story_time: StoryTime | null;    // 公共场为 null；time_tag 类型消息的 content 即为时间字符串
  visible_to: string[];            // 可见的用户 ID 列表（写扩散）
  client_timestamp?: number;       // 客户端本地时间戳（辅助排序）
  created_at: Timestamp;           // 服务端接收时间
  metadata?: {
    dice_result?: DiceResult;
    character_snapshot?: object;
    clue_id?: string;
  };
}

// 消息类型枚举（V2.1 修订：从原 system 中拆分出 scene_event 和 gm_ledger）
type MessageType =
  | 'narrative'       // 角色剧情对话/叙事
  | 'dice'            // 骰子检定结果
  | 'ooc'             // 场外闲聊（导出日志时默认不包含）
  | 'clue_card'       // 线索卡
  | 'scene_event'     // 场景事件：角色进出场景的提示消息，受时序裁剪，仅场景内在场玩家可见
  | 'time_tag'        // 时间标签：GM 宣布剧情时间推进，豁免时序裁剪
  | 'announcement'    // GM 公告：面向全体的通知，豁免时序裁剪
  | 'system'          // 系统通知：技术性全局通知（如玩家掉线），豁免时序裁剪
  | 'gm_ledger';      // GM 台账：不进入聊天流，仅写入 GM 助理台（如完整移动路径记录）

// 消息类型可见性规则速查表：
// ┌──────────────┬──────────┬─────────────────────────────────────┐
// │ 类型          │ 时序裁剪  │ 说明                                 │
// ├──────────────┼──────────┼─────────────────────────────────────┤
// │ narrative    │ 受裁剪    │ 仅在场期间可见                         │
// │ dice         │ 受裁剪    │ 仅在场期间可见                         │
// │ ooc          │ 受裁剪    │ 仅在场期间可见                         │
// │ clue_card    │ 受裁剪    │ 仅在场期间可见                         │
// │ scene_event  │ 受裁剪    │ 角色进出提示，仅场景内在场玩家可见          │
// │ time_tag     │ 豁免      │ 历史查询时始终返回                      │
// │ announcement │ 豁免      │ 历史查询时始终返回                      │
// │ system       │ 豁免      │ 历史查询时始终返回                      │
// │ gm_ledger    │ 不适用    │ 不进入 chat_messages 聊天流             │
// └──────────────┴──────────┴─────────────────────────────────────┘



// 全局公告（特殊类型）
interface GlobalAnnouncement {
  id: string;
  campaign_id: string;
  content: string;
  story_time: StoryTime;
  sender_gm_id: string;
  target_scenes: ('spatial' | 'virtual' | 'lobby')[]; // 广播范围
}
```

**消息排序规则**：
- 统一按 `id` 升序排列（雪花 ID 单调递增，反映服务端接收顺序）。
- 不依赖 `story_time` 排序——剧情时间仅用于轨迹矩阵（会员）和日志导出，不影响聊天流展示顺序。

**数据库表说明**

- `story_time` 以 JSON 格式存储，无需拆分为独立列。
    
- 排序在应用层完成，不依赖数据库索引优化。

##### 4.5.1.1 交互状态细则：消息发送失败占位符与重试

> 所有发送失败的消息必须遵循以下统一占位格式，禁止在业务组件中自行实现。

###### 消息状态视觉规范

| 消息状态 | UI 表现 | 用户操作 |
|:---|:---|:---|
| `pending`（发送中） | 气泡半透明（opacity: 0.6），左侧显示旋转加载动画（16px） | 不可操作，等待自动重试 |
| `sent`（发送成功） | 正常气泡，右侧显示绿色对勾图标（12px，可选关闭） | 无 |
| `failed`（发送失败） | 气泡右下角显示红色感叹号图标（20px），气泡背景微红（`var(--color-danger-bg)`） | 点击感叹号弹出菜单：<br>• **重新发送**：立即重试一次<br>• **删除**：从本地消息流中移除 |
| `retrying`（手动重试中） | 同 `pending` 状态 | 不可操作 |

###### 重试队列行为

| 场景 | 行为 |
|:---|:---|

### 4.5.3 公共场的特殊规则
 
> - 公共场**不使用剧情时间**，因此聊天消息的 `story_time` 字段为 `null`，仅使用 `created_at` 本地时间排序。
>

>     
> - 用户可通过**长按（移动端）/右键（PC端）**消息，在弹出菜单中查看该消息的真实发送时间（精确到秒，来自服务端 `created_at`）。公共场和剧情场均适用此操作。

**公共场身份展示规则**：

### 4.5.4 消息可靠性保障（弱网场景）

为保证弱网和断网场景下的消息顺序一致性及可靠性，系统在服务端雪花ID排序基础上，增加客户端侧的可靠性机制。

#### 排序规则（重申）

消息列表的最终排序严格遵循：

1. **剧情时间 `story_time`**（升序，公共场为 `null` 时排最后）
    
2. **服务端雪花ID `id`**（升序）
    

`client_timestamp` **仅用于调试和审计，不参与业务排序**。这保证了所有用户在同一时间看到的消息顺序完全一致，不受各设备本地时间差异或网络波动影响。

#### 弱网场景补充机制

|场景|问题描述|解决方案|
|---|---|---|
|**发送中网络断开**|消息未到达服务端，但用户已点击发送|客户端维护本地消息队列，未确认消息标记为 `pending`，网络恢复后自动重试|
|**服务端已处理但客户端未收到ACK**|消息实际已入库，但客户端因丢包未收到确认|客户端重连时携带本地最新消息ID，服务端返回断线期间消息列表，客户端根据雪花ID去重合并|
|**乱序到达（先发后至）**|因网络路径差异，后发送的消息可能先到达客户端|客户端对收到的消息进行缓冲区排序，检查序列号连续性，缺失时短暂等待（最多500ms）后再渲染，避免显示错乱|
|**消息重复推送**|重连时可能推送已接收过的消息|客户端维护已接收消息ID的LRU缓存（最多缓存500条），重复消息直接丢弃|

#### 客户端本地发送队列与重试策略

typescript

interface PendingMessage {
  local_id: string;               // 客户端生成的临时ID（UUID）
  scene_id: string;
  content: string;
  message_type: string;
  client_send_time: number;       // 毫秒时间戳（仅用于本地排序）
  retry_count: number;            // 已重试次数
  status: 'pending' | 'sent' | 'failed';
}
// 重试策略：指数退避
const RETRY_SCHEDULE = [1000, 3000, 7000]; // 1秒、3秒、7秒
async function sendMessageWithRetry(msg: PendingMessage) {
  while (msg.retry_count < RETRY_SCHEDULE.length) {
    try {
      const serverId = await socket.emitWithAck('chat_message', msg);
      // 收到服务端雪花ID，更新本地状态为sent，建立local_id -> server_id映射
      updateLocalMessageStatus(msg.local_id, 'sent', serverId);
      return;
    } catch (e) {
      msg.retry_count++;
      if (msg.retry_count === RETRY_SCHEDULE.length) {
        markAsFailed(msg.local_id); // 显示红色感叹号，允许用户手动重试
        return;
      }
      await sleep(RETRY_SCHEDULE[msg.retry_count - 1]);
    }
  }
}

#### 重连同步与去重流程

1. 客户端WebSocket重连成功后，发送 `join_room` 事件，携带 `last_event_id`（本地已接收的最大雪花ID）。
    
2. 服务端从消息环形缓冲区（Redis）中查询 `id > last_event_id` 且 `visible_to` 包含当前角色的消息，通过 `missed_messages` 事件批量下发。
    
3. 客户端收到后：
    
    - 遍历每条消息，检查本地LRU缓存中是否已存在该ID。
        
    - 若存在则跳过；若不存在则插入本地数据库并更新UI。
        
    - 同时检查序列号连续性：若发现ID缺口（如收到1005，但本地最大ID为1003），则向服务端主动拉取缺失的1004（通过 `/api/messages/missing` 接口）。
        
4. 去重缓存最大保存500条ID，超出后按LRU淘汰。

#### 4.6.2.3 网格地图（可选模块）

**定位**：为 DND 等需要战术移动的规则提供角色位置可视化。该功能默认关闭，开团时由 GM 启用，属于 **会员专享**。

**启用方式**：
- 团创建/编辑界面 → 高级设置 → ☑ 启用网格地图（用于 DND 风格战术移动）
- 启用后，剧情场右侧会增加一个“地图”标签页，显示当前场景的网格和角色 Token。
- 若不启用，前端不加载地图组件，`character_scene_states.position` 字段不会被写入。

**数据模型**：
- `character_scene_states` 表预留 `position` JSON 字段，存储坐标：`{"x":3, "y":5, "layer":0}`
- 引擎不解析该字段，仅由前端地图组件读写。

**交互**：
- GM 可上传背景图片作为地图底图，设置网格大小（如 50x50 像素）。
- Token 拖拽按角色权限控制：默认仅 GM 可拖拽；开启“玩家可移动自己角色”后，玩家仅可拖拽自己的 Token。系统自动更新 `position` 字段并广播给同场景成员。
- 支持多个图层（如地面、高空），可切换。
“**移动端适配**：为保障触屏体验，移动端采用静态地图预览与列表选择坐标的简化交互，完整的拖拽功能请在 PC 端使用。”

**技术实现**：
- 地图组件独立打包，通过 `import()` 动态加载。
- 使用 Canvas 渲染网格，支持缩放、拖拽视口。
- 位置变化通过 Socket.IO 广播，仅同场景成员接收。

**会员限制**：
- 免费用户：不可启用网格地图。
- 会员用户：可启用，且享有全部地图功能（上传底图、多图层、无限 Token）。

   - GM 可临时创建线索（名称 + 内容），同样进入线索库。
   
2. **GM 设置呈现样式**：
   - 在线索库中点击线索旁的“🎨 样式”按钮。
   - 选择六大文字艺术化主题之一（如“血字滴落”）。
   - 调整参数（速度、强度等），实时预览。
   - 保存后，该线索的呈现样式被记录（存储到 `campaign_clues` 表）。

3. **GM 发放线索**：
   - 点击线索旁的“📤 发放”按钮，选择接收范围（全员/指定角色/私密场）。
   - 系统在聊天室中生成一条特殊消息：
     - 消息类型为 `clue_card`
     - 内容包含线索 ID、标题、缩略提示（如“一张染血的纸条”）
     - 不直接显示完整文字

4. **玩家接收线索**：
   - 聊天消息中显示一个可点击的卡片（标题 + 主题图标）。
   - 点击后弹出模态框，按照 GM 设置的呈现样式展示完整内容。
   - 该线索同时出现在玩家的“个人线索簿”中，同样支持艺术化查看。

5. **技术实现**：
   - 线索数据存储：`campaign_clues` 表（id, campaign_id, title, content, presentation_style JSON, created_by）。
   - 聊天消息中 `message_type = 'clue_card'`，`metadata.clue_id` 关联线索。
   - 前端根据 `presentation_style` 动态加载对应的 CSS 主题。
    - 线索消息的 `visible_to` 根据 GM 发放时选择的接收范围（全员/指定角色/私密场）计算，写入 `chat_messages.visible_to`。
    - 若选择“私密场”，则只对该私密场当前参与者可见（与普通私密场消息规则一致）。

### 4.6.5 GM 共用笔记（可协作表格）

**定位**：一张自由格式的在线表格（类似 Excel / 腾讯文档），供 GM 记录暗线、NPC 状态、线索整理、房规说明等非结构化信息。与系统数据（角色卡、轨迹矩阵）完全独立。

**核心能力**：
- **多 GM 实时协同编辑**：主 GM 可添加副 GM，多人同时编辑同一份表格，实时同步，互不覆盖（单元格级锁）。
- **权限分层**：
  - 主 GM：可编辑内容、可增删 Sheet、可设置是否公开给玩家、可管理副 GM 权限。
  - 副 GM：可编辑内容，不可修改表格结构、不可改变公开状态。
- **公开给玩家**：主 GM 可一键切换“公开模式”，开启后所有玩家在只读视图中查看表格内容（实时同步，不可编辑）。
- **版本历史**（可选，推荐）：自动保存操作记录，支持回滚到任意历史版本。

**交互 UI**：
- 在 GM 控制台增加标签页“共用笔记”，默认显示空表格（可预设几行示例）。
- 顶部工具栏：
  - “公开给玩家”开关（默认关闭）
  - “添加 Sheet”、“删除当前 Sheet”（仅主 GM 可见）
  - “查看版本历史”（可选）
- 玩家端：在房间侧边栏固定显示“GM 公示表”（仅开团招人 开启公开时可见，只读）。

**技术实现要点**：
- 前端组件：统一使用 **Luckysheet**（开源、支持协同编辑）。
- 后端存储：表格数据结构（行列、样式、合并单元格等）以 JSON 格式存储于数据库（如 `gm_shared_table` 表），每张表有独立 ID 关联 campaign。
- 实时同步：通过 WebSocket 广播操作，固定使用 OT 算法，单元格级锁防止冲突。
- 公开模式：玩家端渲染同一份数据但设为只读，不广播编辑操作。
- 权限：复用 `campaigns` 表中的 `gm_user_id` 和 `assistant_gm_ids` 字段。
- 共用笔记中插入的表情包统一走富文本图片通道，渲染方式为 `<img>` 标签，不走 SvgIcon；上传时限制类型为 PNG / GIF / WebP，单张 ≤ 2MB。

**与现有功能的关系**：
- 独立于“轨迹矩阵”（系统只读）、“助理台 GM 私密面板”（简短文本笔记）。
- 与“招募管理”、“角色卡编辑”等无直接数据交互。

**会员限制**（可选）：
- 免费版：不支持多 GM 协同，仅主 GM 可编辑，不可公开。
- 专业版/创作者版：支持多 GM 协同 + 公开给玩家。
## 4.7 跑团日志系统

### 4.7A 高光时刻分享

#### 一、高光时刻分享

**功能定位**

用户在跑团聊天流中选择一段精彩对话，生成一张精美的分享卡片，发布到讨论区“跑团分享”板块，或保存到个人叙途页作为跑团纪念。

**设计理念**：用户自己选择哪些是精彩片段，AI不需要判断。平台提供工具降低创作门槛，让用户专注于内容本身。

**分享流程**
1. 进入多选模式：用户在聊天流中长按一条消息，进入“多选模式”
2. 选择消息：勾选2-20条消息，被选中的消息高亮显示
3. 生成分享卡片：点击“分享精彩片段”按钮，系统将选中的消息打包，生成分享卡片预览
4. 编辑与发布：用户可添加一句话点评（选填，100字以内），选择是否标记“包含剧透”，确认后发布

**分享卡片结构**

| 展示元素 | 说明 |
| --- | --- |
| 团名与时间标签 | 显示“来自《团名》的精彩片段”，以及对应的时间标签 |
| 模组绑定 | 如果团绑定了模组，卡片显示模组名称 |
| 对话内容 | 按时间顺序展示选中的消息，每条消息显示角色名和内容 |
| 发布者信息 | 发布者的头像和昵称 |
| 剧透标记 | 如果发布者勾选了“包含剧透”，卡片顶部显示剧透预警 |

**数据存储**
选中的消息ID列表 + 团信息（团名、时间标签）+ 绑定的模组ID（如果有）+ 发布者信息 + 剧透标记

**私密场内容分享限制**

| 限制类型 | 具体规则 | 状态 |
| --- | --- | --- |
| 主持人审核 | 私密场内容分享需经过该私密场的创建者（主持人）或GM审核通过 | 必选 |
| 团结束后开放 | 私密场内容仅可在对应团结束后分享，防止剧透 | 必选 |

生效逻辑：两个限制为“且”关系，缺一不可。剧情场的公开对话分享不受此限制。

#### 二、剧透保护机制

**设计原则**
平台只负责标记，用户自己做决定。不采用平台主动筛选（如判断用户是否玩过该模组），而是通过发布者标签 + 读者端手动展开的方式，把选择权交还给用户。

**发布者端**
发布者在分享时，系统显示轻量提示：“请确认此内容不包含剧透信息。分享包含剧透的内容可能影响其他玩家的游戏体验。”
发布者可勾选“包含剧透”标签。

**读者端**

| 场景 | 展示方式 |
| --- | --- |
| 非剧透分享 | 正常展示卡片内容 |
| 被标记为剧透的分享 | 卡片默认折叠，显示“本内容包含剧透，点击查看”，用户手动点击后展开 |

**模组完成状态验证（后续版本可选）**
标记过“已玩过该模组”的用户，展开剧透内容前不再弹出额外提示。标记方式：
1. 在“叙途-成长履迹”中有该模组的完成记录 → 自动识别
2. 用户手动标记“我在其他平台拥有此模组” → 荣誉机制，不强制验证

#### 三、分享与模组的绑定

**绑定逻辑**
分享帖携带module_id字段，指向对应的模组。如果团绑定了模组，分享卡片自动绑定该模组。

**信息流跳转路径**

| 起点 | 跳转方式 | 终点 |
| --- | --- | --- |
| 模组集市详情页 | “玩家分享”板块 | 直接看到该模组的所有高光时刻分享 |
| 讨论区分享帖 | 帖子内的模组名称链接 | 跳转到模组详情页 |
| 叙途个人馆藏 | 跑团记录中的分享列表 | 查看自己和队友分享过的片段 |

均为单向一次点击跳转，不存在多层嵌套。

### 4.7.1 设计原则

- **全量记录**：所有剧情场、私密场消息自动入库，按真实时间（雪花ID）排序

### 4.7.4 我的剧本（My Story）详解

**定位**：玩家的「个人跑团回忆录」，按**个人剧情时间线**重组。

**数据组装逻辑**（伪代码）：
```typescript
function assembleMyStory(userId: string, campaignId: string): LogEntry[] {
  // 1. 获取该用户有权查看的所有片段
  const fragments = await db.fragments.where({
    campaign_id: campaignId,
    $or: [
      { scene_type: 'spatial', visibility: 'public' },               // 剧情场
      { scene_type: 'virtual', $and: [                               // 私密场：当前仍为参与者时可见全部历史
          { character_id: userId },
          { left_at: null }
        ]
      },
      { scene_type: 'lobby', history_visibility: 'recent' }          // 公共场：按可见性配置
    ]
  }).orderBy('story_time_start').get();
  // 2. 按剧情时间排序，场切换时插入分隔符
  return fragments.flatMap((frag, index) => [
    {
      type: 'scene_transition',
      scene_name: frag.scene_name,
      story_time: frag.story_time_start,
      note: frag.scene_type === 'virtual' ? '（私密对话）' : ''
    },
    ...frag.messages
  ]);
}
```

**可见性过滤详细规则**：

- **剧情场**：只返回该角色加入时间点之后的消息（以 `character_scene_states.joined_at` 为准）。
    
- **私密场**：仅当该角色当前仍在 `scene_participations` 参与者列表中时，才返回该私密场全部历史；一旦退出，则该私密场整体完全不可见。
    
- **公共场**：新加入成员若 `history_visibility = 'recent'`，返回加入前最近 `visible_history_count` 条消息；若 `= 'none'`，不返回加入前历史。成员加入后的消息始终返回；GM 不受该裁剪限制。

## 4.7.6 权限矩阵与视角选择（严格版）

| 角色         | 我的剧本          | 完整剧本   | 模拟他人视角                 |
| ---------- | ------------- | ------ | ---------------------- |
| **GM（房主）** | ✅ 自己的         | ✅ 所有内容 | ✅ **关键能力**：可模拟任意玩家视角导出 |
| **玩家（PL）** | ✅ 仅自己的        | ❌      | ❌                      |
| **OB（观战）** | ❌             | ❌      | ❌                      |
| **退出成员**   | ✅ 导出自己参与期间的内容 | ❌      | ❌                      |

**GM 的"上帝视角导出"流程**：
1. 点击「导出日志」
2. 选择模式：
   - **A. 完整剧本**（进入拖拽编辑器）
   - **B. 模拟玩家视角** → 下拉选择玩家「张三」→ 系统生成该玩家能看到的内容（GM 可用于核对信息泄露或帮玩家制作 Replay）

- OB 在任何情况下都**不可导出日志**。

**日志导出消息类型过滤**：

导出日志时，系统提供以下过滤开关：

| 选项 | 默认值 | 说明 |
|------|--------|------|
| 包含剧情叙事（narrative） | ☑ 开 | 核心剧情内容 |
| 包含骰子结果（dice） | ☑ 开 | 技能检定记录 |
| 包含线索（clue_card） | ☑ 开 | GM 发放的线索 |
| 包含场景事件（scene_event） | ☑ 开 | 角色进出场景记录 |
| 包含场外闲聊（ooc） | ☐ **关** | 默认过滤，导出纯净剧情流 |

- `gm_ledger` 类型消息不进入聊天流，不在导出范围内。
- `time_tag`、`announcement`、`system` 类型消息始终包含在导出中（不可关闭）。
- 默认关闭 OOC 是跑团平台的标配行为——导出的日志应为纯净剧情流。

## 4.7.7 三种导出模式的最终定义（整合版）

### 模式一：我的剧本（My Story）
**技术定义**：`filter: message.visible_to 包含当前用户 或 依据场景参与规则可见（剧情场在场区间 / 私密场当前参与者）`

**排序策略**：强制使用**主轴交织**（以该玩家参与的剧情场为主轴，其参与的私密场作为分支插入）

**特殊能力（GM 专属）**：
- GM 可选择「模拟玩家 X」，导出该玩家的「我的剧本」
- 这用于：帮玩家制作 Replay、核对信息是否泄露、创作模组时验证视角

### 模式二：完整剧本（Full Script）
**技术定义**：`filter: none`（全量数据）

**排序策略**：
- 默认：**主轴交织**（剧情场为主，私密场按时间插入）
- 可选：**场优先序**（适合分章节阅读）
- **必须**：提供**可视化拖拽编辑器**，允许 GM 自由调整

**分轨视图选项**（PDF/HTML 导出时）：
```
[剧情场时间线] ───────────────────────────────
    │           │           │
    ▼           ▼           ▼
[私密场A]   [私密场B]   [GM密谈]
（并行展示，用颜色区分，适合理解多线并发）
```


当**同一剧情时间**（如第1日 20:15）存在多个场同时发生时：

| 排序策略 | 算法逻辑 | 适用场景 | 可读性 |
|---------|---------|---------|--------|
| **严格时序**<br>Strict | 按毫秒级 `created_at` 精确排序，跨场穿插 | 追求绝对真实的时间线，适合仲裁争议 | 低（阅读碎片化） |
| **场优先序**<br>Scene-First | 先排完场 A 的所有消息，再排场 B（按场创建顺序） | 分幕阅读，适合按场景复盘 | 中（场景内连续，但时间跳跃） |
| **主轴交织**<br>Main-Interleave | 以**剧情场**为主轴，私密场作为"分支"插入在合适位置 | 平衡真实性与可读性 | 高（推荐默认） |
| **玩家自定**<br>Custom | GM/导出者在可视化界面拖拽调整 | 制作 Replay、出版级模组 | 极高（完全可控） |

**默认推荐**：**主轴交织策略**
```
第1日 20:15 【酒馆】（剧情场 - 主轴）
张三：我要了杯酒...
[刺客密谈分支开始 → ]
第1日 20:15 【小巷】（私密场 - 分支）
刺客A：计划是什么？
[ ← 刺客密谈分支结束，回到主轴 ]
第1日 20:20 【酒馆】（剧情场 - 主轴继续）
李四：我看到你离开了一会儿...
```

### 排序算法伪代码

```typescript
function sortFragments(fragments: Fragment[], strategy: SortStrategy): Fragment[] {
  switch(strategy) {
    case 'strict':
      return fragments.sort((a, b) => a.created_at - b.created_at);
      
    case 'scene-first':
      // 先按场分组，场内按时间排序
      const byScene = groupBy(fragments, 'scene_id');
      return Object.values(byScene).flatMap(sceneFrags => 
        sceneFrags.sort((a, b) => compareStoryTime(a.story_time, b.story_time))
      );
      
    case 'main-interleave':
      // 剧情场为主轴，私密场插入到开始时间最近的剧情场之后
      const spatial = fragments.filter(f => f.scene_type === 'spatial')
        .sort((a, b) => compareStoryTime(a.story_time, b.story_time));
      const virtual = fragments.filter(f => f.scene_type === 'virtual')
        .sort((a, b) => compareStoryTime(a.story_time, b.story_time));
      
      return interleave(spatial, virtual, (s, v) => {
        // 私密场插入到：时间 >= 它且最近的剧情场之后
        return v.story_time >= s.story_time;
      });
  }
}
```

4.8 模组来源与衍生管理
4.8.1 模组身份定义
新增模组来源标签体系，在模组创建时永久确定：

标签	含义	产品表现
原创	创作者完全独立创作的作品	作者版标识（品牌蓝色，实心）
作者版	原作者入驻后亲自发布的版本	作者版标识（品牌蓝色，实心）
社区贡献·待认领	用户搬运，作者未入驻，等待认领	社区标识（中性灰色，空心）
社区贡献·已授权	搬运版，经作者审核批准后公开	社区·已认领标识（绿色）
衍生创作	基于他人作品的二次创作	溯源链接 + 衍生标识
已认证的独立创作	衍生版通过转原创认证，脱离原授权体系	独立创作标识（金色）
4.8.2 社区版模组生命周期
上传入口：非创作者用户可通过“叙途”→“个人馆藏”的「导入社区模组」入口上传。此入口对所有登录用户可见，无需创作者身份。

强制版权声明闸门：用户进入上传流程前，必须通过互斥单选框完成版权声明：

○ 我是此模组的原创作者，或有合法授权 → 跳转创作者中心使用完整导入功能

○ 本模组为免费公开发布资源，本人承诺无版权纠纷 → 强制填写原发布链接（必填）+ 来源说明（选填），然后进入上传

校对与发布：AI解析完成后，用户进入校对预览界面，可进行有限修改（修正错误、补全信息、调整分类、删除冗余），但不可直接修改原文。完成后可选择：

路径A：私有导入（community_status = 'private_use'）：仅自己可见，保存在“个人馆藏”，不触发审核，不产生贡献者权益展示

路径B：公开分享（community_status = 'public_share'）：通过轻量自动审核后，公开可见，标记为“社区贡献·待认领”，贡献者名字进入社区贡献墙

“放弃录入”选项：在校对预览界面，除“确认导入”外，必须有一个“放弃并删除记录”按钮。点击后，AI解析的半成品被彻底清除，不进入“个人馆藏”。

4.8.3 认领与分流逻辑
场景A：作者未入驻平台
模组状态直接为社区贡献·待认领，可出现在公开搜索中，可被浏览、获取、开团。此时不需要任何审核。

场景B：作者已入驻平台
系统检测到同名/高相似度模组后，新上传的版本进入社区贡献·待审核状态，仅上传者自己可见，不可公开搜索。需经过原作者审核后才能转为社区贡献·已授权并公开。

互斥规则：待认领与待审核是互斥状态。同一模组在同一时间，永远不会同时处于这两种状态。

4.8.4 原作者的三级授权体系
作者认领模组后，可在创作者后台设置对该模组的衍生管理策略：

模式	行为	溯源链接
开放生态	允许公开衍生，衍生版强制展示溯源链接	强制
封闭保护	查重系统直接拒绝高相似度新模组的公开申请	无
授权审核	衍生版可提交申请，由作者审批。与“致作者的信”+AI审核报告联动	批准后强制
4.8.5 衍生链的“家族树”模型
完整溯源：所有模组在数据库记录完整溯源链。上游节点即使失效，溯源链不断，但失效节点标记为“源模组已失效”。

分权管理：每个创作者只管理自己版本的直接衍生品，无权管理下游衍生品。创作者B基于A的版本创作了衍生版，B可以管理基于B版本的衍生申请，但不能管理基于A版本的其他衍生品。

转原创认证：衍生者可申请转原创，需向平台提交申请。平台审核通过后，该模组标记为已认证的独立创作，在家族谱中保留记录但脱离原作者的授权体系。

4.8.6 认领后的“7天缓冲期”与“封存”机制
时限：原作者认领后，有7天（168小时）时间决定如何处理已存在的社区版。

处理选项：

保留：社区版进入“已授权”状态，成为原作者认可的衍生版本

下架：社区版进入“封存”状态

封存不抹除：若作者选择下架，模组状态变为应作者要求已封存，从公开列表隐藏。但已获取该模组的用户不受影响，仍可在“叙途-个人馆藏”中查看和使用。贡献者的贡献记录和积分不消失，但在其“叙途”页中，该记录状态显示为“已封存”。

短信通知节点：

认领发生时，立即向贡献者发送短信：“【共叙】你上传的《{模组名}》已被原作者认领。请于7天内登录处理，过期版本将自动封存。详情见站内信。”

缓冲期最后24小时，若贡献者仍未登录，再次发送短信提醒。

7天期满后，若作者未主动选择，默认转为“保留”（已授权状态）。

4.8.7 贡献者激励与“致作者的信”
申请理由：提交公开/衍生申请时，必须填写“致原作者的信”。不设字数上限，支持基本富文本（换行、粗体、列表）和最多3张图片附件。定位为“一次正式对话”。

AI审核报告：提交申请时，系统自动生成一份审核报告，包含：全维度相似度概览、改动内容摘要（新增/删除章节、关键实体变更清单）、合规性预检（敏感内容、版权来源复杂性）。此报告供原作者决策参考。

荣誉协作者：被认领后，贡献者成为“永久荣誉协作者”，名字和贡献历史永久展示在模组叙阅器页底部（灰底小字区域，非侵入式）。此标签仅在叙阅器作品详情页可见，在跑团房间、讨论区等非创作场景中，系统强制隐藏。

4.8.8 叙途页的资产展示逻辑
在叙途“个人馆藏”中，当用户同时拥有同一模组的作者版和社区版时，合并展示为一张卡片。卡片上标注主版本标识（如“作者版”）。点击进入叙阅器详情后，可在叙阅器内部切换查看“作者版”或“社区版”的内容。避免用户看到重复卡片的困惑。

### 5.7 实时通信安全

采用 Socket.IO 作为传输层，在业务中间件层实现以下安全机制：

|安全机制|实现方式|验收标准|
|:--|:--|:--|
|**连接认证**|Socket.IO 握手时从 auth.token 获取 JWT，服务端中间件校验|无效 token 拒绝连接，返回 auth_error|
|**房间权限**|加入剧情场/私密场时校验角色是否有权限|私密场仅允许参与者加入，剧情场允许团内成员|
|**频率限制**|Redis 滑动窗口，单用户 5 条/秒，突发 10 条|超限消息丢弃，客户端收到 rate_limited 事件|
|**身份验证**|发送消息时校验 sender_character_id 是否属于当前用户|防止伪造他人角色卡发送消息|

#### 4.7.6 时间控制与预约移动

##### 全局剧情时间显示

- **所有成员**：顶部栏显示当前全局剧情时间（只读）
- **GM 特权**：
  - 点击推进按钮（`+30m`、`+1h`）执行固定步进推进。
  - 点击时间数字（`第N日 HH:MM`）打开自定义时间选择器（滚轮，精确到分钟）。
  - 两个入口独立生效，不互斥。

##### 时间推进确认弹窗（GM）

**触发**：
- 固定步进推进：GM 点击时间推进按钮（+30 分钟、+1 小时）。
- 自定义推进：GM 点击时间数字并在选择器内确认目标时间。

**弹窗内容**：
- 提示文本："推进全局时间至 第X日 HH:MM"
- 列出将触发执行的所有预约移动（角色、起点、终点、预计到达时间）。
- 若某移动的目标场景已被删除，该项显示红色警告，并注明"将被自动取消"。
- 若某移动的目标场景类型不是剧情场，该项显示红色警告，并注明"将被自动取消"。
- 按钮：【取消】【确认推进】

**确认后行为**：服务端在事务中执行时间推进、更新角色位置、记录位置历史，并通过 Socket.IO 广播结果。

##### 玩家申请移动

**入口**：
- 助理台指令速查中的 `[申请移动]` 按钮
- 输入 `/move` 指令

**界面元素**：
- 标题："申请移动"
- 下拉选择器：目标场景（列出当前团所有剧情场）
- 交通方式下拉（仅当团启用场景连通时显示）：步行 / 骑行 / 驾车
- 预计耗时（自动计算，只读）
- 预计到达时间（自动计算，只读）
- 按钮：【取消】【提交申请】

**交互规则**：
- 入口：
  - 助理台指令速查中的 `[申请移动]` 按钮。
  - 输入 `/move` 指令。
- 选择目标场景后，若启用场景连通且选择了交通方式，系统根据连通表自动计算预计耗时和到达时间。
- 若未启用场景连通，则只显示目标场景选择，不显示交通方式和耗时。
- 点击【提交申请】后，生成一条 `status = 'pending'` 的预约移动记录，并向 GM 发送待审批通知。

**数据来源**：
- 目标场景列表：从 `scenes` 表中查询当前团的 `type = 'spatial'` 的记录。
- 耗时计算：从 `scene_connections` 表中查询最短路径并累加耗时。

##### GM 审批面板

**入口**：GM 控制台 → "待审批移动"标签页。

**界面元素**：
- 标题："待审批移动"
- 表格列：申请人 | 当前位置 | 目标场景 | 交通方式 | 预计耗时 | 申请时间 | 操作
- 操作按钮：【批准】【拒绝】【修改时间】（每个申请一行）

**交互规则**：
- 入口：GM 控制台 → "待审批移动"标签页。
- 点击【批准】：弹出时间修改框（预设到达时间 = 当前全局时间 + 预计耗时），GM 可调整。确认后预约移动状态变为 `approved`，并通知玩家。
- 点击【拒绝】：预约移动状态变为 `cancelled`，通知玩家申请被拒绝（可选填理由）。
- 点击【修改时间】：仅修改到达时间，状态保持 `pending`，并通知玩家时间已调整。
- 若目标场景已被删除，该行显示红色警告，且【批准】按钮禁用。

**数据来源**：
- 待审批列表：从 `scheduled_moves` 表中查询 `status = 'pending'` 且 `campaign_id = 当前团` 的记录。
- 角色信息：关联 `character_sheets` 表获取角色名。
- 场景信息：关联 `scenes` 表获取场景名。

##### 强制移动（GM 特权）

**入口**：
- 左侧导航在场角色列表中，右键角色 → "强制移动"
- 轨迹矩阵单元格右键 → "移动此角色到此场"

**弹窗**：

```
┌─────────────────────────────────────────────────────────┐
│  强制移动 张三                                          │
│  目标场景：[下拉选择剧情场 ▼]                           │
│  到达时间：[立即] / [设定剧情时间：第1日 09:00]         │
│  [取消]                                [确认强制移动]   │
└─────────────────────────────────────────────────────────┘
```

- 立即执行：取消该角色所有未执行预约，直接更新位置和个人时间为当前全局时间。
- 定时执行：创建一个已批准的预约移动（跳过玩家申请环节），到期自动执行。
- 聊天区插入 `[GM强制]` 标记的系统消息。

##### 预约移动执行（系统自动）

开团招人 推进全局时间时，系统自动检查所有 `status='approved'` 且 `execute_at_story <= 新时间` 的预约移动，按时间升序依次执行：

1. **离开原场景**：更新 `campaign_character_instances.current_spatial_scene_id = NULL`，位置历史中旧记录的 `story_time_left` 设为离开时间。
2. **在途状态**：角色不显示在任何场景，轨迹矩阵中对应时间段留白。
3. **到达目标场景**：更新 `current_spatial_scene_id = 目标场景`，个人剧情时间 = 到达时间，位置历史插入新记录（`story_time_entered = 到达时间`）。
4. **广播**：通过 Socket.IO 推送 `position_changed` 事件，所有客户端实时更新界面。

#### 4.7.7 技能同步提示组件

**触发场景**：
1. **检定时检测到跨团技能成长**：玩家发起技能检定（如 `ra 侦查`）时，系统对比 Template 与当前 Instance 的技能值，若 Template 更高，则弹出确认框。
2. **进入房间时检测到跨团技能成长**：玩家进入房间时，后台检测到该角色卡在其他团中有技能成长，顶部显示可关闭横幅。

**弹窗样式**：

```
┌─────────────────────────────────────────────────┐
│ 🔄 检测到技能成长                                │
├─────────────────────────────────────────────────┤
│ 你在其他团中的「侦查」技能已提升至 55。          │
│ 当前团的技能值为 50。是否立即同步？              │
│                                                 │
│ [暂不同步] [立即同步]                            │
└─────────────────────────────────────────────────┘
```

- 点击「立即同步」：Instance 技能值更新为 Template 值，弹窗关闭，检定继续使用新值。
- 点击「暂不同步」：保留 Instance 旧值，本次团内不再提示该技能的同步，但 GM 可手动触发。

**顶部横幅样式**：

```
┌──────────────────────────────────────────────────────────────────┐
│ ℹ️ 你的角色卡在其他团中有技能成长（侦查 50→55，图书馆 40→45） [同步] [忽略] ✕ │
└──────────────────────────────────────────────────────────────────┘
```

- 背景色：`--color-info-bg`，文字色：`--color-info`。
- 点击「同步」：批量同步所有有成长的技能，横幅消失。
- 点击「忽略」：关闭横幅，本次登录会话内不再显示。
- 点击「✕」：仅临时关闭横幅，刷新页面或重新进入房间后可再次显示。

**交互规则**：
- 若技能值差距 ≥5 点，不弹窗，直接强制同步并显示轻提示："技能「侦查」已自动同步至 55"。

#### 4.7.8 轨迹矩阵（会员功能，需开团时启用）

**界面元素**：
- 横向滚动表格：
  - 纵轴（行）：时间切片固定为每 30 分钟。
  - 横轴（列）：剧情场列表（按创建顺序排列）。
- 单元格内容：
  - 灰色单元格：已发生的时间点，显示角色头像。3 个及以下平铺展示，超过 3 个折叠为“+N”。
  - 红色竖线：标记当前全局剧情时间所在的列。
  - 白色单元格 + 虚线框：未来时间点，显示已批准的预约移动预览。
- 右键菜单：移动此角色到此场 / 查看角色状态快照。

**交互规则**：
- 入口：GM 控制台 → "轨迹矩阵"标签页（仅当团创建时启用此模块才显示）。
- 点击单元格 → 弹出该时刻该场的角色状态快照（角色卡摘要）。
- 右键单元格 → 弹出菜单，可触发强制移动或查看快照。
- 支持选择时间范围导出剧情回顾（CSV/JSON）。
- 拖拽预约移动的虚线框可调整到达时间（需重新审批）。
- **只读约束**：GM 不可直接编辑单元格内容。

**数据来源**：
- 时间切片：根据 `campaigns.global_story_time` 和配置的粒度生成。
- 场景列表：从 `scenes` 表中查询当前团的 `type = 'spatial'` 的记录。
- 历史位置：从 `position_history` 表中查询，按 `story_time_entered` 和 `story_time_left` 确定每个角色在特定时间切片的位置。
- 预约移动预览：从 `scheduled_moves` 表中查询 `status = 'approved'` 且 `execute_at_story > 当前时间` 的记录。

##### 移动端适配（时间轴视图）

**默认视图**：垂直时间轴，按时间倒序排列，每条节点显示：
- 时间（如"第1日 15:30"）
- 该时刻发生的场景切换事件摘要（如"张三 进入 图书馆"）
- 可点击展开查看该时刻所有场景的角色位置快照（卡片列表）

**场景筛选**：顶部下拉选择特定场景，时间轴只显示该场景的角色位置变化。

**GM 操作**：长按时间节点弹出动作菜单（强制移动、查看快照）。

> 技术实现：使用虚拟滚动列表渲染时间轴，快照数据按需加载。

#### 4.7.9 场景连通配置（高阶 GM 功能，会员专享）

**移动端**：仅支持只读查看路径列表，编辑提示"请在电脑上操作"。

**界面元素**：
- 标题："场景连通路径配置"
- 按钮：【导入】【导出】【+ 添加连通】

- 操作按钮：【编辑】【删除】（每行）

**交互规则**：

- 点击【+ 添加连通】：弹出表单，选择起点、终点，填写各交通方式耗时（分钟），支持设为双向。

- 【导入/导出】：支持上传/下载 JSON 配置文件，便于复用。

**数据来源**：
- 连通列表：从 `scene_connections` 表中查询 `campaign_id = 当前团` 的记录。
- 起点/终点下拉选项：从 `scenes` 表中查询当前团的 `type = 'spatial'` 的记录。
- 默认耗时：若某交通方式不可用，设为 `null`。

| 场景 | 显示规则 |
|---|---|
| 在跑团房间内 | 显示房间底部快捷栏（`[🎲] [角色卡] [指令] [更多]`），隐藏全局底部导航 |
| 在创作者后台/讨论/招募/探索/团途页面 | 显示全局底部导航，隐藏房间底部快捷栏 |
| 房间返回非房间页 | 底栏在路由切换完成后替换，不做并存显示 |

### 5.13 结束团与跑团反馈触发

#### 5.13.1 结束团的操作

**入口**：
- 「房间」标签 -> 进行中列表 -> 房间卡片右侧「...」菜单 -> 「结束团」
- GM 导演台 -> 「设置」面板 -> 「结束团」

**二次确认弹窗**：

```
┌── 结束团 ──────────────────────────────┐
│                                         │
│  确定要结束《{团名}》吗？                │
│                                         │
│  结束后：                               │
│  · 所有成员将收到跑团反馈邀请            │
│  · 房间变为只读，不可再发言              │
│  · 可在「已结束」列表中查看和导出日志     │
│                                         │
│  ⚠️ 此操作不可撤销                       │
│                                         │
│  [取消]              [确认结束团]        │
└─────────────────────────────────────────┘
```

**结束前检查**：如果团内仍有活跃的私密场（有参与者未退出），GM 点击结束时额外提示「仍有 N 个活跃的私密场，结束后将自动归档」，不阻止操作。

**确认后事务**：

1. 将 `campaign.status` 改为 `ended`
2. 取消本团所有未执行的预约移动（`status = 'pending'` 或 `'approved'`）
3. 将所有剧情场和私密场标记为 `archived`
4. 向所有参与者（状态为 `active` 或 `left`，不含 OB）推送通知：「《{团名}》已结束，点击留下你的跑团反馈」
5. 对当前在线的参与者，通过 WebSocket 弹出 Stars and Wishes 反馈框

#### 5.13.2 Stars and Wishes 反馈弹窗

**触发条件**：GM 结束团后即时触发，接收者为团内所有状态为 `active` 或 `left` 的参与者（含 GM 本人），不含 OB。

**弹窗设计**：

```
┌── 跑团反馈：《{团名}》───────────────────┐
│                                          │
│  这个团结束了！想对 GM 和队友说点什么吗？  │
│                                          │
│  ⭐ Star（星星）                          │
│  这次跑团中让你印象深刻的瞬间？           │
│  ┌──────────────────────────────────┐   │
│  │                                  │   │
│  └──────────────────────────────────┘   │
│  （选填，500 字以内）                    │
│                                          │
│  💫 Wish（愿望）                         │
│  下次跑团你希望看到什么？                │
│  ┌──────────────────────────────────┐   │
│  │                                  │   │
│  └──────────────────────────────────┘   │
│  （选填，500 字以内）                    │
│                                          │
│  [跳过]                      [提交]      │
└──────────────────────────────────────────┘
```

**用户操作**：

| 操作 | 行为 |
|------|------|
| 填写并提交 | 反馈写入 `reviews` 表（`review_type='campaign'`，`feedback_type='star'/'wish'`） |
| 点击「跳过」 | 不提交，关闭弹窗。后续可在团途页面补填 |
| 关闭弹窗（点 ✕） | 同上 |

**反馈提交后**：

| 规则 | 说明 |
|------|------|
| 可见范围 | 默认仅 GM 可见（`visibility = gm_only`），GM 可在团设置中切换为全团可见 |
| 修改 | 允许随时修改，显示「已编辑」标记 |
| 删除 | 允许随时删除 |
| 用途 | 不公开、不参与排序、不计算信誉分 |

**补填入口**：
- 站内通知：「《{团名}》已结束，点击留下你的跑团反馈」-> 点击跳转反馈弹窗
- 团途 -> 成长履迹 -> 已完成的跑团记录 -> 「补填反馈」

#### 5.13.3 GM 查看反馈与未填名单

**入口**：GM 导演台 -> 「记录」面板 -> 「跑团反馈」

**已提交反馈列表**：

| 列 | 内容 |
|------|------|
| 参与者 | 昵称 + 头像 |
| Star | 反馈内容摘要（前 50 字） |
| Wish | 反馈内容摘要（前 50 字） |
| 提交时间 | 时间戳 |
| 操作 | 查看完整反馈 |

**未提交反馈名单**：

已提交列表下方展示「待反馈」区域：

| 列 | 内容 |
|------|------|
| 参与者 | 昵称 + 头像 |
| 状态 | 「未提交」 |

GM 可看到哪些参与者尚未提交反馈，用于温和提醒（如私信或群内 @），平台不自动催促。

#### 5.13.4 团途页面的反馈入口

用户在团途 -> 成长履迹中，可看到自己参与过的已结束团列表。每个已结束团卡片下方有「查看反馈 / 补填反馈」按钮：

- 已提交反馈：显示已提交的 Star/Wish 内容，可编辑或删除
- 未提交反馈：显示反馈弹窗，可补填
