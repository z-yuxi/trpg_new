## 一、背景与问题

### 1.1 当前问题

此前采用**全量块级编辑**方案，将所有内容（叙事文本、NPC、道具、场景等）统一拆分为独立块对象，导致两类成本同时升高：

| 问题类型 | 具体表现 |
|---------|---------|
| **创作成本高** | 创作者需频繁处理字段与结构，写作被工具流程打断，产生畏惧心理 |
| **研发维护重** | 块增删改查、多端同步、解析链路复杂，易出现一致性问题和 bug |

### 1.2 核心诉求

必须同时保留两个能力，不可偏废：

1. **创作者**：需要流畅、简单的长篇内容写作体验，接近普通文档编辑
2. **KP（主持人）**：在跑团房间内必须能快速调用 NPC / 道具 / 场景等结构化内容

## 二、目标与边界

### 2.1 设计目标

| 目标 | 说明 |
|------|------|
| 降低创作门槛 | 90% 内容为普通富文本，无需学习块操作 |
| 保留调用能力 | 通过轻量 Mention 标记实现结构化内容调用 |
| 控制研发成本 | 基于成熟开源编辑器（TipTap），避免自研富文本引擎 |
| 支持跨端编辑 | 电脑编辑、手机接续，无需实时协同 |

### 2.2 明确非目标

以下能力**不在首版建设范围**：

- 多人实时协同编辑
- 完整音乐系统与开放音效市场
- 复杂混音功能
- 网文专属功能（小黑屋、拼字、稿费统计等）

## 三、核心方案

### 3.1 总体架构：富文本 + 轻量 Mention

```
┌─────────────────────────────────────────────────────────────┐
│                      应用层（自研）                           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │  章节管理    │  │  实体库      │  │  规则绑定与覆盖      │  │
│  │  (分卷/排序) │  │  (NPC/场景/  │  │  (rule_template_id  │  │
│  │              │  │   线索/检定) │  │   + override_config)│  │
│  └──────┬──────┘  └──────┬──────┘  └─────────────────────┘  │
│         │                │                                    │
│  ┌──────┴────────────────┴──────────────────────────────┐   │
│  │              富文本编辑器（TipTap 2）                   │   │
│  │  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐  │   │
│  │  │ text    │  │ heading │  │ mention │  │ list    │  │   │
│  │  │ (普通文本)│  │ (标题)   │  │ (@引用)  │  │ (列表)   │  │   │
│  │  └─────────┘  └─────────┘  └─────────┘  └─────────┘  │   │
│  └────────────────────────────────────────────────────────┘   │
│         │                                                     │
│  ┌──────┴──────────────────────────────────────────────┐     │
│  │              数据层（自研）                           │     │
│  │  文档 JSON + mention 索引数组 + 版本号 + 时间戳        │     │
│  └──────────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 编辑体验

**普通叙事内容（90% 场景）**：
- 连续富文本编辑，支持 Markdown 快捷输入
- 加粗、倾斜、标题层级、列表等基础格式
- 与普通文档/笔记工具无差异的写作体验

**结构化内容引用（10% 场景）**：
- 输入 `@` 触发选择面板（桌面端）
- 或点击工具栏"插入引用"按钮（移动端）
- 选择实体类型（场景 / NPC / 线索 / 检定 / 道具）
- 从实体库中选择目标，插入 Mention 标记

### 3.3 Mention 标记规范

Mention 只承载**最小必要结构信息**：

```json
{
  "type": "mention",
  "attrs": {
    "entityType": "npc",      // 实体类型：scene | npc | clue | check | item
    "entityId": "npc_001",    // 实体唯一标识
    "label": "老罗",           // 显示文本
    "moduleId": "mod_xxx"     // 所属模组（跨模组引用时必填）
  }
}
```

**渲染效果**：
```
"守夜人 @老罗 正在壁炉旁低声祷告。"
      ↑ 可点击，悬停显示摘要，点击打开实体详情卡
```

### 3.4 KP 调用链路

```
跑团房间消息 / 编辑器预览
    │
    ▼
点击 Mention 标记
    │
    ▼
打开实体详情浮层 / 侧边面板
    │
    ▼
显示完整属性、技能、描述，支持直接调用（如发起检定）
```

### 3.5 实体维护方式

- **右侧实体面板**：独立维护 NPC、场景、线索、检定、道具等实体
- **与正文分离**：实体字段（属性、技能、图片等）不在正文中编辑
- **双向关联**：实体面板显示"被引用次数"和"引用位置"，点击可跳转

|---|---------|---------|---------|---------|

| 4 | **发布与公示期** | 模组发布前进入 7 天公示期，社区可提出版权异议 | ① 提交发布后进入「公示中」状态，持续 7 天；② 公示期间展示摘要、作者信息、规则模板来源；③ 任何用户可提交异议 | 模组表含 status 枚举 + `public_notice_end_at` 时间字段 |
| 5 | **导入功能（Word/TXT + AI 辅助）** | 支持将已有模组文档导入平台，AI 辅助识别结构化实体 | ① 支持 .docx 和 .txt 上传；② AI 自动识别场景/NPC/线索/事件段落；③ 识别结果可人工审核修正；④ 确认后生成实体并回填 Mention | AI 导入通过 Redis 异步队列处理；导入任务表预留 `ai_model_version`、`parse_confidence` |

#### 导入功能的增强：实体批量提取与关联

##### 批量提取流程

用户上传模组文档后，AI 在识别结构化实体的同时，额外执行以下步骤：

1. **实体列表预览**：AI 识别完成后，先展示「疑似实体列表」给用户审核，而非直接写入文档 JSON。列表按实体类型分组（NPC / 场景 / 线索 / 道具），每行显示实体名称、AI 提取的属性摘要、置信度（高/中/低）。
2. **逐条确认与修正**：用户可逐条确认、修改或删除。对于置信度「低」的实体，系统高亮提醒用户重点审核。
3. **一键导入实体库**：用户确认后，所有实体批量写入模组的实体库，同时在文档正文中自动回填 Mention 标记。

##### 关联关系提取

AI 在识别实体的同时，尝试提取实体之间的关联关系：

| 关联类型 | 示例 | 存储位置 |
|---------|------|---------|
| NPC 出现在场景 | 「老罗在丰庄外街巡逻」→ 关联 NPC「老罗」与场景「丰庄外街」 | 实体的 `referenced_positions` 字段 |
| 线索指向 NPC | 「纸条上写着老罗的名字」→ 关联线索「纸条」与 NPC「老罗」 | 线索实体的 `related_npc_ids` 字段 |
| NPC 之间的关系 | 「老罗是酒馆老板的弟弟」→ 关联 NPC「老罗」与 NPC「酒馆老板」 | NPC 实体的 `related_npc_ids` 字段 |

关联关系在实体库中可视化展示（如 NPC 详情页显示「关联场景」「关联线索」「关联 NPC」），方便 GM 快速理解模组的角色关系网。

##### 验收标准

- 实体批量提取的准确率 ≥ 70%（用户确认前）
- 关联关系提取的准确率 ≥ 50%（关联关系比实体识别更难，较低准确率可接受）
- 用户从上传文档到完成实体导入的总操作时间 ≤ 5 分钟（10 万字以内的模组）
| 6 | **PDF 导出** | 支持导出模组为 PDF，分基础版（免费）和美化版（付费/会员） | ① 基础版导出功能性文档；② 美化版支持主题模板、图文混排；③ 支持模板市场 | PDF 采用 Puppeteer 渲染 HTML 转 PDF；模板市场预留 `marketplace_id` |
| 7 | **章节/分卷管理** | 模组章节的管理、排序、增删 | ① 支持多级分卷；② 章节可拖拽排序；③ 章节标题支持 H1/H2/H3 | 章节数据独立表，与文档 JSON 通过 `chapterId` 关联 |
| 8 | **实体库管理** | 统一管理模组内的 NPC、场景、线索、检定、道具 | ① 支持实体的增删改查；② 实体含自定义属性/描述；③ 实体可被多次 Mention 引用 | 各实体类型独立表，统一接口规范 |
| 9 | **模组预览（玩家视角）** | 编辑器内一键切换玩家视角，验证 Mention 渲染和隐藏内容 | ① 隐藏 KP 专属备注；② Mention 正常渲染为可点击标记；③ 显示玩家须知内容 | 预览模式通过权限标记过滤内容 |
| 10 | **版本快照** | 每次保存自动生成历史版本，支持回滚 | ① 保留最近 20 个版本；② 可查看历史版本差异；③ 支持一键回滚到指定版本 | 版本表存储完整文档 JSON + 时间戳 + 操作人 |
| 11 | **移动端降级** | 移动端仅保留核心编辑能力 | ① 可编辑元信息（标题/描述/标签）；② 可编辑纯文本段落与标题；③ Mention 实体只读，不开放增删改；④ 图片/音频仅查看；⑤ 保存后推送给桌面端 | 资源级频道 `/modules/{id}/changes` 推送变更通知 |

## 五、白噪音策略

### 5.1 结论

**白噪音是比背景音乐更适合首版的氛围方案。**

原因：
1. **不抢叙事**：白噪音不携带强旋律与情感指向，不会压过文字想象
2. **低门槛**：GM 无需选曲与试听匹配，按场景一键切换
3. **低风险**：可使用自制或免版权环境音，规避音乐版权链路
4. **可复用**：编辑器与房间共享同一套音频能力层

### 5.2 功能定位

白噪音不是音乐系统，而是**氛围开关**：
- **编辑器侧**：辅助创作专注
- **房间侧**：辅助沉浸叙事

### 5.3 推荐关键词（首批 8 类）

| 关键词 | 英文标识 | 适用场景 |
|--------|---------|---------|
| 雨 | rain | 雨夜、潮湿、压抑 |
| 风 | wind | 荒野、高空、寒冷 |
| 火 | fire | 营地、壁炉、温暖 |
| 洞 | cave | 地下、封闭、神秘 |
| 夜 | night | 深夜、寂静、不安 |
| 城 | city | 都市、繁华、喧嚣 |
| 海 | sea | 海岸、航行、广阔 |
| 机 | engine | 机械、工业、蒸汽朋克 |

### 5.4 数据模型

```typescript
type AmbienceKey = 'rain' | 'wind' | 'fire' | 'cave' | 'night' | 'city' | 'sea' | 'engine' | null;

interface SceneAmbienceConfig {
  ambience: AmbienceKey;
  volume?: number;      // 0~1，默认 0.18
  enabled?: boolean;    // 默认 true
}
```

### 5.5 接口建议

```http
GET  /scenes/:sceneId/ambience
PUT  /scenes/:sceneId/ambience
```

**权限规则**：
- GM 可配置是否广播给全体玩家
- 玩家可本地单独静音或调整音量
- 房间复用播放器能力层，但状态与权限单独管理

## 七、前端实现建议

### 7.1 技术选型

| 层级 | 选型 | 说明 |
|------|------|------|
| 编辑器底座 | **TipTap 2** (ProseMirror) | 成熟稳定，Mention 扩展完善 |
| UI 框架 | React / Vue（团队现有栈） | 保持一致性 |
| 状态管理 | Zustand / Pinia | 轻量，适合编辑器状态 |
| 本地缓存 | IndexedDB | 离线编辑、版本快照 |

```typescript
        onUpdate: (props) => updateMentionList(props),
        onExit: () => destroyMentionList(),
      }),
    },
  }),
  // 自定义 Mention 渲染节点
  MentionNode.extend({
    renderHTML({ node }) {
      return [
        'span',
        {
          'data-entity-type': node.attrs.entityType,
          'data-entity-id': node.attrs.entityId,
          class: 'mention-tag mention-tag--' + node.attrs.entityType,
        },
        '@' + node.attrs.label,
      ];
    },
  }),
];
```

### 7.3 移动端适配

| 场景 | 桌面端 | 移动端 |
|------|--------|--------|
| Mention 插入 | 输入 `@` 触发浮层 | 工具栏"插入引用"按钮 → 实体列表页 |

### 7.4 白噪音播放器

**资源规范**：
- 放置路径：`/public/audio/ambience/`
- 单文件时长：30-120 秒（循环播放）
- 编码：MP3，128kbps
- 统一响度：-20dB，避免首次播放突兀

**播放器能力层**：

```typescript
interface AmbiencePlayer {
  play(key: AmbienceKey): void;           // 播放指定白噪音
  stop(): void;                           // 停止播放
  setVolume(value: number): void;         // 设置音量 0-1
  fadeTo(value: number, ms: number): void; // 平滑过渡音量
  mute(): void;                           // 静音
  unmute(): void;                         // 取消静音
  isPlaying(): boolean;                   // 是否正在播放
  currentKey(): AmbienceKey | null;       // 当前播放的 key
}
```

**关键交互**：
1. 进入场景后按配置自动启用，默认音量 15%-20%
2. 任何端都可一键静音与调整音量
3. 切场景时：旧环境淡出（500ms）→ 新环境淡入（500ms）

## 八、跨端同步机制

### 8.1 设计原则

- **不需要实时协同**：模组创作为异步场景，无需 CRDT/OT
- **Last-Write-Wins**：单人跨设备场景，后写覆盖即可
- **版本号驱动**：通过版本号判断数据新鲜度

### 8.2 同步流程

```
┌─────────────┐     自动保存/手动保存      ┌─────────────┐
│   电脑端     │ ───────────────────────→ │   服务端      │
│  (编辑器)    │   POST /modules/{id}/save │  (模组数据)   │
└─────────────┘                          └──────┬──────┘
                                                │
┌─────────────┐     打开时检查版本              │
│   手机端     │ ←─────────────────────────────┘
│  (编辑器)    │   GET /modules/{id}/status
└─────────────┘
```

### 8.3 保存接口

```http
POST /api/modules/{id}/save
Content-Type: application/json

{
  "document": { /* TipTap JSON */ },
  "mentions": [
    { "entityType": "npc", "entityId": "npc_001", "positions": [...] }
  ],
  "base_version": 41,           // 客户端已知版本
  "device_id": "device_abc",    // 设备标识
  "device_type": "desktop",     // desktop | mobile
  "save_type": "auto"           // auto | force
}
```

**响应**：
```json
{
  "version": 42,
  "saved_at": "2026-04-28T08:54:00Z",
  "conflict": false,            // 如版本冲突返回 true
  "snapshot_id": "snap_001"     // 版本快照 ID
}
```

### 8.4 状态检查接口

```http
GET /api/modules/{id}/status
```

**响应**：
```json
{
  "module_id": "mod_xxx",
  "version": 42,
  "last_modified": "2026-04-28T08:54:00Z",
  "last_device": "device_abc",
  "last_device_type": "desktop"
}
```

### 8.5 打开模组时的同步逻辑

```
1. 读取本地 IndexedDB 缓存
2. 调用 GET /modules/{id}/status 获取服务端版本
3. 若服务端 version > 本地 version：
   → 拉取完整数据覆盖本地
4. 若本地 version > 服务端 version（离线编辑后）：
   → 先上传本地数据 → 再确认同步成功
5. 若版本相同：
   → 使用本地缓存，无需请求
```

### 8.6 离线编辑支持

```
用户编辑
  ↓
本地状态更新（即时响应，无延迟）
  ↓
写入 IndexedDB（本地持久化）
  ↓
网络可用？
  ├─ 是 → 防抖计时器（3s/5s）→ 自动保存到服务端
  └─ 否 → 标记为"待同步"，恢复网络后自动上传
```

### 8.7 实施约束补充（迁移吸收）

为避免弱网与多端切换导致的重复写入和误判，补充以下实现约束：

1. 保存请求增加 `op_id` 字段，服务端按 `op_id` 做幂等去重，客户端重试同一保存任务时必须复用同一 `op_id`。
2. 资源级订阅频道按资源粒度划分：
   - 模组变更频道：`/modules/{module_id}/changes`
   - 规则包变更频道（预留）：`/rulesets/{ruleset_id}/changes`
3. 桌面端收到移动端新版本时，先显示非阻断 Toast，提供“刷新查看/稍后处理”；若用户继续编辑，以后续保存时的版本冲突响应为准，不强制中断输入。
