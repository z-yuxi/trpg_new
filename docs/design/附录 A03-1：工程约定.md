## 1. 总则

所有业务代码的实现，在满足产品功能需求的前提下，**必须**优先满足本文档定义的非功能性需求。本文档的优先级高于“能用就行”的实现习惯。

## 2. 数据库与并发控制

### 2.1 状态流转原子性
任何涉及状态转换的操作（如申请审批、订单支付回调），**严禁**使用“先查后改”的模式。必须使用数据库的原子更新机制来防止并发冲突。

- **✅ 强制要求**：使用带有状态条件的 `UPDATE` 语句或 ORM 的原子操作（如 `updateMany`）。
- **❌ 禁止行为**：
```typescript
// 存在竞态条件，禁止使用
const order = await db.order.findById(orderId);
if (order.status === 'pending') {
  await db.order.update(orderId, { status: 'paid' });
}
2.2 关键业务查询索引基线
对于已在产品文档中明确的查询场景，必须在数据库 Schema 中建立对应的索引。在实现伪代码时，必须用注释指明所依赖的索引。

业务查询场景	涉及核心表	强制索引要求
查询某团内所有待审批的预约移动	scheduled_moves	(campaign_id, status, execute_at_story)
查询用户参与中的活跃房间	campaign_character_instances	(user_id, status, left_at)
查询招募板公开的 GM 招募帖	recruitment_posts	(status, type, created_at DESC)
实现示例:

javascript
// INDEX: (campaign_id, status, execute_at_story)
// 此注释提示开发者/DB迁移必须确保此索引存在
const moves = await db.scheduled_moves.findMany({
  where: { campaignId, status: 'approved', executeAtStory: { lte: newTime } },
  orderBy: { executeAtStory: 'asc' },
});
3. 性能基线
所有接口在常规压力下，应满足以下响应时间标准。

接口类型	P95 延迟	说明
普通 CRUD 接口	< 100ms	如创建角色卡、修改设置
列表查询接口	< 200ms	如招募板列表、探索页
复杂规则引擎接口	< 500ms	如一次掷骰检定
AI 同步任务	< 3s	如智能校对
优化路径：当性能不满足基线时，应依次考虑：优化查询/添加索引 -> 本地缓存 -> 引入Redis。

4. 错误处理与降级
4.1 错误响应结构
所有 API 错误必须返回统一的结构，前端必须基于 error_code 进行逻辑处理，禁止根据 message 做业务判断。

json
{
  "success": false,
  "error_code": "MOVE_CONCURRENT_CONFLICT",
  "message": "操作冲突，请稍后重试",
  "details": { "moveId": "xxx" } // 可选，仅用于调试
}
4.2 AI 任务失败原则
配额保障: AI 调用失败、超时 (>30s) 或返回格式错误时，绝对不能消耗用户配额。

局部成功: 对于分片处理的任务（如模组长文档导入），允许部分分片失败。最终应合并成功部分，并明确提示用户哪些内容需要手动处理。
