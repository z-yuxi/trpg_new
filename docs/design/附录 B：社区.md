## 5. 约局（招募）详细流程

### 5.1 成团流程（文字描述）

**GM视角**：  
发布招募 → 收到申请 → 查看申请者资料（含角色卡） → 沟通确认 → 人齐后点击【成团】 → 生成团（Campaign）

**玩家视角**：  
浏览帖子 → 申请加入（选择已有角色卡或新建） → 等待 GM 确认 → 收到成团通知 → 获取团信息 → 按时进团跑团

### 5.2 技术实现
- 招募列表/筛选：`HTTP GET`，分页 + 筛选  
- 发布/申请/状态变更：`HTTP POST/PUT`  
- 站内沟通与通知：`Socket.IO`（轻量使用）  
- 成团通知：`Socket.IO` 推送 + 站内信  
- 团入口：我的团 → 我的房间  
- **无公开房间大厅**，所有房间均通过招募产生

## 6. 成团触发规则与增强机制

### 6.1 按钮启用条件（GM 视角）
1. 当前招募帖状态 = `open`  
2. 至少有 **1 个** 申请状态为 `approved`（已通过）  
3. 招募帖 `campaign_id` 为空  

### 6.2 成团弹窗交互

```
┌─────────────────────────────────────────────────┐
│ 确认成团 - 《常暗之厢》                           │
├─────────────────────────────────────────────────┤
│ 已通过玩家（3人）：                              │
│ ☑ 张三（侦探） ☑ 李四（记者） ☑ 王五（医生）    │
│                                                  │
│ 模组状态：                                       │
│ ○ 使用已选定模组《常暗之厢》                     │
│ ○ 从资产库选择其他模组 [下拉▼]                  │
│ ○ 创建空白模组（即兴团）                         │
│                                                  │
│ [取消]                         [确认成团]        │
└─────────────────────────────────────────────────┘
```
- 默认勾选所有已通过玩家（GM 可取消）  
- 若发帖时模组状态为“待定”，必须选择一个选项才能确认  

### 6.3 后端事务边界（伪代码示例）

```typescript
async function finalizeRecruitment(postId, selectedPlayerIds, moduleChoice) {
  const tx = await db.beginTransaction();
  try {
    const post = await tx.query(`SELECT * FROM recruitment_posts WHERE id = ? FOR UPDATE`, [postId]);
    if (post.status !== 'open') throw new Error('RECRUITMENT_CLOSED');
    
    const campaignId = generateUUID();
    await tx.query(`INSERT INTO campaigns (id, name, ruleset_id, module_id, ...) VALUES (...)`, [campaignId, ...]);
    
    for (const playerId of selectedPlayerIds) {
      await addPlayerToCampaign(tx, campaignId, playerId);
    }
    
    await tx.query(`UPDATE recruitment_posts SET status = 'grouped', campaign_id = ? WHERE id = ?`, [campaignId, postId]);
    await sendNotifications(selectedPlayerIds, campaignId);
    
    await tx.commit();
    return { campaignId, success: true };
  } catch (error) {
    await tx.rollback();
    throw error;
  }
}
```

**失败处理**：事务回滚，帖子保持 `open` 状态，返回明确错误码（如 `PLAYER_ALREADY_IN_OTHER_CAMPAIGN`）。

### 6.4 成团后的异常处理：流团、解散与重开

#### 6.4.1 新增状态 `dissolved`
- 含义：已解散（流团）  
- 触发条件：GM 主动解散 / 成团后 7 天无人进入房间 / 超 50% 成员退出  

#### 6.4.2 状态流转补充
`grouped` → `dissolved`（GM、管理员或系统自动触发）

#### 6.4.3 解散流程（GM 视角）
- 点击【解散团队】→ 二次确认 → 可选填写原因  
- 解散后：`campaign` 状态改为 `dissolved`，房间只读；成员收到通知  
- 原招募帖保留为 `grouped`（历史），但允许“重新开团”  

#### 6.4.4 重新开团规则
- 若原帖关联的 `campaign` 已解散且未超归档期（30 天），GM 可点击【基于此帖重新开团】  
- 系统**复制**原帖生成新帖（新 `post_id`），原帖加标签 `[已流团-重开新帖]` 并链接到新帖  

#### 6.4.5 自动解散条件（可配置）
| 条件 | 阈值 | 动作 |
|------|------|------|
| 成团后无人进入房间 | 7 天 | 自动 `dissolved` 并通知 |
| 成员退出超 50% 且剩余人数 < 2 | 实时 | 自动解散 |
| GM 连续 14 天未登录 | 14 天 | 警告；再 7 天无动作则自动解散 |

### 6.5 候选席与确认入团机制（防“放鸽子”）

#### 6.5.1 新增申请状态（独立于帖子状态）
| 状态 | 含义 |
|------|------|
| `pending` | 申请待审核 |
| `invited` | GM 已通过，等待玩家确认 |
| `confirmed` | 玩家已确认，占用席位 |
| `rejected` | 被拒绝 |
| `waiting` | 候补（席位满时自动进入） |

#### 6.5.2 流程变更
- 玩家申请 → `pending`  
- GM 通过 → `invited`，玩家 24 小时内需点击【确认入团】，变为 `confirmed`  
- 超时未确认 → 自动变为 `rejected`，释放席位  
- 成团时**只统计 `confirmed` 的玩家**  

#### 6.5.3 候补机制
- 席位满（`full`）后新申请自动进入 `waiting` 队列（按申请时间排序）  
- 有人退出或超时未确认 → 席位空出 → 自动将队列第一个 `waiting` 变为 `invited` 并通知  
- 原 `full` 状态若因退出导致剩余席位 > 0，自动回到 `open`  

#### 6.5.4 前端展示
- 招募帖头部：已确认 / 总席位 X/Y，候补人数 N  
- 玩家申请后可见自身状态：`pending` / `已邀请（请确认）` / `已确认` / `候补第N位`  
### 6.5.5 交互状态细则：[申请加入] 按钮与流程

#### 招募帖卡片上的按钮状态

| 状态 | 触发条件 | 按钮文案 | 是否禁用 | 额外视觉 | 点击行为 | 失败兜底 |
|:---|:---|:---|:---|:---|:---|:---|
| `default` | 已登录，非 GM 本人，招募帖 `open`，席位未满，未申请 | 申请加入 | 否 | - | 弹出角色卡选择弹窗，选择后提交申请 | Toast “操作失败，请重试”，按钮恢复可用 |
| `pending` | 已提交申请，GM 未审核 | 已申请 | 是（灰底） | 按钮右侧有时钟图标 | 无 | - |
| `invited` | GM 已通过，等待玩家确认 | 确认入团 (剩余 N 小时) | 否（主按钮蓝底强调） | 倒计时文案实时刷新 | 提交确认入团请求，成功后变为“已加入” | 网络失败自动进入重试队列，仍保留确认资格 |

#### 确认入团弹窗内的状态与反馈

| 状态 | 前端反馈 | 后端动作 |
|:---|:---|:---|

### 6.6 关键操作幂等与弱网重试

#### 6.6.1 幂等键机制
所有非查询写操作（POST/PUT）必须支持幂等键：

| 操作 | 幂等键生成规则 |
|------|----------------|
| 发布招募帖 | 前端生成 `client_post_id` (UUID)，后端唯一约束 |
| 申请加入 | `user_id + post_id + date` |
| 确认入团 | `application_id + timestamp` 哈希 |
| 点赞/收藏 | `user_id + target_id + type` |

后端：首次请求执行并存储结果；重复请求直接返回首次结果。

#### 6.6.2 弱网重试队列（前端 / PWA 必须实现）
- 请求超时（5秒）或网络不可用时，将请求存入 `IndexedDB` 队列（含 `id`, `url`, `method`, `body`, `幂等键`, `重试次数`, `创建时间`）  
- 网络恢复后自动按 FIFO 重试，指数退避（1s, 2s, 4s … 最大 30s），最多 5 次  
- 成功则从队列删除并 toast 提示；失败则标记“需手动重试”，用户可在“待发送”列表手动重试  
- 用户提交时立即提示“已加入发送队列，网络恢复后自动提交”，不丢失内容  

#### 6.6.3 草稿持久化
- 发帖/评论的富文本内容每 5 秒自动保存至本地存储（`localStorage`）  
- 重新进入页面时提示“检测到未发表的草稿，是否恢复？”  
- 草稿保留 7 天，超时清除

## 7. 评论系统设计（TRPG 专业两层模式）

### 7.1 设计选择
采用 **主楼 + 楼中楼 严格两层结构**（贴吧/NGA/纯美苹果园模式），保证招募沟通有序、楼层可追溯、GM 易管理。

### 7.2 核心概念
- **主楼层**：对主题帖的直接回复，按时间正序排列，拥有全局唯一楼层号。1 楼为帖子正文（存储于 `posts` 表）。  
- **楼中楼**：附着在某主楼层下的二级评论，不占楼层号，折叠显示，仅用于补充对话。  

### 7.3 数据规则（统一软删除）
- 主楼层从 **2** 楼开始编号，删除采用**软删除**（`is_deleted=true`），前台显示“[该楼层已删除]”，楼层号保留。  
- **楼中楼也采用软删除**（与主楼层一致），前台显示“[该回复已删除]”，保留占位符。  
- 禁止三级嵌套（应用层校验 `parent_comment_id` 不能指向另一个楼中楼）。  
- 支持 `@提及`，触发站内通知。  

### 7.4 交互规则
| 操作 | 行为 | 前端反馈 |
|------|------|----------|
| 回复主题帖 | 生成新主楼层，楼层号 = 当前最大楼层号 + 1 | 滚动到页面底部，显示新楼层 |
| 回复某楼层 | 在该楼层下方新增楼中楼 | 该楼层的楼中楼区域展开，新评论高亮 1 秒 |
| 展开/折叠楼中楼 | 默认显示最近 3 条，点击“共X条回复”展开全部 | 平滑展开动画 |
| 删除主楼层（楼主/GM/管理员） | 软删除，内容清空，占位显示 | 替换为灰色占位文字 |
| 删除楼中楼（楼主/GM/管理员） | 软删除，占位显示 | 占位文字 |
#### 软删除占位符统一规范

所有软删除操作（主楼层、楼中楼）必须使用以下占位符，禁止使用系统默认文本或自定义样式。

| 被删对象 | 删除者 | 占位文案 | 占位区域样式 | 原楼层号处理 | 其他交互元素 |
|:---|:---|:---|:---|:---|:---|
| 主楼层 | GM / 管理员 | `[该楼层已被管理员删除]` | 灰色背景，高度基准 48px，居中灰字，14px | 保留，仍显示“X楼” | 点赞、回复等按钮全部隐藏 |
| 主楼层 | 楼主本人 | `[该回复已被作者删除]` | 同上 | 保留 | 同上 |
| 楼中楼 | 任意拥有删除权限者 | `[该回复已被删除]` | 原评论位置替换为 40px 高灰色块，内含灰字 | 不涉及 | 不显示任何操作按钮 |

> **实施要求**
> - 占位区域不可点击、不可展开、不可被选中。
> - 占位文本需使用 `--text-muted` 变量着色，确保日/夜间模式一致。
> - 任何人（包括 GM）都无法查看软删除后的原始内容。如需审计，需通过后台日志查询。

### 7.5 GM/楼主管理权限
- 主楼置顶（最多 3 条）  
- 删除主楼/楼中楼（软删除）  
- 批量清空楼中楼  
- 一键关闭评论  
- 查看并处理违规内容  

### 7.6 性能规则
- 主楼层首次加载 20 条，滚动加载（每次 20 条）  
- 楼中楼默认加载最近 3 条，点击展开后每次加载 20 条

## 8. 用户信誉分体系（社区治理核心）

### 8.1 设计目标
通过量化用户行为，自动影响招募排序权重、举报处置等级、发帖频控阈值，抑制恶意用户，激励正面行为。

### 8.2 信誉分构成
初始分：**100**，范围 0～120（超出的部分为奖励缓冲）

| 行为类型 | 分值变化 | 触发条件 |
|----------|----------|----------|
| 完成一次跑团（且双方互评） | +2 | 跑团结束 7 天内双方均完成评价 |
| 获得对方好评（4星及以上） | +1 | 每次评价 |
| 发布招募帖并成功成团 | +3 | 成团瞬间 |
| 高光被点赞 > 10 | +1 | 每 10 赞，上限 +5/帖 |
| 举报被核实有效 | +1 | 每日上限 +5 |
| 申请后未确认（超时） | -2 | 每次 |
| 成团后无故退出（GM 标记） | -5 | 需 GM 提交原因，用户可申诉 |
| 被删除违规评论（管理员） | -3 至 -10 | 根据违规等级 |
| 被禁言 | -15 | 每次禁言处罚 |
| 流团（GM 无故解散） | -10 | GM 主动解散且无合理解释 |

### 8.3 信誉等级与权益
| 信誉分 | 等级 | 影响 |
|--------|------|------|
| ≥ 110 | 极佳 | 发帖频控提升 2 倍，招募排序加权，可申请“优秀 GM”标识 |
| 90～109 | 良好 | 默认权益 |
| 70～89 | 一般 | 发帖需验证码，招募排序降权 20% |
| 50～69 | 较差 | 每日仅能发 1 帖，所有评论需审核 |
| < 50 | 差 | 禁止发帖，所有评论仅自己可见，可申诉恢复 |

### 8.4 信誉分恢复机制
- 每完成一次无违规跑团恢复 1 分（每周上限 5 分）  
- 连续 30 天无负面行为自动增加 2 分（上限回归 100）  
- 运营活动额外加分  

### 8.5 数据存储
信誉分变更写入 `user_credit_log` 表（字段定义见第 17 章数据字典）。

## 9. 自动化举报初筛与分级处罚

### 9.1 举报自动分流规则

| 举报类型 | 机器初筛逻辑 | 动作 |
|----------|--------------|------|
| 违法/色情 | 命中关键词库 + 图片 OCR/哈希比对 | 自动进入 L4（永久封禁）人工复核 |
| 刷屏/广告 | 同一用户短时间内重复相似内容 | 自动删除 + L1 警告 + 信誉分 -5，第二次自动禁言 1 天 |
| 人身攻击 | 命中攻击性关键词 + 被举报次数 > 3 | 进入 L2 待人工复核，临时折叠内容 |
| 骚扰私信 | 私信频率 + 举报数量 | 自动限制对方私信权限 7 天（L2） |

### 9.2 分级处罚自动执行

| 等级 | 典型行为（自动判定） | 自动处置 | 人工复核时限 |
|------|----------------------|----------|--------------|
| L1 轻微 | 重复发同一句话 5 次以上 | 删除重复内容 + 站内警告 + 信誉分 -2 | 24h 内无异议则生效 |
| L2 中度 | 1 小时内被 3 个不同用户举报 | 限制发帖/评论 1 天 + 信誉分 -10 | 12h 内人工确认 |
| L3 严重 | 命中色情/违法关键词 | 立即下架内容 + 限制发帖 7 天 + 信誉分 -30 | 4h 内必须复核 |
| L4 极严重 | 账号被不同用户举报 > 10 次且包含诈骗证据 | 临时冻结账号，等待人工终审 | 24h 内出结果 |

所有自动处置用户均可立即发起申诉，申诉后人工优先处理。

### 9.3 隐形降权（Shadow Ban）
- 用户信誉分 < 60 时自动触发隐形降权：自己能看到内容，其他用户默认折叠或不可见  
- 管理员可手动对某用户开启（需填写原因），持续 7 天

## 10. 招募帖生命周期与状态机（统一版）

### 10.1 帖子状态定义

| 状态 | 含义 | 可见性 | 可申请 | 可评论 |
|------|------|--------|--------|--------|
| `draft` | 草稿 | 仅作者 | 否 | 否 |
| `open` | 招募中 | 全体 | 是 | 是 |
| `full` | 名额暂满 | 全体 | 否（可候补） | 是 |
| `grouped` | 已成团 | 全体 | 否 | 仅历史只读 |
| `dissolved` | 已解散（流团） | 全体 | 否 | 否 |
| `closed` | 手动/过期关闭 | 全体 | 否 | 否 |
| `archived` | 归档（30天后） | 全体 | 否 | 否 |

### 10.2 状态流转规则
1. `draft → open`（发布）  
2. `open → full`（剩余席位 = 0）  
3. `full → open`（退出或扩容导致剩余席位 > 0）  
4. `open/full → grouped`（成团成功）  
5. `open/full → closed`（手动关闭或截止时间到）  
6. `grouped → dissolved`（流团）  
7. `grouped/closed → archived`（超 30 天自动）  

### 10.3 约束
- `grouped` 后不能回退到 `open/full`  
- `campaign_id` 非空时状态必须为 `grouped`  
- 终态（`grouped/dissolved/closed/archived`）不允许新增申请  
- 所有状态变更写入审计日志（操作者、时间、原因、旧值、新值）

## 11. 信息流与排序规则

### 11.1 信息流类型
1. **招募流**：找团/开团（默认优先）  
2. **动态流**：高光片段、战报、规则讨论  
3. **公示流**：模组/规则公示内容  

### 11.2 排序策略

| 流类型 | 默认排序 | 可切换排序 | 说明 |
|--------|----------|------------|------|
| 招募流 | 最新活跃优先 | 最新发布 / 即将截止 / 席位紧张 | “最新活跃”定义为：最后一条非楼主评论的创建时间，若无评论则取最后申请状态变更时间 |
| 动态流 | 时间倒序 | 热度优先 | 热度仅用于浏览，不影响招募流程 |
| 公示流 | 截止时间升序 | 最新发布 | 保证异议窗口可见 |

### 11.3 热度分计算（仅动态流）
```
score = like×3 + comment×2 + collect×4 + share×5 - decay(t)
decay(t) = floor( (当前时间戳 - 发布时间戳) / 86400 ) × 10
```
即每天衰减 10 分，防止旧内容长期占榜。  
命中风控降权的内容可见但不参与热榜。

### 11.4 规则体系筛选逻辑
- 招募流必须支持按 `ruleset_id` 多选筛选，默认“全选”  
- 筛选条件通过 URL query 持久化（如 `?rulesets=coc,dnd`）  
- 移动端 Tab 切换等价于单选一个规则体系，“全部”则显示所有

## 14. 权限与风控规则

### 14.1 频控阈值

| 行为 | 阈值 | 超限处置 |
|------|------|----------|
| 发帖 | 5 次/小时 | 冷却 30 分钟 |
| 主楼层回复 | 20 次/小时 | 冷却 10 分钟 |
| 楼中楼回复 | 40 次/小时 | 冷却 10 分钟 |
| @提及 | 30 次/小时 | 仅自己可见提醒 |
| 举报提交 | 10 次/天 | 超限后仅保留草稿 |

### 14.2 反垃圾策略
- 命中高风险关键词时触发二次确认或验证码  
- 新账号首日限制：只可评论，不可连续发布多帖  
- 外链发布默认折叠，连续外链触发人工复核  

### 14.3 禁言与解禁
- 禁言仅限制“发帖/评论/私信”，不影响查看历史内容  
- 到期自动解禁，重复违规按倍增规则延长时长  
- 管理员手动解禁必须填写原因并入审计日志

## 15. 移动端社区交互规范

### 15.1 布局
- 单栏信息流  
- 评论保持两层结构（主楼+楼中楼）  
- 申请按钮固定底部  

### 15.2 体验约束
- 输入框上浮时不遮挡当前回复上下文  
- 楼中楼默认折叠，展开后支持就地收起  
- 弱网优先保障：发帖 / 申请 / 成团（见 6.6 重试队列）  

### 15.3 可用性指标
- 首屏可交互时间（TTI）≤ 2.5s  
- 评论提交成功率 ≥ 99.5%  
- 成团通知在线延迟 ≤ 3s  

### 15.4 离线草稿与断网重试（见 6.6.2 和 6.6.3）
- 本地草稿自动保存（3 秒间隔，7 天有效期）  
- 断网重试队列（IndexedDB，指数退避）  
- 推送通知可靠性：离线时存入 `offline_notifications` 表，下次打开拉取；关键通知同时走 Socket + DB + Push

## 18. API 接口规范（核心示例）

所有接口前缀：`/api/v1/community`  
认证方式：`Authorization: Bearer {token}`  
幂等键：非幂等写操作必须携带 `idempotent_key`（前端生成 UUID）。

### 18.1 招募帖

请求体：

{

  "content": "string",

  "ruleset_id": "uuid",

## 20. 扩展与可选功能（从历史设计提取）

> 本章节内容来自旧版设计（附录 B02），经筛选后保留**与现有核心设计无冲突**的部分，可作为**可选增强**在后续迭代中实现，或供 GM 按需启用。  
> **标记 🔵 表示建议直接纳入 MVP**；标记 🟡 表示低优先级或 v2.0。

### 20.1 发帖表单扩展字段（🔵 建议纳入）

当前数据字典已包含基础字段。以下字段可在发布招募帖时作为可选补充，存储于 `recruitment_posts` 表的扩展列（或 JSON 字段）。这些字段**不参与全站筛选**（避免筛选器复杂化），但可在帖子详情中展示，帮助玩家了解团风。

| 字段 | 类型 | 可选值 | 说明 |
|------|------|--------|------|
| `difficulty` | 枚举 | `beginner` / `normal` / `hardcore` | 难度（新手友好 / 普通 / 硬核） |
| `play_frequency` | 枚举 | `weekly1` / `weekly2_3` / `flexible` | 开团频率（每周1次 / 每周2-3次 / 人齐后定） |
| `total_duration` | 枚举 | `short` / `medium` / `long` | 总时长（短团<10h / 中团10-30h / 长团>30h） |
| `module_status` | 枚举 | `selected` / `pending` / `improvisation` | 模组状态（已选定 / 待定商议 / 无模组即兴） |
| `allow_spectate` | 布尔 | 默认 `false` | 是否允许观战（若房间支持 OB） |
| `has_secret_ho` | 布尔 | 默认 `false` | 是否包含秘密HO（隐藏线索/角色） |

**发帖表单呈现**：
- 这些字段放置在“通用信息”区，与规则包无关，所有 GM 均可填写。
- 模组状态为“已选定”时，下方展开资产库选择器（从用户已拥有的模组中选择）。

**详情页展示**：
- 在招募卡片中可展示 `allow_spectate` 标识（👁️ 可观战）。
- 详情页展示所有扩展字段的友好标签。

> **注意**：`module_status` 与成团时的模组选择逻辑一致：若发帖时已选定模组，成团时直接使用；若为待定，成团时弹出模态框要求选择；若为即兴，则创建空白团。**此逻辑已在第 6 章成团流程中覆盖**，此处仅明确字段来源。

### 20.2 可观战标识与观看直播（🔵 纳入，需配合房间能力）

**卡片展示**：
- 若 `allow_spectate = true`，在招募卡片上显示 👁️ 图标，鼠标悬浮显示“本团支持观战”。

**列表操作按钮逻辑**（针对已开团的招募帖）：
- 若招募帖状态为 `grouped`（已成团）且 `allow_spectate = true`，且当前用户不是团员：
  - 卡片操作按钮显示 `[观看直播]`，点击进入房间的观战模式（只读视角，不可发言/操作）。
- 若 `allow_spectate = false` 或房间未开启 OB，且当前用户不是团员，按钮显示 `[已满员]`（禁用态）。

> 实现依赖房间模块支持观战模式（附录 C 需补充观战能力）。

### 20.3 邀请入团（GM 主动邀请，🟡 v2.0 可选）

**背景**：当前流程只允许玩家主动申请，GM 审批。为增强 GM 招募效率，可支持 GM 在浏览“玩家求组帖”时主动向玩家发送邀请。

**触发位置**：
- 在招募广场的“玩家求组”类型帖子卡片上，对 GM 显示 `[邀请入团]` 按钮（普通玩家不可见）。

**流程**：
1. GM 点击 `[邀请入团]`，弹出模态框：
   - 标题：“邀请玩家 [玩家昵称] 加入你的游戏”
   - 选择邀请类型：
     - ○ 邀请至现有房间（下拉选择 GM 进行中的房间）
     - ○ 为此玩家新建一个房间（下方显示模组选择器，默认使用玩家期望规则）
2. GM 确认后，系统创建邀请记录（`invitations` 表），状态为 `pending`。
3. 玩家收到站内通知 + Socket 推送：“GM [GM昵称] 邀请你加入《团名》”。
4. 玩家点击“接受”后：
   - 若邀请类型为“现有房间” → 玩家直接加入该 campaign，成为正式成员。
   - 若邀请类型为“新建房间” → 系统创建新 campaign，将 GM 和该玩家加入，并关联此邀请。
5. 玩家拒绝或 48 小时未响应 → 邀请失效。

**与现有申请流程的关系**：
- 邀请入团是**独立于申请流程的快捷通道**，不改变原有的申请→审批机制。
- 被邀请的玩家若已申请该团，则邀请按钮置灰，避免重复。

**数据表新增**（v2.0 时加入）：
```sql
CREATE TABLE invitations (
  id UUID PRIMARY KEY,
  from_gm_id UUID NOT NULL,      -- 邀请人（GM）
  to_player_id UUID NOT NULL,    -- 受邀玩家
  campaign_id UUID,              -- 现有房间（若为新建则为空）
  target_ruleset_id UUID,        -- 期望规则（新建时使用）
  status ENUM('pending','accepted','rejected','expired'),
  expire_at TIMESTAMP,
  created_at TIMESTAMP
);
```
