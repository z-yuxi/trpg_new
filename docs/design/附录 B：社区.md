## 5. 约局（招募）详细流程

### 5.1 成团流程（文字描述）

**GM视角**：  
发布招募 → 收到申请 → 查看申请者资料（含角色卡） → 沟通确认 → 人齐后点击【成团】 → 生成团（Campaign）

**玩家视角**：  
浏览帖子 → 申请加入（选择已有角色卡或新建） → 等待 GM 确认 → 收到成团通知 → 获取团信息 → 按时进团跑团

### 5.2 技术实现
- 招募列表/筛选：`HTTP GET`，分页 + 筛选  
- 发布/申请/状态变更：`HTTP POST/PUT`  
- 站内沟通与通知：`Socket.IO`（轻量使用）  
- 成团通知：`Socket.IO` 推送 + 站内信  
- 团入口：我的团 → 我的房间  
- **无公开房间大厅**，所有房间均通过招募产生

## 6. 成团触发规则与增强机制

### 6.1 按钮启用条件（GM 视角）
1. 当前招募帖状态 = `open`  
2. 至少有 **1 个** 申请状态为 `approved`（已通过）  
3. 招募帖 `campaign_id` 为空  

### 6.2 成团弹窗交互

```
┌─────────────────────────────────────────────────┐
│ 确认成团 - 《常暗之厢》                           │
├─────────────────────────────────────────────────┤
│ 已通过玩家（3人）：                              │
│ ☑ 张三（侦探） ☑ 李四（记者） ☑ 王五（医生）    │
│                                                  │
│ 模组状态：                                       │
│ ○ 使用已选定模组《常暗之厢》                     │
│ ○ 从资产库选择其他模组 [下拉▼]                  │
│ ○ 创建空白模组（即兴团）                         │
│                                                  │
│ [取消]                         [确认成团]        │
└─────────────────────────────────────────────────┘
```
- 默认勾选所有已通过玩家（GM 可取消）  
- 若发帖时模组状态为“待定”，必须选择一个选项才能确认  

### 6.3 后端事务边界（伪代码示例）

```typescript
async function finalizeRecruitment(postId, selectedPlayerIds, moduleChoice) {
  const tx = await db.beginTransaction();
  try {
    const post = await tx.query(`SELECT * FROM recruitment_posts WHERE id = ? FOR UPDATE`, [postId]);
    if (post.status !== 'open') throw new Error('RECRUITMENT_CLOSED');
    
    const campaignId = generateUUID();
    await tx.query(`INSERT INTO campaigns (id, name, ruleset_id, module_id, ...) VALUES (...)`, [campaignId, ...]);
    
    for (const playerId of selectedPlayerIds) {
      await addPlayerToCampaign(tx, campaignId, playerId);
    }
    
    await tx.query(`UPDATE recruitment_posts SET status = 'grouped', campaign_id = ? WHERE id = ?`, [campaignId, postId]);
    await sendNotifications(selectedPlayerIds, campaignId);
    
    await tx.commit();
    return { campaignId, success: true };
  } catch (error) {
    await tx.rollback();
    throw error;
  }
}
```

**失败处理**：事务回滚，帖子保持 `open` 状态，返回明确错误码（如 `PLAYER_ALREADY_IN_OTHER_CAMPAIGN`）。

### 6.4 成团后的异常处理：流团、解散与重开

#### 6.4.1 新增状态 `dissolved`
- 含义：已解散（流团）  
- 触发条件：GM 主动解散 / 成团后 7 天无人进入房间 / 超 50% 成员退出  

#### 6.4.2 状态流转补充
`grouped` → `dissolved`（GM、管理员或系统自动触发）

#### 6.4.3 解散流程（GM 视角）
- 点击【解散团队】→ 二次确认 → 可选填写原因  
- 解散后：`campaign` 状态改为 `dissolved`，房间只读；成员收到通知  
- 原招募帖保留为 `grouped`（历史），但允许“重新开团”  

#### 6.4.4 重新开团规则
- 若原帖关联的 `campaign` 已解散且未超归档期（30 天），GM 可点击【基于此帖重新开团】  
- 系统**复制**原帖生成新帖（新 `post_id`），原帖加标签 `[已流团-重开新帖]` 并链接到新帖  

#### 6.4.5 自动解散条件（可配置）
| 条件 | 阈值 | 动作 |
|------|------|------|
| 成团后无人进入房间 | 7 天 | 自动 `dissolved` 并通知 |
| 成员退出超 50% 且剩余人数 < 2 | 实时 | 自动解散 |
| GM 连续 14 天未登录 | 14 天 | 警告；再 7 天无动作则自动解散 |

### 6.5 候选席与确认入团机制（防“放鸽子”）

#### 6.5.1 新增申请状态（独立于帖子状态）
| 状态 | 含义 |
|------|------|
| `pending` | 申请待审核 |
| `invited` | GM 已通过，等待玩家确认 |
| `confirmed` | 玩家已确认，占用席位 |
| `rejected` | 被拒绝 |
| `waiting` | 候补（席位满时自动进入） |

#### 6.5.2 流程变更
- 玩家申请 → `pending`  
- GM 通过 → `invited`，玩家 24 小时内需点击【确认入团】，变为 `confirmed`  
- 超时未确认 → 自动变为 `rejected`，释放席位  
- 成团时**只统计 `confirmed` 的玩家**  

#### 6.5.3 候补机制
- 席位满（`full`）后新申请自动进入 `waiting` 队列（按申请时间排序）  
- 有人退出或超时未确认 → 席位空出 → 自动将队列第一个 `waiting` 变为 `invited` 并通知  
- 原 `full` 状态若因退出导致剩余席位 > 0，自动回到 `open`  

#### 6.5.4 前端展示
- 招募帖头部：已确认 / 总席位 X/Y，候补人数 N  
- 玩家申请后可见自身状态：`pending` / `已邀请（请确认）` / `已确认` / `候补第N位`  
### 6.5.5 交互状态细则：[申请加入] 按钮与流程

#### 招募帖卡片上的按钮状态

| 状态 | 触发条件 | 按钮文案 | 是否禁用 | 额外视觉 | 点击行为 | 失败兜底 |
|:---|:---|:---|:---|:---|:---|:---|
| `default` | 已登录，非 GM 本人，招募帖 `open`，席位未满，未申请 | 申请加入 | 否 | - | 弹出角色卡选择弹窗，选择后提交申请 | Toast “操作失败，请重试”，按钮恢复可用 |

| `invited` | GM 已通过，等待玩家确认 | 确认入团 (剩余 N 小时) | 否（主按钮蓝底强调） | 倒计时文案实时刷新 | 提交确认入团请求，成功后变为“已加入” | 网络失败自动进入重试队列，仍保留确认资格 |

### 6.6 关键操作幂等与弱网重试

#### 6.6.1 幂等键机制
所有非查询写操作（POST/PUT）必须支持幂等键：

| 操作 | 幂等键生成规则 |
|------|----------------|
| 发布招募帖 | 前端生成 `client_post_id` (UUID)，后端唯一约束 |
| 申请加入 | `user_id + post_id + date` |
| 确认入团 | `application_id + timestamp` 哈希 |
| 点赞/收藏 | `user_id + target_id + type` |

后端：首次请求执行并存储结果；重复请求直接返回首次结果。

#### 6.6.2 弱网重试队列（前端 / PWA 必须实现）
- 请求超时（5秒）或网络不可用时，将请求存入 `IndexedDB` 队列（含 `id`, `url`, `method`, `body`, `幂等键`, `重试次数`, `创建时间`）  
- 网络恢复后自动按 FIFO 重试，指数退避（1s, 2s, 4s … 最大 30s），最多 5 次  
- 成功则从队列删除并 toast 提示；失败则标记“需手动重试”，用户可在“待发送”列表手动重试  
- 用户提交时立即提示“已加入发送队列，网络恢复后自动提交”，不丢失内容  

#### 6.6.3 草稿持久化
- 发帖/评论的富文本内容每 5 秒自动保存至本地存储（`localStorage`）  
- 重新进入页面时提示“检测到未发表的草稿，是否恢复？”  
- 草稿保留 7 天，超时清除

## 7. 评论系统设计（TRPG 专业两层模式）

### 7.1 设计选择
采用 **主楼 + 楼中楼 严格两层结构**（贴吧/NGA/纯美苹果园模式），保证招募沟通有序、楼层可追溯、GM 易管理。

### 7.2 核心概念
- **主楼层**：对主题帖的直接回复，按时间正序排列，拥有全局唯一楼层号。1 楼为帖子正文（存储于 `posts` 表）。  
- **楼中楼**：附着在某主楼层下的二级评论，不占楼层号，折叠显示，仅用于补充对话。  

### 7.3 数据规则（统一软删除）
- 主楼层从 **2** 楼开始编号，删除采用**软删除**（`is_deleted=true`），前台显示“[该楼层已删除]”，楼层号保留。  
- **楼中楼也采用软删除**（与主楼层一致），前台显示“[该回复已删除]”，保留占位符。  
- 禁止三级嵌套（应用层校验 `parent_comment_id` 不能指向另一个楼中楼）。  
- 支持 `@提及`，触发站内通知。  

### 7.4 交互规则
| 操作 | 行为 | 前端反馈 |
|------|------|----------|
| 回复主题帖 | 生成新主楼层，楼层号 = 当前最大楼层号 + 1 | 滚动到页面底部，显示新楼层 |
| 回复某楼层 | 在该楼层下方新增楼中楼 | 该楼层的楼中楼区域展开，新评论高亮 1 秒 |
| 展开/折叠楼中楼 | 默认显示最近 3 条，点击“共X条回复”展开全部 | 平滑展开动画 |
| 删除主楼层（楼主/GM/管理员） | 软删除，内容清空，占位显示 | 替换为灰色占位文字 |
| 删除楼中楼（楼主/GM/管理员） | 软删除，占位显示 | 占位文字 |
#### 软删除占位符统一规范

所有软删除操作（主楼层、楼中楼）必须使用以下占位符，禁止使用系统默认文本或自定义样式。

| 被删对象 | 删除者 | 占位文案 | 占位区域样式 | 原楼层号处理 | 其他交互元素 |
|:---|:---|:---|:---|:---|:---|
| 主楼层 | GM / 管理员 | `[该楼层已被管理员删除]` | 灰色背景，高度基准 48px，居中灰字，14px | 保留，仍显示“X楼” | 点赞、回复等按钮全部隐藏 |
| 主楼层 | 楼主本人 | `[该回复已被作者删除]` | 同上 | 保留 | 同上 |
| 楼中楼 | 任意拥有删除权限者 | `[该回复已被删除]` | 原评论位置替换为 40px 高灰色块，内含灰字 | 不涉及 | 不显示任何操作按钮 |

> **实施要求**
> - 占位区域不可点击、不可展开、不可被选中。
> - 占位文本需使用 `--text-muted` 变量着色，确保日/夜间模式一致。
> - 任何人（包括 GM）都无法查看软删除后的原始内容。如需审计，需通过后台日志查询。

### 7.5 GM/楼主管理权限
- 主楼置顶（最多 3 条）  
- 删除主楼/楼中楼（软删除）  
- 批量清空楼中楼  
- 一键关闭评论  
- 查看并处理违规内容  

### 7.6 性能规则
- 主楼层首次加载 20 条，滚动加载（每次 20 条）  
- 楼中楼默认加载最近 3 条，点击展开后每次加载 20 条

## 8. 表态互动（多表情情绪反馈）

### 8.1 功能定位
「表态互动」是平台预设的轻量级情绪反馈功能。用户对一条帖子（招募帖、讨论帖、公告帖、日志帖等）只需一次点击即可表达态度，无需输入文字。

设计目标：
- 降低互动门槛：让“只看不评”的沉默用户也能参与社区互动
- 快速感知风向：GM 可一眼看懂招募帖的情绪倾向（不满/困惑/认可）
- 辅助社区治理：管理员可通过表情数据提前识别争议帖，在举报之前介入

### 8.2 与其他互动方式的分层关系

| 互动层级 | 用户成本 | 典型行为 | 对应功能 |
|---|---|---|---|
| 零成本互动 | 1 次点击 | 点 👍 点 ❤️ 点 😭 | 表态互动（本章） |
| 轻量互动 | 多次点击 | 对楼层点赞 | `floor_likes` 表（第 7 章） |
| 深度互动 | 需要输入文字 | 评论、申请入团、发招募帖 | 评论系统（第 7 章）、申请系统（第 5-6 章） |

三者互不替代，共同构成完整的社区互动漏斗。

### 8.3 预设表情及语义定义
平台提供以下 6 种预设表情，所有帖子类型统一使用，不可自定义。

| 表情标识 | 图标 | 显示文案 | 语义定义 | 适用场景举例 |
|---|---|---|---|---|
| like | 👍 | 点赞 | 赞同、认可、支持 | 认可招募帖规则、称赞日志帖 |
| love | ❤️ | 爱心 | 喜爱、强烈推荐 | 特别喜欢某篇战报、感动 |
| cry | 😭 | 哭脸 | 遗憾、不满、惋惜 | 错过招募时间、角色死亡、对规则感到不满 |
| laugh | 😂 | 笑哭 | 觉得好笑、有趣氛围 | 搞笑战报片段、轻松讨论 |
| question | ❓ | 问号 | 困惑、不理解、有疑问 | 规则写得不清楚、内容有歧义 |
| angry | 😡 | 愤怒 | 生气、强烈反对 | 对争议性公告表达不满 |

选取原则：
- 覆盖 TRPG 社区最常见的情感表达需求（认可/不满/困惑/娱乐）
- 每种表情有明确、无歧义的语义，避免用户误解
- 数量控制在 6 种，保证选择效率，避免决策疲劳

### 8.4 数据模型

```sql
-- 帖子表态记录表
CREATE TABLE post_reactions (
  id VARCHAR(64) PRIMARY KEY,
  post_id VARCHAR(64) NOT NULL COMMENT '关联的帖子ID（招募帖/讨论帖/公告帖/日志帖/作品帖）',
  user_id VARCHAR(64) NOT NULL COMMENT '表态用户ID',
  reaction_type VARCHAR(32) NOT NULL COMMENT '表情类型：like / love / cry / laugh / question / angry',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_post (post_id, user_id) COMMENT '每个用户对每条帖子只能有一条表态记录',
  INDEX idx_post_reaction (post_id, reaction_type)
);
```

设计说明：
- `UNIQUE KEY uk_user_post (post_id, user_id)` 确保每个用户对每条帖子只能表态一次。
- 用户切换表情时，直接 `UPDATE reaction_type`，不需要先删除再插入。
- 用户取消表态时，`DELETE` 该记录。
- 每个表情的计数通过实时查询 `SELECT COUNT(*) FROM post_reactions WHERE post_id = ? AND reaction_type = ?` 获取，不设冗余计数字段（避免点赞系统的一致性问题）。

### 8.5 交互状态细则

#### 8.5.1 表情面板与按钮状态

| 状态 | 触发条件 | 前端反馈 | 后端动作 | 异常处理 |
|---|---|---|---|---|
| default | 已登录，未表态 | 6 个表情均以灰色轮廓图标显示，无高亮 | 无 | - |
| selected | 已登录，已选择某个表情 | 选中的表情高亮为彩色填充，其余 5 个保持灰色轮廓 | 无（仅查询显示） | - |
| not_login | 未登录 | 表情正常显示，点击任意表情时弹出登录/注册模态框 | 无 | 登录成功后不自动表态，需用户再次点击 |

#### 8.5.2 用户点击表情的完整行为

| 用户操作 | 前端反馈 | 后端动作 | 异常处理 |
|---|---|---|---|
| 点击未选中的表情 | 1. 该表情高亮为彩色填充，数字 +1<br>2. 该表情图标轻微弹跳动画（300ms） | 写入 `post_reactions` 记录 | 网络失败 -> 进入重试队列，前端先乐观更新，失败后回滚 |
| 点击已选中的表情（同一个） | 1. 该表情恢复为灰色轮廓，数字 -1 | 删除该记录 | 同上 |
| 点击另一个表情（已有选中表情） | 1. 旧表情恢复灰色轮廓，数字 -1<br>2. 新表情高亮彩色，数字 +1<br>3. 新表情弹跳动画 | 更新 `reaction_type` | 同上 |
| 快速连续点击多个表情 | 只执行最后一次点击对应的操作 | 以最终状态为准 | 前端防抖 300ms |

#### 8.5.3 表情计数展示规则

| 场景 | 展示规则 |
|---|---|
| 计数 = 0 | 该表情不显示（不出现“0”） |
| 计数 > 0 | 显示图标 + 数字（如 👍 25） |
| 表情排序 | 按计数从高到低排列，计数相同时按 `reaction_type` 固定顺序（`like > love > cry > laugh > question > angry`） |
| 数字更新 | 用户操作后立即乐观更新，不等待服务端确认 |

### 8.6 权限与频控

| 限制项 | 值 | 说明 |
|---|---|---|
| 表态对象 | 所有类型的帖子（招募帖/讨论帖/公告帖/日志帖/作品帖） | 不区分帖子类型 |
| 同一帖子的表态次数 | 每个用户对每条帖子只能有一条记录，切换表情时更新 | 不受理“每日表态上限” |
| 未登录用户 | 可见表情计数，不可表态 | 点击时弹出登录/注册模态框 |
| 帖子关闭/删除后 | 表情面板隐藏，已有的表态记录保留但不展示 | 软删除帖子时不物理删除关联表 |

### 8.7 与其他功能的关系

| 功能 | 关系 | 说明 |
|---|---|---|
| 楼层点赞（`floor_likes`） | 互补，不冲突 | 楼层点赞针对单条评论楼层；表态互动针对整条帖子 |
| 评论系统 | 互补，层级不同 | 评论需要输入文字，表态只需一次点击 |
| 举报系统 | 辅助信号 | 某条帖子 `angry` 表情异常偏高时，管理员可提前介入 |
| 通知系统 | 不生成通知 | 表态互动不计入站内通知，避免通知过载（与楼层点赞规则一致） |

### 8.8 验收标准
- ✅ 所有帖子详情页底部显示 6 种预设表情及各自的计数。
- ✅ 已登录用户点击表情可完成表态/切换/取消，动画流畅。
- ✅ 未登录用户点击表情时弹出登录/注册模态框。
- ✅ 同一用户对同一帖子只能有一条表态记录，切换表情时正确更新。
- ✅ 表情计数实时更新，页面刷新后数据不丢失。
- ✅ 帖子关闭/删除后表情面板不再显示，但历史数据保留。
- ✅ 表情按计数降序排列，0 计数的表情不显示。

## 9. 用户信誉分体系（社区治理核心）

### 9.1 设计目标
通过量化用户行为，自动影响招募排序权重、举报处置等级、发帖频控阈值，抑制恶意用户，激励正面行为。

### 9.2 信誉分构成
初始分：**100**，范围 0～120（超出的部分为奖励缓冲）

| 行为类型 | 分值变化 | 触发条件 |
|----------|----------|----------|
| 完成一次跑团（且双方互评） | +2 | 跑团结束 7 天内双方均完成评价 |
| 获得对方好评（4星及以上） | +1 | 每次评价 |
| 发布招募帖并成功成团 | +3 | 成团瞬间 |
| 高光被点赞 > 10 | +1 | 每 10 赞，上限 +5/帖 |
| 举报被核实有效 | +1 | 每日上限 +5 |
| 申请后未确认（超时） | -2 | 每次 |
| 成团后无故退出（GM 标记） | -5 | 需 GM 提交原因，用户可申诉 |
| 被删除违规评论（管理员） | -3 至 -10 | 根据违规等级 |
| 被禁言 | -15 | 每次禁言处罚 |
| 流团（GM 无故解散） | -10 | GM 主动解散且无合理解释 |

### 9.3 信誉等级与权益
| 信誉分 | 等级 | 影响 |
|--------|------|------|
| ≥ 110 | 极佳 | 发帖频控提升 2 倍，招募排序加权，可申请“优秀 GM”标识 |
| 90～109 | 良好 | 默认权益 |
| 70～89 | 一般 | 发帖需验证码，招募排序降权 20% |
| 50～69 | 较差 | 每日仅能发 1 帖，所有评论需审核 |
| < 50 | 差 | 禁止发帖，所有评论仅自己可见，可申诉恢复 |

### 9.4 信誉分恢复机制
- 每完成一次无违规跑团恢复 1 分（每周上限 5 分）  
- 连续 30 天无负面行为自动增加 2 分（上限回归 100）  
- 运营活动额外加分  

### 9.5 数据存储
信誉分变更写入 `user_credit_log` 表（字段定义见第 18 章数据字典）。

## 10. 自动化举报初筛与分级处罚

### 10.1 举报自动分流规则

| 举报类型 | 机器初筛逻辑 | 动作 |
|----------|--------------|------|
| 违法/色情 | 命中关键词库 + 图片 OCR/哈希比对 | 自动进入 L4（永久封禁）人工复核 |
| 刷屏/广告 | 同一用户短时间内重复相似内容 | 自动删除 + L1 警告 + 信誉分 -5，第二次自动禁言 1 天 |
| 人身攻击 | 命中攻击性关键词 + 被举报次数 > 3 | 进入 L2 待人工复核，临时折叠内容 |
| 骚扰私信 | 私信频率 + 举报数量 | 自动限制对方私信权限 7 天（L2） |

### 10.2 分级处罚自动执行

| 等级 | 典型行为（自动判定） | 自动处置 | 人工复核时限 |
|------|----------------------|----------|--------------|
| L1 轻微 | 重复发同一句话 5 次以上 | 删除重复内容 + 站内警告 + 信誉分 -2 | 24h 内无异议则生效 |
| L2 中度 | 1 小时内被 3 个不同用户举报 | 限制发帖/评论 1 天 + 信誉分 -10 | 12h 内人工确认 |
| L3 严重 | 命中色情/违法关键词 | 立即下架内容 + 限制发帖 7 天 + 信誉分 -30 | 4h 内必须复核 |
| L4 极严重 | 账号被不同用户举报 > 10 次且包含诈骗证据 | 临时冻结账号，等待人工终审 | 24h 内出结果 |

所有自动处置用户均可立即发起申诉，申诉后人工优先处理。

### 10.3 隐形降权（Shadow Ban）
- 用户信誉分 < 60 时自动触发隐形降权：自己能看到内容，其他用户默认折叠或不可见  
- 管理员可手动对某用户开启（需填写原因），持续 7 天

## 11. 招募帖生命周期与状态机（统一版）

### 11.1 帖子状态定义

| 状态 | 含义 | 可见性 | 可申请 | 可评论 |
|------|------|--------|--------|--------|
| `draft` | 草稿 | 仅作者 | 否 | 否 |
| `open` | 招募中 | 全体 | 是 | 是 |
| `full` | 名额暂满 | 全体 | 否（可候补） | 是 |
| `grouped` | 已成团 | 全体 | 否 | 仅历史只读 |
| `dissolved` | 已解散（流团） | 全体 | 否 | 否 |
| `closed` | 手动/过期关闭 | 全体 | 否 | 否 |
| `archived` | 归档（30天后） | 全体 | 否 | 否 |

### 11.2 状态流转规则
1. `draft → open`（发布）  
2. `open → full`（剩余席位 = 0）  
3. `full → open`（退出或扩容导致剩余席位 > 0）  
4. `open/full → grouped`（成团成功）  
5. `open/full → closed`（手动关闭或截止时间到）  
6. `grouped → dissolved`（流团）  
7. `grouped/closed → archived`（超 30 天自动）  

### 11.3 约束
- `grouped` 后不能回退到 `open/full`  
- `campaign_id` 非空时状态必须为 `grouped`  
- 终态（`grouped/dissolved/closed/archived`）不允许新增申请  
- 所有状态变更写入审计日志（操作者、时间、原因、旧值、新值）

## 12. 信息流与排序规则

### 12.1 信息流类型
1. **招募流**：找团/开团（默认优先）  
2. **动态流**：高光片段、战报、规则讨论  
3. **公示流**：模组/规则公示内容  

### 12.2 排序策略

| 流类型 | 默认排序 | 可切换排序 | 说明 |
|--------|----------|------------|------|
| 招募流 | 最新活跃优先 | 最新发布 / 即将截止 / 席位紧张 | “最新活跃”定义为：最后一条非楼主评论的创建时间，若无评论则取最后申请状态变更时间 |
| 动态流 | 时间倒序 | 热度优先 | 热度仅用于浏览，不影响招募流程 |
| 公示流 | 截止时间升序 | 最新发布 | 保证异议窗口可见 |

### 12.3 热度分计算（仅动态流）
```
score = like×3 + comment×2 + collect×4 + share×5 - decay(t)
decay(t) = floor( (当前时间戳 - 发布时间戳) / 86400 ) × 10
```
即每天衰减 10 分，防止旧内容长期占榜。  
命中风控降权的内容可见但不参与热榜。

### 12.4 规则体系筛选逻辑
- 招募流必须支持按 `ruleset_id` 多选筛选，默认“全选”  
- 筛选条件通过 URL query 持久化（如 `?rulesets=coc,dnd`）  
- 移动端 Tab 切换等价于单选一个规则体系，“全部”则显示所有

## 13. 互动通知矩阵

### 13.1 通知渠道
- 站内通知（默认开启）  
- Socket.IO 实时提醒（在线用户）  
- Push/邮件（用户可选）  

### 13.2 核心事件与去重

| 事件 | 触发对象 | 默认渠道 | 去重窗口 |
|------|----------|----------|----------|
| 帖子被评论（主楼层） | 楼主 | 站内 + Socket | 60 秒 |
| 楼中楼被回复 | 被回复用户 | 站内 + Socket | 60 秒 |
| `@提及` | 被 @ 用户 | 站内 + Socket + Push（可关） | 30 秒 |
| 收到入团申请 | GM | 站内 + Socket | 0 秒（即时） |
| 申请被通过/拒绝 | 申请玩家 | 站内 + Socket | 0 秒 |
| 成团成功 | 全体成员 | 站内 + Socket + Push | 0 秒 |
| 举报处理结果 | 举报人 | 站内 + 邮件（可选） | 0 秒 |

- 同类事件在去重窗口内合并为摘要通知  
- 成团类通知为高优先级，不参与合并  
- 通知中心保留最近 90 天记录，支持按类型筛选

## 19. API 接口规范（核心示例）

所有接口前缀：`/api/v1/community`  
认证方式：`Authorization: Bearer {token}`  
幂等键：非幂等写操作必须携带 `idempotent_key`（前端生成 UUID）。

### 19.1 招募帖

#### 发布招募帖
`POST /recruitment`  
请求体：
```json
{
  "title": "string",
  "content": "string",
  "post_type": "gm_recruit|player_seek",
  "ruleset_id": "uuid",
  "module_id": "uuid?",
  "slots_total": 4,
  "time_slots": [{"weekday":1, "start":"20:00", "duration":4}],
  "recruit_expire_at": "2026-05-01T00:00:00Z",
  "idempotent_key": "uuid"
}
```
成功响应 `201`：`{ "post_id": "uuid", "status": "draft" }`

#### 发布帖子（从草稿到 open）
`POST /recruitment/{post_id}/publish` → `200`

#### 获取招募列表
`GET /recruitment/list?rulesets=coc,dnd&status=open&page=1&limit=20`  
支持筛选：`rulesets`, `post_type`, `status`, `time_slot`（如 `2_21:00`）

### 19.2 申请与确认

#### 申请加入
`POST /recruitment/{post_id}/apply`  
请求体：
```json
{
  "character_id": "uuid?",
  "character_card_json": {},
  "idempotent_key": "uuid"
}
```
响应：
```json
{ "application_id": "uuid", "status": "pending", "position": 3 }
```

#### 审批申请（GM）
`PUT /applications/{application_id}/approve` → 状态变为 `invited`

#### 确认入团（玩家）
`POST /applications/{application_id}/confirm` → 状态变为 `confirmed`

### 19.3 评论系统

#### 回复主题帖（生成主楼层）
`POST /posts/{post_id}/replies`  
请求体：`{ "content": "string", "idempotent_key": "uuid" }`  
响应：`{ "reply_id": "uuid", "floor_number": 12, "created_at": "..." }`

#### 回复主楼层（生成楼中楼）
`POST /replies/{parent_floor_id}/comments`  
请求体：`{ "content": "string", "reply_to_user_id": "uuid?", "idempotent_key": "uuid" }`

#### 删除评论（软删除）
`DELETE /comments/{comment_id}`（需权限） → `204`

### 19.4 成团操作

#### GM 成团
`POST /recruitment/{post_id}/finalize`  
请求体：
```json
{
  "selected_player_ids": ["uuid1", "uuid2"],
  "module_choice": {
    "type": "selected|other|blank",
    "module_id": "uuid?"   // 仅 other 时提供
  },
  "idempotent_key": "uuid"
}
```
响应：`{ "campaign_id": "uuid", "success": true }`

### 19.5 关注/私信

#### 关注用户
`POST /users/{user_id}/follow` → `204`

#### 取消关注
`DELETE /users/{user_id}/follow` → `204`

#### 发送私信
`POST /messages`  
请求体：`{ "to_user_id": "uuid", "content": "text", "images": ["url"]?, "idempotent_key": "uuid" }`

### 19.6 评价

#### 提交评价
`POST /campaigns/{campaign_id}/reviews`  
请求体：`{ "target_id": "uuid", "rating": 5, "content": "string", "idempotent_key": "uuid" }`

### 19.7 举报

#### 提交举报
`POST /reports`  
请求体：`{ "target_type": "post|comment|user", "target_id": "uuid", "reason": "string", "idempotent_key": "uuid" }`

### 21.1 发帖表单扩展字段（🔵 建议纳入）

当前数据字典已包含基础字段。以下字段可在发布招募帖时作为可选补充，存储于 `recruitment_posts` 表的扩展列（或 JSON 字段）。这些字段**不参与全站筛选**（避免筛选器复杂化），但可在帖子详情中展示，帮助玩家了解团风。

| 字段 | 类型 | 可选值 | 说明 |
|------|------|--------|------|
| `difficulty` | 枚举 | `beginner` / `normal` / `hardcore` | 难度（新手友好 / 普通 / 硬核） |

| `module_status` | 枚举 | `selected` / `pending` / `none` | 模组状态（已选定 / 待定商议 / 无模组即兴） |
| `allow_spectate` | 布尔 | 默认 `false` | 是否允许观战（若房间支持 OB） |
| `has_secret_ho` | 布尔 | 默认 `false` | 是否包含秘密HO（隐藏线索/角色） |

**发帖表单呈现**：
- 这些字段放置在“通用信息”区，与规则包无关，所有 GM 均可填写。
- 模组状态为“已选定”时，下方展开资产库选择器（从用户已拥有的模组中选择）。

**详情页展示**：
- 在招募卡片中可展示 `allow_spectate` 标识（👁️ 可观战）。
- 详情页展示所有扩展字段的友好标签。

> **注意**：`module_status` 与成团时的模组选择逻辑一致：若发帖时已选定模组，成团时直接使用；若为待定，成团时弹出模态框要求选择；若为即兴，则创建空白团。**此逻辑已在第 6 章成团流程中覆盖**，此处仅明确字段来源。
> 存储口径统一为 `selected` / `pending` / `none`。其中“即兴开团”仅作为 UI 文案映射，不作为独立枚举值存库。

### 21.2 可观战标识与观看直播（🔵 纳入，需配合房间能力）

**卡片展示**：
- 若 `allow_spectate = true`，在招募卡片上显示 👁️ 图标，鼠标悬浮显示“本团支持观战”。

**列表操作按钮逻辑**（针对已开团的招募帖）：
- 若招募帖状态为 `grouped`（已成团）且 `allow_spectate = true`，且当前用户不是团员：
  - 卡片操作按钮显示 `[观看直播]`，点击进入房间的观战模式（只读视角，不可发言/操作）。
- 若 `allow_spectate = false` 或房间未开启 OB，且当前用户不是团员，按钮显示 `[已满员]`（禁用态）。

> 实现依赖房间模块支持观战模式（附录 C 需补充观战能力）。

### 21.3 邀请入团（GM 主动邀请，🟡 v2.0 可选）

**背景**：当前流程只允许玩家主动申请，GM 审批。为增强 GM 招募效率，可支持 GM 在浏览“玩家求组帖”时主动向玩家发送邀请。

**触发位置**：
- 在招募广场的“玩家求组”类型帖子卡片上，对 GM 显示 `[邀请入团]` 按钮（普通玩家不可见）。

**流程**：
1. GM 点击 `[邀请入团]`，弹出模态框：
   - 标题：“邀请玩家 [玩家昵称] 加入你的游戏”
   - 选择邀请类型：
     - ○ 邀请至现有房间（下拉选择 GM 进行中的房间）
     - ○ 为此玩家新建一个房间（下方显示模组选择器，默认使用玩家期望规则）
2. GM 确认后，系统创建邀请记录（`invitations` 表），状态为 `pending`。
3. 玩家收到站内通知 + Socket 推送：“GM [GM昵称] 邀请你加入《团名》”。
4. 玩家点击“接受”后：
   - 若邀请类型为“现有房间” → 玩家直接加入该 campaign，成为正式成员。
   - 若邀请类型为“新建房间” → 系统创建新 campaign，将 GM 和该玩家加入，并关联此邀请。
5. 玩家拒绝或 48 小时未响应 → 邀请失效。

**与现有申请流程的关系**：
- 邀请入团是**独立于申请流程的快捷通道**，不改变原有的申请→审批机制。
- 被邀请的玩家若已申请该团，则邀请按钮置灰，避免重复。

**数据表新增**（v2.0 时加入）：
```sql
CREATE TABLE invitations (
  id UUID PRIMARY KEY,
  from_gm_id UUID NOT NULL,      -- 邀请人（GM）
  to_player_id UUID NOT NULL,    -- 受邀玩家
  campaign_id UUID,              -- 现有房间（若为新建则为空）
  target_ruleset_id UUID,        -- 期望规则（新建时使用）
  status ENUM('pending','accepted','rejected','expired'),
  expire_at TIMESTAMP,
  created_at TIMESTAMP
);
```

| @ 提及 | 输入 `@` 后弹出底部用户选择抽屉，支持搜索与滑动选择 |
| 加载更多 | 主楼层滚动到底部自动加载下一页；楼中楼展开时分页加载 |
| 发布回复 | 发布按钮固定在输入框右侧，轻触提交 |

### 22.3 桌面与移动差异

| 功能 | 桌面端 | 移动端 |
|------|--------|--------|
| 输入框位置 | 页面底部内联 | 固定悬浮在屏幕底部 |
| @ 提及选择 | 下拉搜索框 | 底部滑出抽屉 |
| 楼层号点击 | 显示复制链接菜单 | 直接 Toast 提示 |
| 楼中楼折叠 | 默认展开最近 3 条 | 默认展开最近 3 条，超出部分折叠为计数入口 |

## 23. 社区招募板移动端适配（迁自附录 J）

### 23.1 页面结构

1. 招募板移动端采用单栏垂直滚动。
2. 顶部包含一级 Tab、筛选栏和发帖入口。
3. 一级 Tab 为横向滚动（找团玩 / 当 GM / 我的），激活态使用下划线指示。

### 23.2 筛选栏与底部抽屉

1. 高频筛选项横向滚动展示（规则包、难度、剩余席位等）。
2. 右侧固定漏斗图标，点击后打开 BottomSheet（建议高度 >= 70%）。
3. 抽屉内承载完整筛选条件，底部固定“重置 / 应用筛选”按钮。
4. 筛选条件持久化到 URL 参数，便于刷新和分享。

### 23.3 列表与卡片

1. 默认两列卡片网格（`repeat(2, 1fr)`），当视口 < 390px 时降级为单列。
2. 找团玩卡片展示：标题、规则标签、招募状态、GM 信息、人数进度、时间安排、可观战标识。
3. 当 GM 卡片展示：玩家信息、期望规则/题材、可参与时间、自我介绍摘要。
4. 操作按钮触控热区 >= 44px。

### 23.4 发帖与动作弹层

1. 发帖入口位于页面右上角，可为双按钮或单“发布”按钮 + 动作菜单。
2. 发帖表单在移动端使用底部抽屉（约 90% 高度），字段规范与桌面端保持一致。
3. 成团与邀请入团统一采用底部抽屉交互，不再使用居中弹窗。
