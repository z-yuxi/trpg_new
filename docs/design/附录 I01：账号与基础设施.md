## I01.2 账号与身份系统

### I01.2.1 设计原则

- 极简优先：手机号 + 验证码完成注册登录，密码为后续备用能力。
- 渐进式收集：手机号为唯一强制字段，昵称、头像、身份标签后置补完。
- 最小权限：身份标签用于推荐和展示，功能权限以业务角色和后台中间件为准。
- 安全优先：Access Token 1 小时，Refresh Token 7 天，采用滑动续期与吊销机制。

### I01.2.2 注册与登录流程

| 步骤 | 操作 | 后端行为 | 前端行为 |
| --- | --- | --- | --- |
| 1 | 输入手机号，点击获取验证码 | 校验格式与频率限制，生成 6 位验证码并写入 Redis，TTL 5 分钟 | 展示 60 秒倒计时 |
| 2 | 输入验证码，点击登录/注册 | 校验验证码有效性，查询手机号是否已存在 | 登录按钮禁用并展示 loading |
| 3（新用户） | 自动创建账号 | 生成 UUID 主键、7 位 UID、临时昵称，签发 Access/Refresh Token | 跳转完善资料或首页 |
| 3（老用户） | 直接登录 | 签发新 Token，更新最后登录时间 | 跳转首页或回跳来源页 |

### I01.2.3 验证码安全策略

| 限制项 | 值 | 说明 |
| --- | --- | --- |
| 同一手机号 | 1 次/60 秒，5 次/天 | 防止短信轰炸 |
| 同一 IP | 10 次/小时，50 次/天 | 防止恶意请求 |
| 验证码有效期 | 5 分钟 | 一次性使用 |
| 错误次数限制 | 连续 5 次错误锁定 15 分钟 | 防爆破 |
| 短信模板 | 【TRPG平台】您的验证码是：123456，5分钟内有效。请勿泄露。 | 标准模板 |

### I01.2.4 临时昵称与身份标签

- 临时昵称格式固定为 叙事者_ + 4 位数字。
- 禁止用户自定义与临时昵称格式完全相同的名称，避免伪装。
- identity_tags 仅用于展示与推荐，允许值为 player、gm、creator。
- creator 标签不等于创作者权限；创作者实际权限判定见附录 H01 与附录 A03。

### I01.2.5 登录态管理

| 令牌 | 类型 | 有效期 | 存储位置 | 续期规则 |
| --- | --- | --- | --- | --- |
| Access Token | JWT | 1 小时 | HttpOnly Cookie | 过期后通过 Refresh Token 刷新 |
| Refresh Token | 随机字符串 | 7 天 | HttpOnly Cookie | 每次刷新时轮换并立即吊销旧 Token |

刷新接口固定行为：

1. 校验旧 Refresh Token 未过期、未吊销。
2. 生成新 Access Token 与新 Refresh Token。
3. 将旧 Refresh Token 标记 revoked。
4. 返回新 Access Token，并通过 Set-Cookie 下发新 Refresh Token。

### I01.2.6 密码备用登录

- MVP 不默认开放密码注册登录。
- 用户可在后续版本于账号安全中主动设置密码。
- 密码采用 bcrypt 哈希存储，强度 10。
- 忘记密码只能通过手机号验证码重置。

## I01.2A 用户标识符与登录体系

### 一、用户标识符定义

| 字段 | 用途 | 唯一性 | 能否修改 | 用户感知 | 类比 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **UID** | 系统内部标识，数据库主键 | 全局唯一 | ❌ 永远不能 | 可见但不主动推广 | 身份证号 |
| **username** | 登录凭据 + 搜索凭据 + @提及 | 全局唯一 | ✅ 可改（需唯一） | 用户主动设置，对外展示 | 微信号 |
| **昵称** | 展示名，帖子/评论旁显示 | ✅ 允许重复 | ✅ 随时可改 | 用户感知最强的名字 | QQ名/微信名 |

### 二、昵称规则

| 约束项 | 规则 | 理由 |
| :--- | :--- | :--- |
| 最小长度 | 1 个字符 | 允许单字昵称，符合 TRPG 圈文化习惯 |
| 最大长度 | 16 个字符 | 与现有设计一致 |
| 禁止纯数字 | 不允许昵称全由数字组成 | 防止与 UID 混淆 |
| 禁止纯符号 | 不允许昵称全由符号组成 | 防止无意义的占位昵称 |
| 敏感词过滤 | 昵称必须通过敏感词检测 | 与现有内容安全规则一致 |
| 禁用特定格式 | 不允许使用“叙事者_XXXX”格式 | 该格式为系统保留的临时昵称模板 |

**单字昵称的特殊处理**：单字昵称在搜索结果中，优先展示其 username 辅助辨识，展示格式为 `昵称 (@username)`。

### 三、昵称可重复的设计理由

允许昵称重复，基于以下考量：

1. **降低命名焦虑**。成熟平台（B 站、微博、知乎）都允许昵称重复。用户不必为取名而焦虑。
2. **避免 ID 交易灰产**。不允许昵称重复会导致抢注、囤积、买卖 ID 等灰色产业链，这在贴吧和游戏圈已有大量负面案例。共叙不做稀缺 ID 经济。
3. **TRPG 圈文化兼容**。很多跑团玩家用经典角色名（如“克苏鲁”、“奈亚”），如果昵称不可重复，后来者将无法使用这些名字。

**防冒用机制**：昵称可重复带来的安全风险，通过身份标签体系（实名认证标识、创作者认证标识、信誉分）和 username 辅助辨识来解决，而非通过禁止昵称重复来解决。

### 四、username 规则

| 约束项 | 规则 |
| :--- | :--- |
| 格式 | 字母 + 数字组合，4-20 个字符 |
| 唯一性 | 全局唯一 |
| 修改限制 | 可修改，但修改后原 username 保留 7 天不可被他人占用 |
| 禁止内容 | 不得包含敏感词、不得模仿官方账号格式 |

### 五、搜索规则

用户在搜索框输入内容时：

| 输入类型 | 匹配优先级 | 返回结果 |
| :--- | :--- | :--- |
| 纯数字 | 优先匹配 UID | 精确匹配结果 |
| 字母 + 数字 | 优先匹配 username | 精确匹配结果 |
| 中文 | 匹配昵称 | 可能返回多个结果，每个结果展示为 `昵称 (@username)` |

### 六、登录体系

**三种登录方式并存**：

| 登录方式 | 输入内容 | 适用场景 |
| :--- | :--- | :--- |
| **验证码登录（默认）** | 手机号 + 验证码 | 新用户注册、老用户快速登录 |
| **密码登录** | username + 密码 | 用户主动设置密码后可用；不方便收验证码时使用 |
| **手机号+密码登录** | 手机号 + 密码 | 用户同时设置了密码，且愿意用手机号登录 |

**为什么不用 UID 登录**：UID 是连续的无规律数字，攻击者可编写脚本批量遍历（从 1000100 试到 1000200，几秒钟试 100 次）。username 是用户自设的、无规律的字符串，攻击者要猜都不知道该猜哪些。这是 UID 和 username 安全性的核心区别：是否可被程序化批量生成。

**密码登录的安全保障**：

| 安全层 | 规则 |
| :--- | :--- |
| 密码复杂度要求 | 最少 8 位，必须包含字母和数字 |
| 登录失败处理 | 连续 3 次密码错误后，出现图形验证码；连续 5 次错误锁定 15 分钟 |
| 登录频率限制 | 同一账号 1 分钟内最多尝试 5 次 |

### 七、机器人账号的凭据配置

机器人账号（UID 1000095-1000099）不需要手机号。它们在数据库中的设置方式：

| 设置项 | 配置方式 |
| :--- | :--- |
| 手机号 | 不需要，留空或填虚拟占位号 |
| username | 系统直接指定，如 `bot_veil`、`bot_robot` |
| 密码 | 由服务器环境变量生成强密码，不在代码中硬编码 |
| JWT Token | 由部署脚本生成长期有效的专用 Token，用于 API 调用 |

机器人的 JWT Token 由代码包 A 的后端服务在启动时通过环境变量读取，并用于与代码包 B 的 API 通信时进行身份认证。Token 定期轮换，轮换周期由运维配置。

### 八、官方身份认证体系

所有 UID 在 1000000-1000099 范围内的官方账号（含管理员账号和机器人账号），都享有特殊的视觉标识。目标不是抬高身份层级，而是让用户一眼识别账号来源。

| 账号类型 | UID 范围 | 视觉标识 |
| :--- | :--- | :--- |
| **官方机器人** | 1000095-1000099 | 名字旁强制显示 `[机器人]` 标签，头像有专属齿轮/芯片图标，卡片带有微弱蓝紫色光效边框 |
| **平台管理员** | 1000000-1000094 | 名字旁显示 `[官方]` 标签，头像有盾牌图标，卡片带有淡金色光效边框 |

### 九、官方账号多层识别规范

要让用户在任何场景都能快速识别，需要多个识别点同时作用：

| 识别点 | 普通用户 | 官方机器人 | 平台管理员 |
| :--- | :--- | :--- | :--- |
| **昵称标签** | 无 | `[机器人]`（蓝紫色） | `[官方]`（淡金色） |
| **头像装饰** | 无 | 右下角叠加齿轮图标 | 右下角叠加盾牌图标 |
| **卡片边框** | 无色 | 微弱蓝紫色呼吸光效 | 淡金色光效 |
| **个人主页** | 正常 | 顶部显示“本账号为平台 AI 机器人” | 顶部显示“平台管理员账号” |
| **搜索结果** | 正常 | 名称旁带 `[机器人]` 标签 | 名称旁带 `[官方]` 标签 |

**关键设计原则**：上述标识由后端根据 UID 号段强制渲染，系统强制、不可隐藏、不可伪造。

### 十、机器人昵称融入社区的设计边界

机器人昵称可以使用“看起来像普通用户”的命名风格，以降低交流门槛并提升社区自然感，但必须遵循身份透明原则。

**收益目标**：

1. 降低新用户对机器人账号的戒备心，提升互动意愿。
2. 冷启动阶段保持社区内容与互动的自然观感。
3. 在被识别为 AI 时形成正向惊喜，而非被欺骗感。

### 十一、防混淆底线

| 底线 | 规则 |
| :--- | :--- |
| **标签不可隐藏** | `[机器人]`/`[官方]` 标签由系统强制渲染，用户与机器人均不可关闭 |
| **标识不可伪造** | 标签、图标、光效根据 UID 直接渲染，普通用户无法通过昵称、头像模仿 |
| **身份透明** | 机器人主页与首次互动场景，系统主动提示“这是平台 AI 机器人” |

这三条底线确保：机器人可以像人一样自然交流，但不能冒充真实人类身份。

## I01.3 管理员账号与后台访问控制

### I01.3.1 管理员创建方式

- 管理员账号不走普通手机号验证码注册流程。
- 由平台运维直接写入 users 表。
- uid 固定使用保留号段 1000000-1000099。
- user_type 必须包含 admin。
- 管理员账号必须配置 password_hash，不支持纯验证码登录后台。

**保留号段细化分配**：

| 号段范围 | 用途 | 备注 |
|---------|------|----- |
| 1000000–1000009 | 超级管理员账号 | 平台运维直接写入 |
| 1000010–1000094 | 预留（测试账号、运营账号等） | 按需分配 |
| 1000095–1000099 | AI 机器人账号 | `is_bot=TRUE`，前台强制展示「机器人」标签 |

- **1000095-1000099**：AI 测试机器人专用号段。用于自动化社区流程测试与冷启动内容生成，前台强制展示机器人标识，不参与社区排序与信誉分计算。正式上线后转为休眠状态。

**机器人账号（1000095–1000099）识别规则**：

| UID | 昵称 | 人设 |
|-----|------|------|
| 1000095 | 叙言者 | COC 解谜爱好者（偏硬核） |
| 1000096 | 帷幕之后 | 叙事型 GM（带团经验丰富） |
| 1000097 | 墨菲斯 | 规则研究者（严谨文风） |
| 1000098 | 夜骐 | 新手友好、活跃气氛 |
| 1000099 | 旅人说书人 | 故事录常驻作者（文笔好） |

- 前台昵称旁强制叠加「机器人」标签，头像右下角叠加机器人小图标。
- 该标识不可隐藏、不可修改，由系统通过 `is_bot=TRUE` 字段强制渲染。
- 机器人账号生成的所有内容自动标记 `is_bot_generated=TRUE`，便于清理和数据统计。

### I01.3.2 后台访问双层保护

1. 业务权限层：后端 requireAdmin 校验 user_type 包含 admin。
2. 网络层：同时校验请求 IP 位于 WireGuard 内网白名单。
3. 任一条件不满足，统一返回 HTTP 403 Forbidden。
4. 管理员可以作为普通玩家使用平台，但进入后台仍必须满足内网限制。

### I01.3.3 创作者与管理员权限闭环

- 创作者权限判定：subscription_type === 'creator' 或 user_type 含 creator/admin。
- /creator/** 路由需设置 requiresCreator: true。
- /admin/** 路由仅允许 requireAdmin 中间件通过后访问。
- 结构化错误码统一使用 FORBIDDEN。

## I01.4 基础表结构与审计

### I01.4.1 核心表

```sql
CREATE TABLE users (
  id VARCHAR(64) PRIMARY KEY,
  uid INT UNSIGNED NOT NULL UNIQUE,
  phone VARCHAR(20) NOT NULL UNIQUE,
  nickname VARCHAR(64) NOT NULL,
  avatar_url VARCHAR(255),
  identity_tags JSON,
  user_type JSON,
  has_password BOOLEAN DEFAULT FALSE,
  password_hash VARCHAR(255),
  status ENUM('active', 'banned') DEFAULT 'active',
  last_login_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE refresh_tokens (
  id VARCHAR(64) PRIMARY KEY,
  user_id VARCHAR(64) NOT NULL,
  token_hash VARCHAR(255) NOT NULL,
  expires_at TIMESTAMP NOT NULL,
  revoked BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_token_hash (token_hash),
  INDEX idx_user_revoked (user_id, revoked)
);

CREATE TABLE login_logs (
  id VARCHAR(64) PRIMARY KEY,
  user_id VARCHAR(64) NOT NULL,
  ip VARCHAR(45) NOT NULL,
  user_agent VARCHAR(255),
  device_fingerprint VARCHAR(64),
  login_result ENUM('success', 'failure') DEFAULT 'success',
  failure_reason VARCHAR(64),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_user_time (user_id, created_at)
);
```

### I01.4.2 验证码存储

- 主存储：Redis，key = sms:{phone}，TTL = 300 秒。
- 审计需要时，可异步写入 sms_codes 表。
- 落库不是 MVP 强制要求，但频率限制与日志必须保留。

- 构建阶段：npm ci --ignore-scripts。
- 运行阶段：非 root 用户、只读根文件系统。

- 数据库每日自动备份，保留 30 天。
- 房间日志按冷热分层：3 个月热数据在 MySQL，历史压缩归档至 OSS。
- 登录日志、后台操作日志、审计日志按合规要求保留。

### I01.7 创作者身份认证与笔名
1. 认证体系

阶段	时机	认证方式	目的
注册	首次注册	手机号验证码	基础实名，满足信息发布合规
成为创作者	首次开通创作者身份	身份证号+姓名二要素	建立创作者身份唯一性，满足合规要求
发布付费模组/提现	首次涉及资金交易	二要素 + 银行卡绑定 + 手机预留号	满足支付与税务合规
说明：创作者身份认证需接入第三方实名认证服务商（如阿里云、腾讯云等），通过API完成姓名+身份证号的核验。平台仅存储核验记录，不存储完整身份证号（或仅存储脱敏信息）。

2. 创作者笔名

创作者可设置独立的“创作者笔名”（creator_display_name），与玩家昵称完全分离：

玩家昵称（根昵称）：所有社交行为的默认标识

创作者笔名：仅在发布作品、管理作品时对外展示

3. @提及与通知规则

所有@提及的通知，发送给同一账号，在通知中心通过分类标签区分

@创作者笔名的通知，引导用户以创作者身份查看和回复

@根昵称的通知，以玩家/主持人身份进行

回复时，系统自动匹配来源身份，用户无需手动切换

4. 防马甲机制

创作者身份开通需实名认证，一个身份证号仅可绑定一个创作者身份

管理后台中，玩家的所有身份操作日志关联到同一实名主体，确保行为可追溯
