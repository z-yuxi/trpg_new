# 附录 00：文档拆分与迁移执行清单

> 文档版本：V1.6

## 1. 目标与范围

本清单用于执行两件事：

1. 将 `产品设计.md` 中过长的模块化内容拆分为功能附录，降低单文档维护复杂度。
2. 对迁移后的命名、引用、标题、边界说明进行一次性修缮，确保文档体系可持续维护。

说明：本清单聚焦结构治理与内容迁移，不包含社区能力新增设计。社区补足在结构稳定后单独推进。

## 1.1 共识决议（2026-04-28）

经评审确认，文档体系采用三级框架：

1. L1（一级）：`产品设计.md`，仅保留总纲（范围边界、能力清单、跨模块依赖、验收索引）。
2. L2（二级）：功能附录（A/B/C/D...），作为各功能的权威定义来源。
3. L3（三级）：子附录（A01/A02...），承载可查询规范（ID、数据字典、Schema、格式协议、接口契约）。

配套规则：

1. 页面设计采用"全局规范集中 + 功能页面分册"，不做完全散拆。
2. 历史文档保留并标注"历史/参考"，逐步摘除重复内容，不直接删除。
3. 执行顺序固定为：结构修缮 -> 主文档拆分 -> 社区补足。

## 2. 编号与命名规则（统一口径）

1. 统一采用两位编号：`附录 A01`、`附录 B02`。
2. 文件名、一级标题、被引用名称三者必须一致。
3. 每份附录标题末尾保留历史映射：`（原附录 X）`，保留 1-2 个版本周期。
4. 目录排序以编号为准，不以中文名排序。

## 3. 页面设计拆分原则（关键）

页面设计不做完全散拆，采用“全局规范集中 + 功能页面分册”：

1. 全局规范集中在 A 组：栅格、间距、控件密度、按钮层级、响应式、可访问性红线。
2. 功能附录只承载本功能信息架构与流程：页面结构、状态机、权限、异常流、空状态、埋点口径。
3. 禁止在多个功能附录重复定义同一视觉红线；重复项统一回指 A 组。

### 3.1 重复定义强制收口（新增）

1. 状态机在 L2 只保留一份权威定义，其他文档仅回链章节，不复制正文。
2. 数据字典、表结构、Schema 在 L3（`附录 D04`）只保留一份权威定义，其他文档仅回链章节。
3. `产品设计.md` 仅保留能力、边界、依赖和索引，不承载交互细节正文。
4. 历史/参考段落允许保留，但必须标注“非权威源、不再维护”。

## 4. 目标结构（本轮确认）

- A 组：基础公共规范
- B 组：数据与格式标准
- C 组：核心跑团模块
- D 组：规则引擎模块
- E 组：模组编辑器模块
- F 组：社区系统模块
- G 组：品牌与体验规范
- H 组：商业化与会员模块
- I 组：设计质量与维护规范

## 6. 分阶段执行顺序

### Phase 1：结构收口（先做）

1. 统一编号命名。
2. 修复断链引用。
3. 在 `产品设计.md` 增加“模块索引与来源说明”。

验收：无重复编号、无明显断链、主文档可定位到每个模块附录。

### Phase 2：内容拆分（再做）

1. 从 `产品设计.md` 拆分章节到 C-H 附录。
2. 主文档保留“能力摘要 + 链接”，删除冗长细节。

验收：主文档长度显著下降，模块文档职责清晰。

### Phase 3：文案修缮（最后做）

1. 统一术语（例如“规则包/规则集”“房间/团”等）。
2. 统一边界表述与跨文档引用语句。

验收：同一概念无冲突定义，跨文档引用一致。

## 7. 高风险检查项

1. 同编号多文件（如历史 `A03` 冲突）
2. 文件名与标题不一致
3. 主文档引用旧文件名导致断链
4. 同一规则在多文档重复维护
