# TRPG 模组编辑器设计方案（修订版）

## 一、背景与问题

当前全量块级编辑把普通叙事内容和可调用对象统一拆成块，导致两类成本同时升高：

1. 创作成本高：创作者需要频繁处理字段与结构，写作被工具流程打断。
2. 研发维护重：块增删改查、多端同步、解析链路复杂，易出现一致性问题。

## 二、目标与边界

本方案同时保留以下核心能力：

1. 长文本创作体验必须接近普通文档编辑。
2. KP 在房间内必须能快速调用 NPC/道具/场景等结构化内容。

非目标：不在首版建设完整音乐系统、复杂混音与开放上传音效市场。

## 三、核心方案

采用富文本 + 轻量 Mention 标记：

1. 普通叙事内容使用富文本编辑，覆盖 90% 写作场景。
2. 仅在需要可调用对象时输入 @ 触发选择面板，插入 Mention。
3. Mention 只承载最小必要结构信息：type、id、label。

KP 调用方式：在编辑预览或房间消息中点击 Mention，打开对应实体卡片。

## 四、白噪音策略（新增）

### 4.1 结论

一点白噪音是比背景音乐更适合首版的氛围方案。

原因：

1. 不抢叙事：白噪音不携带强旋律与情感指向，不会压过文字想象。
2. 低门槛：GM 无需选曲与试听匹配，按场景一键切换。
3. 低风险：可使用自制或免版权环境音，规避音乐版权链路。
4. 可复用：编辑器与房间可以共享同一套音频能力层。

### 4.2 功能定位

白噪音不是音乐系统，而是氛围开关：

1. 编辑器侧：辅助创作专注。
2. 房间侧：辅助沉浸叙事。

### 4.3 推荐关键词（首批）

首批控制在 8 类，覆盖大多数场景：

1. 雨
2. 风
3. 火
4. 洞
5. 夜
6. 城
7. 海
8. 机

## 五、数据模型与接口建议

场景模型新增字段：

```ts
type AmbienceKey = 'rain' | 'wind' | 'fire' | 'cave' | 'night' | 'city' | 'sea' | 'engine' | null;

interface SceneAmbienceConfig {
	ambience: AmbienceKey;
	volume?: number; // 0~1，默认 0.18
	enabled?: boolean; // 默认 true
}
```

建议接口：

1. GET /scenes/:sceneId/ambience
2. PUT /scenes/:sceneId/ambience

说明：

1. 房间复用播放器能力层，但状态与权限单独管理。
2. GM 可配置是否广播给全体，玩家可本地单独静音。

## 六、前端实现建议

### 6.1 资源规范

预置资源放置：

1. /public/audio/ambience/

音频建议：

1. 单文件时长 30 秒到 120 秒。
2. 编码 MP3，128kbps 即可。
3. 统一响度建议在 -20dB 左右，避免首次播放突兀。

### 6.2 播放器能力层

封装统一播放器服务，至少支持：

1. play(key)
2. stop()
3. setVolume(value)
4. fadeTo(value, ms)
5. mute / unmute

### 6.3 关键交互

1. 默认低音量自动恢复：进入场景后按配置启用，默认 15% 到 20%。
2. 用户可控：任何端都可一键静音与调整音量。
3. 切场景平滑过渡：旧环境淡出，新环境淡入。

## 七、分期落地

### P0（必须）

1. 富文本基础编辑 + Mention 选择插入。
2. 场景 ambience 字段与基础接口。
3. 房间内白噪音播放、静音、音量。

### P1（应当）

1. GM 广播开关与玩家本地覆盖策略。
2. 场景切换淡入淡出。
3. 编辑器侧白噪音复用（创作模式）。

### P2（可选）

1. 更多主题包与关键词扩展。
2. 线索卡微弱音效联动（保持克制，默认关闭）。

## 八、验收标准

1. 创作者可在不理解块结构的情况下完成长文写作。
2. Mention 插入、渲染、点击打开实体卡全链路稳定。
3. 房间白噪音在主流浏览器可稳定循环播放。
4. 白噪音默认音量不打断对话，不引起明显投诉。
5. GM 与玩家都具备明确可见的音频控制权。

## 九、方案收益

| 角色 | 收益 |
| --- | --- |
| 模组创作者 | 写作路径接近普通文档，学习成本和心理负担显著降低 |
| 跑团 KP | 保留快速调用能力，同时获得轻量氛围增强 |
| 开发团队 | 减少块级维护复杂度，避免过早建设重型音频系统 |

## 3. 模组编辑器

_模组编辑器采用**富文本 + Mention 引用**方案：普通叙事以文档方式连续创作，仅在需要调用实体时插入轻量 Mention（场景、NPC、怪物、事件、线索、检定、道具），兼顾写作流畅性与结构化检索能力。_

### 3.1 编辑器布局与 Mention 引用

**编辑器布局示例**：

plain

复制

```plain
[模组标题]
[封面图片]
---
## 简介（创作者自由书写，支持 Markdown/富文本）
... 模组背景、题材、适用人群、创作说明 ...
---
## 玩家须知（PL 可见）
... 无剧透的规则提示、时代背景、初始任务 ...
---
正文（连续富文本）
"暴雨中的丰庄街道空无一人，@场景:丰庄外街 只剩零散灯火。"
"守夜人 @NPC:老罗 正在壁炉旁低声祷告。"
"若玩家尝试撬锁，触发 @检定:侦查-困难；成功后揭示 @线索:烧焦的账本。"
```

说明：

- Mention 只承载 `type/id/label`，实体详情在右侧引用面板维护。
- 场景、NPC、线索、检定等实体维护为独立资源库，正文通过 Mention 引用。
- 房间侧点击 Mention 可直接打开实体卡，保持调用链路一致。

## 5. 移动端适配与跨端同步（迁自附录 J）

### 5.1 移动端行为补充

1. 模组编辑器在移动端为轻量可编辑模式。
2. 开放范围：元信息、纯文本段落、标题层级（H1/H2/H3）。
3. Mention 对应复杂实体只读；图片/音频仅查看。
4. 可视化拖拽编辑器在移动端不可用，统一提示“请在电脑上使用此功能”。
5. 移动端仅支持基础导出（TXT/Markdown）。

### 5.2 跨端同步规则

1. 自动保存防抖：移动端 1.5 秒无输入触发保存；桌面端保持 3 秒。
2. 强制保存触发：点击完成、路由离开、切后台时必须立即保存一次，不等待防抖。
3. 冲突提示策略：桌面端收到移动端更新时显示非阻断 Toast（3 秒自动消失），提供“刷新查看”和“稍后处理”。
4. 用户未刷新继续编辑时，以后续保存返回的版本冲突提示为准，不强制中断输入流。
5. 资源级订阅频道：
	- 模组变更频道：`/modules/{module_id}/changes`
	- 规则包变更频道：`/rulesets/{ruleset_id}/changes`（预留）
6. 频道按资源订阅，不按用户广播；客户端仅订阅当前打开资源。
7. 离线队列：可编辑内容先写入 IndexedDB，再尝试保存；失败采用指数退避重试；恢复前台后自动重试；成功后清理缓存并推送变更事件。
8. 保存请求应携带 `op_id` 做幂等去重，避免弱网重试导致重复写入。
