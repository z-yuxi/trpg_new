### 1. 术语词典：这是最高优先级

你必须把我们刚刚对齐的术语，写成一份明确的 **“术语映射表 (Glossary)”** ，并告诉 AI：**“这是唯一真理，任何情况下都必须遵守，禁止变体。”**

**给 AI 的指令范例：**
```markdown
## 全局术语词典 (必须严格遵守)
在对 UI、文案、变量、API 进行开发时，必须使用以下统一术语：

| 业务概念 | UI文案 (用户所见) | 前端变量/路由/组件 | 后端API字段/数据库字段 | 禁止使用的别名 |
| :--- | :--- | :--- | :--- | :--- |
| 核心游戏载体 | **房间** | `room` | `campaign` | 团、Team、Game |
| 寻找/组建游戏 | **招募** | `recruit` | `recruitment` | 组队、开黑、发车 |
| 游戏主持人 | **GM** | `gm` | `gm` | KP、DM、主持人 |
| 玩家角色数据 | **角色卡** | `characterCard` | `character_sheet` | 人物卡、角色、Sheet |
| 游戏内的子空间 | **场** | `scene` | `scene` | 场景、Scene、地图 |

要求：
1. 生成任何代码时，如果遇到上述概念，必须使用“前端变量/路由/组件”列的命名。
2. 生成任何UI界面时，展示给用户的文本必须使用“UI文案”列的文字。
3. “禁止使用的别名”在任何新代码中都不得出现。
```

### 2. 组件状态规则：这是防止 AI “脑补”的关键

你之前分析过的“申请加入按钮状态”问题，对 AI 来说同样是坑。你需要给它一套明确的规则，而不是让它自己看着办。

**给 AI 的指令范例：**
```typescript
// 文件: ai-context/button-rules.ts
// 这是给AI的上下文，定义了平台中所有“申请”类按钮的状态机

/**
 * 申请加入招募帖的按钮状态机
 * 
 * @param status 当前用户对该帖子的申请状态
 * @param recruitmentStatus 当前招募帖的状态
 * @param isFull 是否已无席位
 */
export function getApplyButtonStatus(
  status: 'none' | 'pending' | 'invited' | 'confirmed' | 'waiting',
  recruitmentStatus: 'open' | 'full' | 'grouped' | 'closed',
  isFull: boolean
) {
  // 1. 已成团或已关闭
  if (recruitmentStatus === 'grouped' || recruitmentStatus === 'closed') {
    return { text: '已结束', disabled: true, action: null };
  }
  // 2. 已确认入团
  if (status === 'confirmed') {
    return { text: '已加入', disabled: true, action: null };
  }
  // 3. 待确认
  if (status === 'invited') {
    return { text: '确认入团', disabled: false, action: '/api/applications/{id}/confirm' };
  }
  // 4. 申请审核中
  if (status === 'pending') {
    return { text: '已申请', disabled: true, action: null };
  }
  // 5. 候补中
  if (status === 'waiting') {
    return { text: '候补中', disabled: true, action: null };
  }
  // 6. 无申请，且招募中
  if (recruitmentStatus === 'open') {
    if (isFull) {
      return { text: '加入候补', disabled: false, action: '/api/.../apply?type=waiting' };
    }
    return { text: '申请加入', disabled: false, action: '/api/.../apply' };
  }
  // 兜底
  return { text: '不可用', disabled: true, action: null };
}
```
把这个文件给AI，告诉它：“所有申请加入相关的按钮，都必须通过这个函数来生成状态，**严禁**在组件里手写 `if-else`。”

### 3. 代码风格与架构红线

AI 最喜欢干的事情就是“自由发挥”，它可能在你规范的 Vue 项目里突然引入 `React` 的写法，或者自己发明一套新的状态管理。

**给 AI 的指令范例：**
```markdown
## 架构与风格红线 (Architecture Red Lines)
1. **框架**：本项目为 Vue 3 + TypeScript，**严禁**引入 React / Angular 的语法或库。
2. **状态管理**：全局状态统一使用 Pinia，组件内部状态统一使用 VueUse 的 composable。**严禁**在组件内写入任何 `fetch` / `axios` 的直接调用，所有 API 调用必须封装在 `api/` 目录下。
3. **组件复用**：在生成任何新页面之前，请先在本文档中搜索是否有可复用的组件(如 `EmptyState`, `PageLayout`)。**严禁**重写功能相同的组件。
4. **样式**：所有样式必须使用 `<style lang="scss" scoped>` 并引用设计令牌变量 (`var(--color-primary)`等)。**严禁**硬编码任何颜色值(如 `#ffffff`)或像素值。
```

## 一、页面一致性检查（Page Coherence）

所有后台页面必须遵循统一的框架规范，消除"切换导航后割裂感"。

| # | 检查项 | 通过标准 | 严重等级 |
|---|--------|----------|----------|
| 1.1 | **PageLayout 复用** | 页面是否复用了统一的 `PageLayout` 容器？禁止每个页面独立手写布局。 | 🔴 阻断 |
| 1.2 | **Header 结构** | 标题区是否为"左：标题+描述 | 右：主操作按钮"？按钮是否垂直居中对齐？ | 🔴 阻断 |
| 1.3 | **主操作按钮位置** | 主操作按钮（新建/上传/发布）是否固定在 Header 右上角？ | 🔴 阻断 |
| 1.4 | **按钮主次顺序** | 按钮顺序是否为"次操作 → 主操作"（从左到右）？主操作是否使用品牌色？ | 🟡 严重 |
| 1.5 | **Stats 区规范** | 统计卡片是否使用了 `DashboardStats` 组件？是否左对齐（禁止居中）？ | 🟡 严重 |
| 1.6 | **FilterBar 位置** | 筛选栏是否在 Stats 下方（如有）或 Header 下方？是否与内容区间距 16px？ | 🟡 严重 |
| 1.7 | **内容区网格** | 卡片网格是否遵循响应式规则（桌面 4/2 列、平板 2 列、移动 1-2 列）？ | 🟡 严重 |
| 1.8 | **空状态统一** | 空状态是否使用了 `EmptyState` 组件？包含 SVG 占位图 + 标题 + 描述 + 操作按钮？ | 🟢 一般 |
| 1.9 | **全局内边距** | 页面内边距是否为 24px（桌面）/ 16px（移动）？内容区最大宽度是否 1280px 居中？ | 🟡 严重 |
| 1.10 | **跨页面组件复用** | 同一组件（卡片、按钮、标签）在不同页面样式是否一致？禁止独立写样式。 | 🔴 阻断 |

## 二、主题适配检查（Theme Adaptation）

确保日间/夜间模式切换后，无元素"掉色"、无硬编码白斑、对比度达标。

| # | 检查项 | 通过标准 | 严重等级 |
|---|--------|----------|----------|
| 2.1 | **品牌色锁定** | `--color-primary` 是否为 `#5B8DB8`（日间）/ `#6B9DC8`（夜间）？禁止改为 Slate 灰或其他蓝色。 | 🔴 阻断 |
| 2.2 | **危险色锁定** | `--color-danger` 是否为 `#B85450`（日间）/ `#C86460`（夜间）？ | 🔴 阻断 |
| 2.3 | **无硬编码颜色** | 组件 CSS 中是否存在 `#f5f5f5`、`#ddd`、`#222`、`#fff` 等裸色值？必须替换为语义变量。 | 🔴 阻断 |
| 2.4 | **无幽灵变量** | 是否存在 `--fg-1`、`--bg-2`、`--bg-3`、`--border` 等未定义变量？必须迁移到新语义命名。 | 🔴 阻断 |
| 2.5 | **夜间模式对比度** | 所有文字在背景上对比度是否 ≥ 4.5:1？（正文）/ ≥ 3:1？（大文字） | 🔴 阻断 |
| 2.6 | **按钮反色** | 夜间模式下主按钮是否为品牌蓝背景 + 白色文字？禁止变成"隐形按钮"（浅灰背景+白字）。 | 🔴 阻断 |
| 2.7 | **输入框背景** | 夜间模式下输入框背景是否为 `--surface-card`（深灰），而非 `--surface-page`（更浅）？ | 🟡 严重 |
| 2.8 | **卡片背景** | 夜间模式下卡片背景是否为 `--surface-card`（`#161B22`），无硬编码白色或浅灰色？ | 🟡 严重 |
| 2.9 | **阴影适配** | 夜间模式下阴影是否加深（`rgba(0,0,0,0.4+)`），而非沿用日间浅色阴影？ | 🟢 一般 |
| 2.10 | **切换动画** | 日/夜切换时，背景色、文字色、边框色是否有 350ms 的平滑过渡？ | 🟢 一般 |

## 三、响应式与布局检查（Responsive & Layout）

确保宽屏无单侧留白、移动端触控友好、信息架构不崩塌。

| # | 检查项 | 通过标准 | 严重等级 |
|---|--------|----------|----------|
| 3.1 | **留白对称** | 宽屏（1920px+）下，主内容区是否居中（`margin: 0 auto`）？禁止左对齐导致右侧大块留白。 | 🔴 阻断 |
| 3.2 | **断点遵循** | 是否使用标准断点（桌面 ≥1280px、平板 ≥768px、移动 <768px）？ | 🟡 严重 |
| 3.3 | **触摸目标** | 移动端所有可点击元素（按钮、卡片、列表项）尺寸是否 ≥ 44px x 44px？ | 🔴 阻断 |
| 3.4 | **底部栏切换** | 跑团房间内是否隐藏全局底部导航，显示专属底部快捷栏？切换是否有动画？ | 🟡 严重 |
| 3.5 | **表单排版模式** | 窄容器（<300px）内是否使用水平标签模式？宽容器（≥600px）内是否使用垂直标签模式？ | 🔴 阻断 |
| 3.6 | **控件密度** | 边栏/工具栏是否使用 Dense 密度（28-32px）？常规表单是否使用 Normal 密度（40px）？ | 🟢 一般 |
| 3.7 | **模态框适配** | 移动端模态框是否为全屏底部抽屉（圆角顶部 16px），而非居中弹窗？ | 🟡 严重 |
| 3.8 | **筛选栏折叠** | 移动端筛选栏是否只显示 2-3 个高频项，其余折叠进"更多筛选"底部抽屉？ | 🟢 一般 |
| 3.9 | **Stats 响应式** | 移动端 Stats 卡片是否为 2 列网格（或 2x2）？禁止 4 列导致卡片过窄。 | 🟡 严重 |
| 3.10 | **内容区单列** | 移动端内容区是否为单列卡片流？必要时双列，禁止三列以上。 | 🟡 严重 |

## 六、跨端同步检查（Cross-Device Sync）

针对模组编辑器移动端与桌面端的近实时同步场景。

| # | 检查项 | 通过标准 | 严重等级 |
|---|--------|----------|----------|
| 6.1 | **防抖策略区分** | 移动端是否为 1.5s 防抖？桌面端是否为 3s 防抖？ | 🟡 严重 |
| 6.2 | **强制保存触发** | 点击"完成"、路由离开、切后台时是否立即触发保存（不等待防抖）？ | 🔴 阻断 |
| 6.3 | **保存状态指示** | 顶部是否常驻保存状态（已保存 ✅ / 保存中 ⏳ / 保存失败 ❌）？ | 🟡 严重 |
| 6.4 | **冲突提示非阻断** | 桌面端收到移动端更新时，是否显示非阻断 Toast（3秒自动消失）？禁止弹窗打断输入流。 | 🟡 严重 |
| 6.5 | **离线队列** | 弱网/断网时，输入是否先写入 IndexedDB？恢复网络后是否自动重试？ | 🔴 阻断 |
| 6.6 | **幂等去重** | 保存请求是否携带 `op_id`？弱网重试时是否避免重复写入？ | 🟡 严重 |

## 八、AI 生成页面指引（修正版）

本文档中的页面布局描述均为**规则级描述**，但**不等于"布局可随意推导"**。

AI 在生成具体页面时，必须遵循以下步骤：

1. **读取本附录**：获取页面核心模块、组件清单、权限矩阵。
2. **读取《附录 B：设计令牌 v2.0》**：获取颜色、字体、圆角、阴影等视觉变量。
3. **读取《产品设计.md》中对应功能的验收标准**：确保交互逻辑正确。
4. **强制复用 PageLayout**：所有后台页面必须使用统一的 `PageLayout` 容器，禁止手写独立布局。
5. **遵循表单排版决策树**：窄边栏（<300px）内绝对禁止使用垂直标签模式。
6. **生成布局**：使用品牌色系、遵循 2.1.2 定义的卡片网格列数（桌面4列，移动2列），自动推导字段排列。
7. **状态处理**：根据本附录中的"空状态与引导"生成对应占位图。

**AI 生成的内容应接受人工检查，重点验证**：
- 权限控制是否正确（GM 独有功能是否对玩家隐藏）。
- 是否复用了 `PageLayout` 容器（检查边距、按钮位置、Stats 对齐方式）。
- 窄边栏内是否有表单输入框（如有，视为 Bug）。
- 移动端是否应用了降级方案。
- 表单必填项是否与《产品设计》一致。

**文档状态**：v1.0，可直接作为前端任务单和 UI 走查依据。  
**维护者**：设计团队 + 前端负责人  
**下次评审**：2026-05-25

### 10.1 空间层级决策树（AI必须遵循）
生成任意页面元素时，先问：
这个元素是"氛围/背景"吗？ → 背景层：无阴影、无交互、低对比度
这个元素是"结构/导航"吗？ → 中景层：shadow-xs、可点击但无位移
这个元素是"操作/焦点"吗？ → 前景层：shadow-sm、悬停shadow-md+translateY(-1px)
无法归类？ → 默认降级一层（宁可平淡，不要抢戏）

### 10.2 组件层级映射表

| 组件 | 所属层级 | 阴影 | 悬停效果 | 常见AI错误 |
|------|---------|------|---------|-----------|
| 页面背景 | 背景层 | 无 | 无 | AI常设为纯白#fff |
| 首页入口块 | 中景层 | 无 | 无 | AI常错误扩展为大 Banner + 多按钮 |
| 分区标题 | 中景层 | 无 | 无 | AI常加阴影 |
| 导航栏 | 中景层 | shadow-xs | 无 | AI常设为透明 |
| 筛选栏 | 中景层 | 无 | 背景色变亮 | AI常加阴影 |
| 列表项（紧凑） | 中景层 | 无 | 背景hover | AI常加卡片阴影 |
| 操作卡片（emphasized） | 前景层 | shadow-sm | shadow-md+上浮 | AI常用默认阴影 |
| 主按钮 | 前景层 | 无（自身有背景） | translateY(-1px) | AI常无悬停效果 |
| 空状态插图 | 前景层 | 无 | 无 | AI常只有文字 |

### 10.3 反例库（AI禁止复用）

以下模式为当前项目中的错误实现，AI生成新页面时**绝对禁止**复用：

1. **扁平列表卡片**：所有卡片同一阴影、同一高度、无悬停区分（见截图_招募板_v1）
2. **首页入口膨胀**：把首页做成 Banner 首屏或塞入多个主操作按钮（与 A07 单按钮规则冲突）
3. **状态文字化**：仅用"准备中"文字标签，无颜色/动画/图标辅助（见截图_房间_v1）
4. **按钮位置混乱**：主操作藏在卡片内、标题下方、或顺序颠倒（见截图_全局_v1）
