```markdown
### 7.7 评论系统设计（贴吧模式）

#### 设计选择
社区-招募板的评论系统采用**贴吧式双层嵌套模式**（主楼层 + 楼中楼），而非扁平评论区。原因如下：
- 招募帖需要清晰的“盖楼”氛围，方便 GM 与多个玩家沟通，楼层号提供明确的引用锚点（如“见3楼”）。
- 楼中楼避免对话打乱主楼层顺序，保持核心信息（如招募进展、规则答疑）的可读性。
- 与主流 TRPG 社区的讨论习惯一致，降低用户学习成本。

#### 核心概念

| 概念 | 定义 | 示例 |
|------|------|------|
| **主楼层** | 用户对主题帖的直接回复，按时间正序排列，拥有全局唯一的楼层号 | 1楼（楼主帖）、2楼、3楼…… |
| **楼中楼** | 附着在某个主楼层下的二级评论，不占用楼层号，仅在该楼层下方折叠显示 | 2楼下的“李四：我报名” |

#### 数据规则
- **1楼为楼主帖内容**：由发帖人创建，不可被回复占位，但可被编辑。
- **主楼层**：用户点击“回复主题帖”生成。楼层号自动递增，删除后**保留占位**（显示“该楼层已删除”），楼层号不变。
- **楼中楼**：用户点击某主楼层的“回复”按钮生成。按时间正序排列，支持点赞、举报、删除。
- **@提及**：在主楼层或楼中楼输入 `@用户名`，被@者收到通知（站内信+私信）。

#### 交互规则

| 操作 | 行为 | 前端反馈 |
|------|------|----------|
| 回复主题帖 | 生成新主楼层，楼层号 = 当前最大楼层号 + 1 | 滚动到页面底部，显示新楼层 |
| 回复某楼层 | 在该楼层的楼中楼区域新增一条评论，不生成新楼层 | 该楼层的楼中楼区域展开，新评论高亮1秒 |
| 展开/折叠楼中楼 | 默认显示最近3条楼中楼，点击“共X条回复”展开全部 | 平滑展开动画 |
| 删除主楼层 | 内容清空，显示“[该楼层已删除]”，楼层号保留 | 原内容消失，替换为灰色占位文字 |
| 删除楼中楼 | 直接移除该条评论 | 从列表中消失 |

#### 与现有“申请加入”功能的关系
- 申请加入团的操作独立于评论系统，通过帖子底部的 `[申请加入]` 按钮触发。
- 评论（主楼层/楼中楼）仅用于讨论，不自动产生申请。

> **性能提示**：楼中楼数据量较大时，采用懒加载（滚动到底部加载更多），不一次性加载全部。
```

### 修改 3：`附录 E：数据字典与 Schema 定义` - 新增两张表

在原有表结构后新增：

```sql
-- ========== 社区评论系统（贴吧模式） ==========

-- 主楼层表（对主题帖的直接回复）
CREATE TABLE post_replies (
  id VARCHAR(64) PRIMARY KEY,
  post_id VARCHAR(64) NOT NULL,          -- 关联的招募帖ID
  user_id VARCHAR(64) NOT NULL,
  floor_number INT NOT NULL,              -- 楼层号（从1开始，1楼为楼主帖内容）
  content TEXT NOT NULL,
  like_count INT DEFAULT 0,
  reply_count INT DEFAULT 0,              -- 楼中楼数量（冗余，用于列表展示）
  is_lou_zhu BOOLEAN DEFAULT FALSE,       -- 是否为楼主（1楼为TRUE）
  deleted BOOLEAN DEFAULT FALSE,          -- 软删除标记
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_post_floor (post_id, floor_number),
  INDEX idx_post_created (post_id, created_at)
);

-- 楼中楼表（单楼层下的评论）
CREATE TABLE reply_comments (
  id VARCHAR(64) PRIMARY KEY,
  reply_id VARCHAR(64) NOT NULL,           -- 关联的主楼层ID
  user_id VARCHAR(64) NOT NULL,
  parent_comment_id VARCHAR(64) NULL,      -- 支持嵌套回复（可选，简化版可不要）
  content TEXT NOT NULL,
  like_count INT DEFAULT 0,
  deleted BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_reply (reply_id, created_at)
);

-- 楼层点赞记录表（防重复点赞）
CREATE TABLE floor_likes (
  id VARCHAR(64) PRIMARY KEY,
  reply_id VARCHAR(64) NOT NULL,           -- 主楼层ID
  user_id VARCHAR(64) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_floor (reply_id, user_id)
);

-- 楼中楼点赞记录表
CREATE TABLE comment_likes (
  id VARCHAR(64) PRIMARY KEY,
  comment_id VARCHAR(64) NOT NULL,
  user_id VARCHAR(64) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_comment (comment_id, user_id)
);
```

> **设计决策说明**：
> - `floor_number` 采用物理存储而非实时计算，避免因删除导致的号段混乱。删除时 `deleted=1`，前端显示“该楼层已删除”，楼层号保留。
> - `parent_comment_id` 用于支持楼中楼内的嵌套回复（回复楼中楼的某条评论）。MVP 阶段可先不支持，设 NULL 即可。
> - 点赞表独立，防止用户重复点赞。

## 二、给程序员的沟通话术

> 以下话术可直接用于与开发团队的沟通。

### 标题：社区评论系统升级为“贴吧模式”（主楼层 + 楼中楼）

**背景**  
当前社区-招募板的评论区是简单的线性评论（类似微信公众号），用户之间互相回复会打断主贴的阅读顺序。例如：
- A 回复主题帖（1楼）
- B 回复 A 的内容（2楼）
- C 回复主题帖（3楼）

这导致 2 楼（B 的回复）与 1 楼的关系被割裂，新人看不懂对话上下文。

**决策**  
采用**贴吧式双层嵌套模式**：
- **主楼层**：用户对主题帖的直接回复，按时间排序，拥有全局唯一的楼层号（1楼、2楼…）。
- **楼中楼**：附着在某个主楼层下的二级评论，不占楼层号，折叠显示。

这样既保留了“盖楼”的互动感，又能让针对某一楼层的讨论集中在楼中楼内，不干扰主贴的整体阅读顺序。

**对现有代码的影响评估**

| 模块 | 现状 | 改动方式 | 预估工作量 |
|------|------|----------|------------|
| 数据库 | 可能已有 `comments` 表 | 新增 `post_replies`（主楼层）和 `reply_comments`（楼中楼）两张表 | 0.5 天 |
| 帖子详情页（前端） | 线性评论列表 | 重构为：主楼层列表 + 每个主楼层下方折叠楼中楼 | 2 天 |
| 回复主题帖接口 | 现有评论接口 | 修改为生成新主楼层（返回楼层号） | 0.5 天 |
| 回复某楼层接口 | 无 | 新增楼中楼接口 | 0.5 天 |
| 楼中楼展开/折叠 | 无 | 前端实现懒加载 + 展开动画 | 1 天 |
| @提及功能 | 无 | 新增用户搜索下拉框 | 1 天 |
| 楼层跳转（链接锚点） | 无 | 前端实现 `#floor=3` 滚动定位 | 0.5 天 |
| 移动端适配 | 现有列表可能不兼容 | 调整为卡片 + 底部输入框 | 1 天 |

**总计约 6-7 人天**，可分两阶段：
- **Phase 1（3 天）**：数据库表 + 主楼层基本功能（发布、列表、删除、点赞）
- **Phase 2（3-4 天）**：楼中楼 + @提及 + 楼层跳转 + 移动端适配

**重要原则（请务必遵守）**

1. **以现有已实现的功能为优先**。如果当前已经有评论系统且运行稳定，不要为了“匹配文档”而推翻重来。本文档仅作为未来迭代的参考，具体实现方式可讨论。
2. **严禁硬编码示例名称**。代码中不得出现如“黑暗边缘团”、“张三”、“李四”等固定字符串。所有用户名、团名、评论内容必须从后端数据动态获取。
3. **楼层号必须永久保留**。删除主楼层时，内容清空，但楼层号不能复用，显示“该楼层已删除”。（可参考贴吧的删除占位逻辑）
4. 若发现文档描述与现有实现冲突（如数据库表名、字段名不一致），请及时反馈，我们会同步更新文档，**不要求强行修改已有代码**。

1. 当前社区评论系统是否已经实现？如果已实现，数据结构是怎样的？（是否有 `floor_number` 概念？）
