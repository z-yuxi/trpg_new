# 旧代码复用与迁移清单

> 结论口径：当前仓库适合“保留工程骨架与通用能力，重构业务状态机与页面编排”，不适合直接在旧页面和旧接口上持续叠加。
> 执行原则：先统一契约与状态机，再改页面与视觉；先主链路，后边角功能。

---

## 1. 总体判断

### 1.1 可复用结论

- **可保留骨架**：Monorepo、前后端分包、共享类型包、PWA 外壳、Socket/Express 基础装配。
- **可保留中层能力**：规则工坊/规则执行引擎、基础 UI 组件、设计令牌体系、部分通用列表与空状态组件。
- **不可直接沿用业务层**：招募状态机、简化开团链路、房间/场景相关部分接口契约、若干页面的信息架构与状态编排。

### 1.2 实施结论

- **不是先写“大提示词”**。
- **也不是直接全仓开改**。
- 正确顺序是：

1. 写一份最小迁移实施口径。
2. 先对齐 shared 类型与 server 业务状态机。
3. 再重排 client 页面与视觉实现。

---

## 2. 可直接复用的部分

### 2.1 工程与基础设施

可直接保留：

- 根工作区脚本、pnpm workspace、Docker 与 nginx 部署骨架。
- Express 应用装配、静态资源目录、统一错误处理入口。
- Socket 服务装配与服务端启动流程。
- PWA 基础能力，包括 Service Worker 注册与安装引导壳层。

处理方式：

- **保留，不作为本轮迁移重点。**
- 仅在接口格式统一时做最小必要调整。

### 2.2 Shared 共享包

可复用内容：

- 共享领域类型的大框架：Campaign、Scene、Recruitment、Ruleset、Module、Socket events。
- 工具函数与导入导出能力，如 CSON、ILF、规则图合并相关工具。

处理方式：

- **保留包结构和导出方式。**
- **重做不一致的类型枚举、字段语义与错误码收敛。**

### 2.3 规则工坊与规则执行内核

可复用内容：

- Recipe 校验、编译、执行相关核心实现。
- 编译器/执行器测试基线与错误码基础设施。
- 规则集新旧格式兼容迁移思路。

处理方式：

- **优先保留。**
- 只围绕新版文档补齐错误契约、类型约束和测试覆盖，不推翻重写。

### 2.4 前端通用层

可复用内容：

- 设计令牌主文件与日夜主题文件。
- PageLayout、EmptyState、SvgIcon、基础卡片/标签/骨架屏组件。
- 路由守卫与登录态基础处理。

处理方式：

- **保留组件，不保留旧页面编排。**
- 页面迁移时优先套用现有通用组件，而不是继续复制散装页面结构。

---

## 3. 必须清理或重构的部分

### 3.1 招募域

问题：

- 当前类型与接口只覆盖 `open/full/closed`、`pending/approved/rejected` 这一版状态。
- 设计文档已经扩展到 `draft/grouped/dissolved/archived`，以及 `invited/confirmed/waiting` 等申请状态。
- 这会直接影响前端按钮文案、卡片状态、GM 管理页、通知流转和成团逻辑。

处理结论：

- **必须重构，不建议在旧路由上增量打补丁。**

需要做：

1. 更新 shared 类型枚举。
2. 重写 recruitment service 的状态流转规则。
3. 统一前后端按钮状态映射来源。
4. 用测试覆盖申请、邀请、确认、候补、成团、归档全链路。

### 3.2 简化开团流程

问题：

- 文档要求“从资产直接开私密团/公开招募团”，并按入口自动绑定 `module_id/ruleset_id`。
- 当前首页、资产页、campaign 创建逻辑还没有严格落地这个链路，入口和状态分叉明显。

处理结论：

- **必须作为第一批主链路改造。**

需要做：

1. 明确开团入口统一动作。
2. 区分“模组入口”与“规则包入口”的默认建团参数。
3. 明确公开招募与私密团的分流点。
4. 创建后统一跳转规则。

### 3.3 房间与场景相关契约

问题：

- shared 中的场景类型定义、服务端建场景 schema、房间交互文档存在偏差。
- 私密场可见性、场景参与、位置历史、预约移动状态等规则已经被新文档进一步精化。
- 目前部分实现可用，但口径不够稳定。

处理结论：

- **保留数据骨架，重收敛契约。**

需要做：

1. 统一 Scene、SceneParticipation、ScheduledMove、ChatMessage 的字段语义。
2. 按新版文档收敛可见性与位置历史规则。
3. 对齐移动审批、自动执行、取消、强制移动的状态机。

### 3.4 接口错误契约与幂等策略

问题：

- 文档要求统一错误格式与幂等写操作。
- 当前大量路由仍返回松散的 `error` 字符串，写操作也未形成统一幂等策略。

处理结论：

- **必须系统清理。**

需要做：

1. 统一 API 响应包络。
2. 建立错误码最小集合。
3. 给写接口补 `idempotent_key` 约束。
4. 前端 API 层统一解包和错误分发。

### 3.5 页面层与视觉落地

问题：

- 设计令牌总体方向已接近新版，但页面内仍存在历史 fallback 色值和散装布局。
- 首页可部分复用视觉方向，但 GM 页、部分管理页仍残留旧版视觉与状态组织方式。
- 个别页面存在历史实现拼接痕迹，继续叠加会提升维护成本。

处理结论：

- **通用组件保留，页面按新版信息架构重排。**

需要做：

1. 清除与视觉强制规范冲突的旧 fallback 色值。
2. 首页、招募、房间页按新版层级关系重写页面编排。
3. 把按钮状态、空状态、错误状态统一落到公共组件与 composable。

## 4. 可以延后处理的部分

这些内容可以在主链路跑通后再做：

- 纯展示型静态页面的精修。
- 创作者后台中未影响主链路的局部视觉优化。
- 市场、商业化、会员等 MVP 外链路。
- 文本艺术、装饰动画、非关键微交互的进一步抛光。

原则：

- **不阻塞“开团 -> 招募/加入 -> 进入房间 -> 房间内移动/消息/管理”主链路的功能，可延后。**

## 5. 推荐实施顺序

### Phase 0：最小实施口径

产物：一页迁移执行说明。

必须写清：

- 文档优先级。
- 统一术语。
- 禁止沿用的旧状态机。
- 验收标准与 Fallback 规则。

说明：

- 这不是新写一套通用提示词，而是把现有文档约束压缩成迁移期可执行模板。

### Phase 1：Shared 与 Server 契约收敛

先做：

1. 招募状态机。
2. 简化开团请求/响应契约。
3. 房间场景与预约移动关键类型。
4. 错误码与统一响应格式。

验收：

- shared 类型稳定。
- server 路由与 service 能按新状态机工作。
- 对应测试通过。

### Phase 2：主链路前端重排

先做页面：

1. 首页。
2. 探索/我的资产开团入口。
3. 招募板与招募详情。
4. 房间。
5. 房间页与 GM 控制台核心页。

验收：

- 用户可以从探索或我的资产完成开团。
- 玩家可完成申请、确认、加入、进入房间。
- GM 可完成审批移动与基本房间管理。

### Phase 3：视觉规范扫尾与边缘页回填

做法：

- 全局检索非法色值和散装状态实现。
- 收口为 design tokens + 公共组件 + composable。
- 清理旧命名、旧注释和历史兼容分支。

---

## 6. 是否先设计提示词

结论：**不先设计“大提示词”，先做最小迁移口径。**

原因：

- `产品设计.md` 与视觉强制规范已经提供了足够的 AI 约束。
- 当前真正的问题不是“AI 不知道怎么写”，而是“旧代码状态机和新版文档已经分叉”。
- 如果先写一大套提示词但不先收敛 shared/server 契约，只会加速错误实现。

建议做法：

- 只补一个 **迁移任务模板**，每次开发任务固定包含：
  - 功能目标。
  - 文档优先级。
  - 统一术语。
  - 本次禁止沿用的旧实现。
  - 验收标准。

---

## 7. 下一步建议

如果开始正式迁移，建议按以下顺序执行：

1. 先新增一份“迁移执行口径”文档。
2. 先改 shared 的招募与开团相关类型。
3. 再改 server 的 recruitment/campaign 服务和路由。
4. 然后改首页、探索/我的资产、招募三条前端主入口。

这四步完成后，再继续房间内状态机与视觉统一，返工成本最低。
