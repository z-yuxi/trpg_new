## 一、项目基本信息

- **工程结构**：monorepo（pnpm workspace），三包：`@trpg/client`（Vue 3 + Vite）、`@trpg/server`（Node.js + Express + Knex + Socket.IO）、`@trpg/shared`（公共类型与工具）
- **数据库**：SQLite（开发）/ PostgreSQL（生产），迁移文件在 `packages/server/src/db/migrations/`，已有 001~014 共 14 个迁移
- **实时通信**：Socket.IO，客户端入口 `packages/client/src/socket/socket-client.ts`
- **UI 组件库**：Element Plus + 自定义 base 组件（`TCard`、`TButton`、`TTag` 等在 `packages/client/src/components/base/`）
- **状态管理**：Pinia（`auth-store`、`campaign-store`、`message-store`、`notification-store`）
- **规则引擎**：纯 TypeScript，位于 `packages/server/src/engine/`，三层指令解析（通用/预置/自定义）
- **关键约束**：纯 Web + PWA，无 Electron，无 AI 功能（V1.0），无支付（V1.0 商业化未实现）

## 三、明确缺失的功能（需后续实现）

### 3.1 高优先级（直接影响核心玩法）

#### A. 职业解析器 ENG-013
- **设计文档位置**：`产品设计.md` 第 2.3 节
- **现状**：角色卡中已有 `occupation_id` 字段，但服务端无职业逻辑运算层
- **需实现**：
  - 职业模板数据结构（`OccupationTemplate`）的 DB 表和 API
  - `OccupationTemplate.feature_graph` 与规则引擎的绑定（动态注册效果节点）
  - COC 静态职业（一次性应用）vs DND 等级制职业（升级/兼职/特性获得）两种模式
  - 创作者在规则工坊中定义职业的 UI
- **建议迁移文件**：`015_occupation_templates.ts`

#### B. 私密场邀请/权限流程完整化
- **现状**：后端 `scene_participations` 表存在，但前端邀请玩家加入私密场的 UI 不完整
- **需实现**：
  - 玩家在房间内创建私密场的入口（顶部场列表标签页右侧 `[+]` 按钮）
  - 主持人邀请成员的对话框（选人 + 确认）
  - GM 可直接指定参与者的控制台操作
  - 私密场成员列表展示（仅主持人/GM 可见）
- **关键文件**：`LeftSidebar.vue`、`Room.vue`、`routes/campaigns.ts`

#### C. 规则引擎原子补全（目标 50+，现有约 15 个）
- **现状**：`packages/server/src/engine/atoms/` 下有约 15 个原子
- **缺失原子类型**（参考设计文档第 2.1 节 功能4）：
  - 技能增长类（skill-growth、attribute-growth）
  - 资源检查类（resource-check）
  - 时序控制类（delay、sequence）
  - 高级比较类（range-check、multi-threshold）
  - 输出格式类（message-template、card-render）
  - 链式调用类（chain-resolver，设计中 sc/san_check 需要）
- **建议**：每个原子独立 `.ts` 文件，遵循现有 `atom-interface.ts` 接口

### 3.2 中优先级（影响创作者体验）

#### D. 自定义原子打包复用（功能 9）
- **设计文档位置**：`产品设计.md` 第 2.1 节 功能 9
- **需实现**：
  - 在 L3 画布中选择多个原子节点并「打包为组件」
  - 组件有独立的输入/输出端口定义界面
  - 组件可在画布中像原子一样使用（`is_custom: true`）
  - 组件发布到组件市场（V1.0 可仅实现前两步，发布留空）

#### E. 模组公示期状态机
- **现状**：模组 `status` 枚举为 `draft | reviewing | published | suspended`，缺少 `public_notice`
- **需实现**：
  - 迁移文件添加 `public_notice` 状态和 `public_notice_end_at` 时间字段
  - 后端定时任务：公示期满自动转为 `published`（可用 `setInterval` 轮询或 Redis 延时队列）
  - 前端展示公示倒计时

#### F. 模组 Word/TXT 导入（非 AI 版本）
- **设计文档位置**：`产品设计.md` 第 3.2 节 功能 5
- **V1.0 简化版**：仅支持纯文本（TXT）上传，按段落切分后填入自由文本块，不做 AI 识别
- **需实现**：上传接口 + 前端文件选择 + 段落切分逻辑（AI 辅助识别留待后续）

### 3.3 低优先级（商业化 / 会员体系）

#### G. 订阅购买流程
- **现状**：`subscription_type` 字段存在（free/pro/creator），但无购买页面
- **V1.0 最简实现**：无真实支付，仅管理员后台手动升级（通过 API），前端展示升级引导页

#### H. 规则包/模组付费
- **现状**：DB 预留了 `price`、`pricing_type` 字段，但无购买流程
- **V1.0 暂缓**：保持现有"全部免费"逻辑，付费流程留待后续版本

## 四、代码质量改进建议

### 4.1 重构优先级（高）

1. **`GMConsole.vue` 拆分**  
   该组件包含时间控制、移动审批、NPC 管理、场景管理、线索库、轨迹矩阵、地图、广播 8 个 Tab 的全部逻辑，Script 段超过 600 行。  
   建议：将每个 Tab 内容拆为独立组件（已有 `TrajectoryMatrix.vue`、`GridMap.vue`、`GmClueLibrary.vue` 可参考），`GMConsole.vue` 仅保留 Tab 切换框架。

2. **统一 API 调用封装**  
   `GMManagement.vue`、`Room.vue` 等多处直接使用裸 `fetch` 而非 `packages/client/src/utils/api.ts` 中的封装。  
   建议：所有 API 调用均通过 `api.ts` 的封装方法，统一处理 token 注入和错误拦截。

### 4.2 重构优先级（中）

3. **`Room.vue` Script 段过长**  
   建议将「场景列表管理」「NPC 身份切换」「左侧导航数据」各自提取为 composable（`useSceneManagement.ts`、`useNpcIdentity.ts` 等）。

4. **引擎原子的统一注册入口**  
   目前 `engine/atoms/index.ts` 手动 export，新增原子需手动维护列表。  
   建议：使用 `import.meta.glob`（Vite 环境）或在 Node.js 侧用 `fs.readdirSync` 自动扫描 `atoms/` 目录注册。

## 五、开发规范与代码约定（必须遵守）

1. **禁止硬编码示例名称**：团名、场景名、角色名等一律从后端数据动态获取，严禁在代码中写死"黑暗边缘团"等示例名
2. **禁止 emoji**：界面文字、注释、变量名均不使用 emoji
3. **ID 规范**：使用雪花 ID（消息）或 UUID（其他实体），格式见附录 A
4. **UI 设计规范**：遵循 `附录 B：UI设计规范.md`，使用 CSS 变量（`--color-*`、`--text-*`）
5. **API 接口规范**：RESTful，统一 `/api/` 前缀，错误响应格式 `{ error: string, code?: string }`
6. **类型共享**：跨包共享类型定义在 `packages/shared/src/types/index.ts`，工具函数在 `packages/shared/src/utils/`
7. **迁移文件**：新增表必须创建单独迁移文件，编号递增，文件名格式 `0XX_描述.ts`
8. **测试**：新增服务层方法须有对应单测，放在同包 `src/__tests__/` 目录
9. **无 AI 功能**：V1.0 所有 AI 相关代码均不实现，仅预留接口注释
10. **无第三方支付**：V1.0 支付集成留空，仅保留数据模型
