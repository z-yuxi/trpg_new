# TRPG 平台成熟度补齐执行检查表

> 适用范围：平台从“功能可用”推进到“可稳定上线、可商业化、可持续运营”阶段
> 使用方式：每一步必须明确负责人、输入材料、输出物、验收结果与回滚方案，再进入下一步

---

## Step 1. 统一目标口径与上线红线

### 负责人角色
- 产品负责人
- 技术负责人
- 运营负责人

### 输入
- 当前版本路线图
- 已知问题清单
- 线上/灰度事故记录
- 商业化目标与本期上线范围

### 输出
- 一页版阶段目标说明
- 上线红线清单
- 阻断发布问题定义
- 非阻断问题延后规则

### 执行检查
- [ ] 明确本阶段只追求哪三项核心结果
- [ ] 定义哪些问题会直接阻断发布
- [ ] 定义哪些问题允许带病上线但需补偿
- [ ] 明确谁有最终发布否决权

### 验收条件
- 产品、技术、运营三方对目标与红线无歧义
- 出现争议时，能直接按文档判断是否发布

### 阻塞项
- 路线图频繁变更
- 目标过多且相互冲突
- 没有统一的事故分级标准

### 回滚点
- 若范围迟迟无法冻结，回退到“仅保核心链路上线”的口径
- 暂停新需求并重新确认 MVP 边界

---

## Step 2. 冻结核心业务契约

### 负责人角色
- 后端负责人
- 前端负责人
- 产品经理

### 输入
- API 契约文档
- 数据库表结构
- 前端页面交互稿
- 状态机与错误码定义

### 输出
- 核心接口冻结版契约
- 统一状态机图
- 错误码字典
- 字段命名与兼容策略说明

### 执行检查
- [ ] 支付、权益、订单、退款、消息可见性字段全部冻结
- [ ] 成功态、失败态、重试态、取消态全部有定义
- [ ] 前后端对错误码和提示语映射一致
- [ ] 变更契约时有版本策略与兼容说明

### 验收条件
- 前后端可以独立按契约联调
- 不再出现“字段存在但语义不一致”问题

### 阻塞项
- 历史遗留字段未清理
- 文档与实现双轨并行
- 状态机仍在频繁改动

### 回滚点
- 若无法一次冻结，先冻结主链路字段，其余字段标为实验态或内部字段

---

## Step 3. 打通真实支付通道

### 负责人角色
- 后端工程师
- 支付对接负责人
- 测试工程师

### 输入
- 支付渠道接入文档
- 订单模型与签名规则
- 回调地址与密钥配置
- 沙箱账号与测试案例

### 输出
- 支付下单接口
- 回调验签逻辑
- 支付状态更新链路
- 沙箱联调记录

### 执行检查
- [ ] 至少接通一个真实支付渠道或完整沙箱
- [ ] 验签、幂等、超时、重试、乱序回调均有处理
- [ ] 重复回调不会重复发货
- [ ] 失败与取消订单能正确收敛状态

### 验收条件
- 成功支付、失败支付、超时支付、重复回调四类场景全部跑通
- 日志中可追踪每一笔支付请求与回调处理结果

### 阻塞项
- 商户资质未完成
- 测试环境不稳定
- 密钥配置与网络白名单未就绪

### 回滚点
- 保留“订单创建但不跳真实支付”的降级开关
- 支付通道异常时切回内测/白名单支付模式

---

## Step 4. 完成“支付到账 -> 权益发放”原子链路

### 负责人角色
- 后端负责人
- 数据库负责人
- 测试工程师

### 输入
- 支付成功状态定义
- 权益模型设计
- 事务边界与补偿策略
- 审计日志要求

### 输出
- 权益发放服务
- 发放幂等键设计
- 失败补偿机制
- 审计流水与追溯脚本

### 执行检查
- [ ] 支付成功后能自动发放对应权益
- [ ] 同一订单重复通知只发放一次
- [ ] 发放失败有补偿任务或人工重放入口
- [ ] 权益查询结果与订单状态保持一致

### 验收条件
- 不存在“已支付但未发放”或“未支付却已发放”脏数据
- 任意订单都能追溯到发放记录与操作者/系统动作

### 阻塞项
- 权益表结构未定
- 历史订单没有统一唯一键
- 事务与异步队列边界不清晰

### 回滚点
- 发放服务异常时，暂停自动发放，切人工补单流程
- 回滚到只记录 paid 状态，不立即开放权益入口

---

## Step 5. 建立财务与风控闭环

### 负责人角色
- 支付运营
- 后端工程师
- 风控负责人

### 输入
- 订单流水
- 渠道对账单
- 退款规则
- 风险场景案例

### 输出
- 每日对账流程
- 异常订单处理台账
- 退款/撤销处理规范
- 风控规则清单

### 执行检查
- [ ] 每日可产出渠道订单与平台订单对账结果
- [ ] 重复支付、异常金额、短时高频支付有规则拦截
- [ ] 退款后权益回收策略明确
- [ ] 黑名单、限流、人工复核条件有定义

### 验收条件
- 财务可确认每笔钱的状态、归属与异常去向
- 风控规则至少覆盖高频刷单、重复回调、异常账号行为

### 阻塞项
- 没有对账数据源
- 权益与退款规则冲突
- 没有统一异常单处理人

### 回滚点
- 如自动风控误伤率过高，先切为“告警不拦截”模式
- 退款链路未稳定前，限制可退款商品范围

---

## Step 6. 建立可观测体系

### 负责人角色
- 后端工程师
- DevOps
- 值班负责人

### 输入
- 核心接口列表
- 异步任务列表
- 当前日志方案
- 事故响应要求

### 输出
- 结构化日志规范
- 核心业务指标清单
- 告警规则
- 线上排障仪表盘

### 执行检查
- [ ] 核心请求都有 trace_id 或 request_id
- [ ] 支付、招募、消息、登录有关键业务指标
- [ ] 5xx、超时、队列堆积、支付失败率有告警
- [ ] 值班同学能靠仪表盘判断故障位置

### 验收条件
- 出现故障时，可在 10 分钟内定位到接口、任务或依赖层级
- 日志、指标、告警三者口径一致

### 阻塞项
- 日志格式不统一
- 指标点位缺失
- 没有值班接收通道

### 回滚点
- 若无法一次上完整平台，先做最小可用：错误日志 + 关键指标 + 人工值班告警群

---

## Step 7. 把关键用户旅程做成 E2E 自动化

### 负责人角色
- QA
- 前端工程师
- 后端工程师

### 输入
- 主链路用例清单
- 测试账号与测试数据
- 预发环境地址
- 关键页面与接口稳定选择器

### 输出
- E2E 测试框架
- 首批主链路自动化用例
- 失败截图/日志归档
- 发布门禁规则

### 执行检查
- [ ] 至少覆盖登录、招募、成团、消息、支付主流程
- [ ] 用例可重复执行，不依赖手工预处理
- [ ] 失败时能直接看到步骤、截图与日志
- [ ] E2E 被纳入 CI 门禁或发布前固定流程

### 验收条件
- 每次发布前都能自动回归核心路径
- 新故障能先补用例再修复，防止再次回归

### 阻塞项
- 页面选择器不稳定
- 测试数据不可重复使用
- 预发环境经常脏掉

### 回滚点
- 若全链路过重，先只保留 smoke 级 E2E，完整回归拆到夜间任务

---

## Step 8. 建立发布与回滚作战流程

### 负责人角色
- 技术负责人
- DevOps
- QA

### 输入
- 当前 CI/CD 流程
- 灰度能力
- 健康检查接口
- 历史回滚经验

### 输出
- 发布 SOP
- 灰度放量规则
- 回滚决策树
- 演练记录

### 执行检查
- [ ] 发布前检查项有固定清单
- [ ] 灰度比例、观察窗口、放量条件明确
- [ ] 回滚触发阈值量化
- [ ] 至少做过一次真实演练

### 验收条件
- 团队成员能不依赖口头说明执行一次完整发布/回滚
- 故障发生时能在文档内找到下一步动作

### 阻塞项
- 没有灰度能力
- 回滚依赖人工记忆
- 数据迁移不可逆且无备份

### 回滚点
- 如灰度链路不稳定，回退到单批次发布 + 强制备份 + 人工观察模式

---

## Step 9. 做稳定性专项

### 负责人角色
- 后端工程师
- 测试工程师
- DevOps

### 输入
- 核心接口列表
- 性能基线
- 慢查询与报错日志
- 历史脏数据样本

### 输出
- 压测报告
- 限流与降级策略
- 脏数据修复脚本
- 容量基线说明

### 执行检查
- [ ] 对登录、招募、消息、支付做压测
- [ ] 明确每个接口的限流与超时策略
- [ ] 有慢查询分析与索引优化结论
- [ ] 历史脏数据有清理脚本和回放方案

### 验收条件
- 高峰流量下核心接口仍满足既定响应目标
- 脏数据不会继续扩散，且历史问题可批量修复

### 阻塞项
- 测试环境容量与线上差太大
- 压测数据不真实
- 脏数据来源未定位

### 回滚点
- 如优化风险过高，先启用更严格限流与降级，延后深度重构

---

## Step 10. 强化移动端与弱网体验

### 负责人角色
- 前端工程师
- QA
- 产品经理

### 输入
- 移动端页面清单
- PWA/缓存策略
- 弱网测试脚本
- 终端机型覆盖范围

### 输出
- 弱网交互规范
- 重连/失败提示方案
- 离线缓存边界说明
- 移动端专项验收报告

### 执行检查
- [ ] 断网、抖动网、切后台、恢复网络都有验证
- [ ] 关键表单提交失败时可恢复或重试
- [ ] Socket 重连后状态同步正确
- [ ] 移动端布局、点击区、输入法交互可用

### 验收条件
- 在常见弱网场景下，用户不会因无提示失败而丢失关键操作
- 关键页面在主流移动端尺寸下可正常使用

### 阻塞项
- 没有统一网络失败提示
- 状态恢复逻辑依赖页面重刷
- 真机覆盖不足

### 回滚点
- 对不稳定的离线能力降级为只读缓存，不做写操作缓存回放

---

## Step 11. 搭建增长与运营闭环

### 负责人角色
- 运营负责人
- 数据分析
- 后端工程师

### 输入
- 招募、留存、转化定义
- 埋点方案
- 用户分层策略
- 触达渠道能力

### 输出
- 漏斗定义文档
- 核心运营看板
- 用户分群策略
- 基础触达与召回流程

### 执行检查
- [ ] 有统一的新增、活跃、留存、转化口径
- [ ] 招募浏览到申请到成团漏斗可追踪
- [ ] 会员、创作者、普通玩家有基本分层
- [ ] 至少一条召回或提醒链路已跑通

### 验收条件
- 运营能每周固定复盘数据并提出动作
- 关键增长指标变化可以追溯到活动、产品改动或实验

### 阻塞项
- 埋点缺失或字段不统一
- 指标定义多版本并存
- 没有触达渠道或模板机制

### 回滚点
- 若自动触达质量差，先退回人工运营名单制触达

---

## Step 12. 做国际化与扩展准备

### 负责人角色
- 前端负责人
- 产品经理
- 设计师

### 输入
- 目标区域或语种规划
- 文案清单
- 时间、货币、时区规则
- 法务与内容合规要求

### 输出
- 多语言资源规范
- 本地化组件改造清单
- 区域化配置方案
- 首个可运行的非中文流程

### 执行检查
- [ ] 文案从代码中抽离
- [ ] 时间、货币、时区展示可配置
- [ ] 关键注册、支付、通知文案支持多语言
- [ ] 目标区域需要的合规项有列表

### 验收条件
- 至少一个非中文语言环境能完整跑通主流程
- 不需要二次改代码即可新增文案资源

### 阻塞项
- 文案硬编码遍布页面
- 接口返回文案不可控
- 合规要求未确认

### 回滚点
- 若全面国际化范围过大，先只抽离公共文案并支持单一区域试点

---

## Step 13. 收尾治理与技术债清单

### 负责人角色
- 技术负责人
- 各模块 owner
- QA

### 输入
- TODO/FIXME 列表
- 临时开关清单
- 兼容逻辑清单
- 上线后遗留问题列表

### 输出
- 技术债看板
- 下线开关计划
- 历史兼容逻辑清理计划
- 发布后观察与复盘模板

### 执行检查
- [ ] 所有临时开关都有 owner 与下线条件
- [ ] 所有已知技术债有优先级和影响面说明
- [ ] 不再需要的兼容逻辑有清退计划
- [ ] 发布后 24h / 72h / 7d 复盘节点明确

### 验收条件
- 团队能清楚区分“必须立即还”的债与“可延期处理”的债
- 发布后不会因为临时逻辑长期堆积导致系统不可维护

### 阻塞项
- 没有统一债务归口
- 临时开关散落在代码和环境变量中
- 责任人不明确

### 回滚点
- 如债务清理影响主链路稳定，先冻结现状，仅清理高风险兼容分支
